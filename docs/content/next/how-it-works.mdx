# How it works

<Callout>**Status.** The next version of Deco is being designed in the open: the API on these pages is proposed and not released yet. The [Roadmap](/roadmap) lists what's left.</Callout>

Most of what changes on a website isn't the code. It's the values the code is given: a headline, a banner image, the share of visitors who see the new checkout. Deco keeps the two apart. Developers write ordinary functions, and the values live as JSON files in your Git repository. Editors change them in [Studio](#studio), Deco's content editor; AI agents edit the files directly; and every change ships with your next deploy.

This page follows one such change, marketing switching the summer banner from "Free shipping over $75" to "Free shipping over $50", from the first line of code to a visitor's screen, and points you to the page that explains each step.

## The life of a change

<Flow label="The life of a change">
  <FlowNode title="1. Write">A developer writes `PromoBanner`</FlowNode>
  <FlowNode title="2. Schema">Its types become a form</FlowNode>
  <FlowNode title="3. Edit">Someone changes the text</FlowNode>
  <FlowNode title="4. Ship">The change goes out with your next deploy</FlowNode>
  <FlowNode title="5. Render">Your app shows the new banner</FlowNode>
</Flow>

### 1. A developer writes the function

The banner is an ordinary component, `PromoBanner`, whose props are typed: a `title` and an `href`. The developer adds it to the block map, which gives each function a name content can call, such as `"promo-banner"`. That's the only Deco-specific code you write. See [Blocks](/next/blocks).

### 2. The types become a form

The `deco schema` command reads those prop types and writes a schema file, `.deco/schema.json`. Studio builds a form from that file, so `title` becomes a text box without anyone designing a form. See [Schema](/next/schema).

### 3. Someone changes the content

The banner's text lives in a saved block: a JSON file in your repository, `.deco/blocks/SummerBanner.json`, that calls `promo-banner` with a `title` of "Free shipping over $75". Edit the file via a [text](/next/blocks#blocks-in-your-repository) or [Studio](#studio) editor. Either way, the change is a commit like any other.

### 4. The change ships

Your usual CI builds and deploys the app, and the new text goes live with it, the same way a code change does. See [Releases and deployment](/next/releases-and-deployment).

<Hosted to="/next/hosted-publishing" label="Publishing without a deploy">**No deploy needed.** With the hosted Deco CMS, a published change reaches visitors within seconds, with no new build or deploy.</Hosted>

### 5. Your app renders it

Your app asks the SDK (the `client` your app gets from `cms.forRelease()`, where `cms` comes from `createCMS`) for `SummerBanner`. The SDK calls `PromoBanner` with the saved props and hands back the result, which you render like any other component. See [Rendering](/next/rendering) for the two ways that result reaches the browser.

## The pieces

Each step above has one owner. Deco provides one package, `@decocms/blocks`, and an editor; shipping is your hosting's job:

| Piece | Step | Reference |
|---|---|---|
| **SDK** (`@decocms/blocks`) | 5. Your app renders it | [API reference](/next/api-reference) |
| **CLI** (`deco`, in `@decocms/blocks`) | 2. The types become a form | [CLI](/next/cli) |
| **Studio** | 3. Someone changes the content | [Studio](#studio) |
| **Hosting** | 4. The change ships | [Releases and deployment](/next/releases-and-deployment) |

The SDK and CLI are open source and run without a Deco account.

### Studio

Studio is Deco's content editor: the web app where marketing and the rest of the business change your site without touching code. It shows a form for each block, built from your types, and saves every change back to the JSON files in `.deco/blocks`. You can test it on your own machine via [`npx @decocms/blocks serve`](/next/cli#deco-serve): run it in your project and open the link it prints. Studio then edits the JSON files in your project folder. (Doing this without a Deco account is planned; see the [Roadmap](/roadmap#roadmap-platform--add-a-play-workspace-for-local-editing).) Deco also hosts Studio, with a few add-ons on top of the same files:

- **Publishing without a deploy:** a published change reaches visitors without a new build.
- **Editing on GitHub:** editors change your GitHub repository straight from the browser, with nothing to install; each save is a commit.
- **Drafts on your real site:** preview a change on your actual pages before it's published.
- **Asset storage:** uploaded images go to a CDN instead of your repository.
- **Telemetry:** errors and upstream latency from your site, with nothing to set up.

## Small on purpose

- **Content is plain JSON.** Read it, diff it, or generate it with a script. There's no database to host.
- **Block functions are plain functions.** You can call any of them directly in a test.
- **Data fetching is your code.** See [Upstream API clients](/next/upstream-clients).
- **Nothing is hidden.** The formats are documented in [Blocks](/next/blocks) and [Internals](/next/internals).

## Key terms

<Terms>
  <Term name="Block">A piece of JSON that names a function to call, plus the inputs to call it with. See [Blocks](/next/blocks).</Term>
  <Term name="Block function">One of your functions with a typed first parameter, such as `PromoBanner`. See [Blocks](/next/blocks#functions-as-blocks).</Term>
  <Term name="Block type">A name in the block map, such as `"promo-banner"`, that a block's `__resolveType` uses to call a function. See [The block map](/next/blocks#the-block-map).</Term>
  <Term name="Block map">An object from names to your block functions, such as `{ "promo-banner": PromoBanner }`, that you pass to `createCMS`. See [The block map](/next/blocks#the-block-map).</Term>
  <Term name="Saved block">A block stored under a name, as one JSON file in `.deco/blocks`, such as `SummerBanner.json`. See [Blocks in your repository](/next/blocks#blocks-in-your-repository).</Term>
  <Term name="Schema">`.deco/schema.json`, the file `deco schema` generates from your types. See [Schema](/next/schema).</Term>
  <Term name="Studio">Deco's visual editor. See [Studio and the content protocol](/next/content-protocol).</Term>
  <Term name="Resolve">What `client.resolve` does: read a saved block and call its function with the saved inputs. See [How resolution works](/next/how-resolution-works).</Term>
</Terms>

### Other terms

<Terms>
  <Term name="Framework binding">`@decocms/tanstack` or `@decocms/nextjs`: an optional package for what depends on where your site runs, such as upstream and page caching. Not wired into these guides yet; see the [Roadmap](/roadmap#roadmap-api--cache-upstream-requests-in-the-bindings).</Term>
  <Term name="Platform template">A starter site per commerce platform (VTEX, Shopify, …) that you copy and then own. Not available yet; see the [Roadmap](/roadmap#roadmap-api--turn-the-apps-into-thin-instrumented-clients).</Term>
</Terms>
