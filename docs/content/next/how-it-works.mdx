# How it works

<Callout>**Status.** Deco Blocks is being designed in the open: the API on these pages is proposed and not released yet. The [Roadmap](/roadmap) lists what's left.</Callout>

Suppose marketing wants the summer banner to say "Free shipping over $50" instead of "Free shipping over $75". In most apps, that's a ticket for a developer. With Deco Blocks, the banner is a function a developer wrote once, and the text it shows is content anyone on the team can change. This page follows that one change from the first line of code to a visitor's screen, and points you to the page that explains each step.

## The life of a change

<Flow label="The life of a change">
  <FlowNode title="1. Write">A developer writes `PromoBanner`</FlowNode>
  <FlowNode title="2. Schema">Its types become a form</FlowNode>
  <FlowNode title="3. Edit">Someone changes the text</FlowNode>
  <FlowNode title="4. Ship">The change goes out with your next deploy</FlowNode>
  <FlowNode title="5. Render">Your app shows the new banner</FlowNode>
</Flow>

### 1. A developer writes the function

The banner is an ordinary component, `PromoBanner`, whose props are typed: a `title` and an `href`. The developer adds it to the block map, which gives each function a name content can call, such as `"promo-banner"`. That's the only Deco-specific code you write. See [Blocks](/next/blocks).

### 2. The types become a form

The `deco schema` command reads those prop types and writes a schema file, `.deco/schema.json`. Studio, Deco's visual editor, builds a form from that file, so `title` becomes a text box without anyone designing a form. See [Schema](/next/schema).

### 3. Someone changes the content

The banner's text lives in a saved block: a JSON file in your repository, `.deco/blocks/SummerBanner.json`, that calls `promo-banner` with a `title` of "Free shipping over $75". An editor changes it in Studio, an AI agent edits it, or a developer opens it, and each change is a commit like any other. See [Blocks in your repository](/next/blocks#blocks-in-your-repository).

### 4. The change ships

The `deco content` command turns `.deco/blocks` into a module your app imports, and your next deploy serves the new text. See [Releases and deployment](/next/releases-and-deployment).

<Hosted to="/next/hosted-publishing" label="Publishing without a deploy">**No deploy needed.** With the hosted Deco CMS, a published change reaches visitors in about a minute, with no new build or deploy.</Hosted>

### 5. Your app renders it

Your app asks the SDK (the `client` your app gets from `createCMS`) for `SummerBanner`. The SDK calls `PromoBanner` with the saved props and hands back the result, which you render like any other component. See [Rendering](/next/rendering) for the two ways that result reaches the browser.

## The pieces

Everything above runs on one package, `@decocms/blocks`, plus a visual editor:

| Piece | Where it shows up | Reference |
|---|---|---|
| **SDK** (`@decocms/blocks`) | Step 5 | [API reference](/next/api-reference) |
| **CLI** (`deco`, in `@decocms/blocks`) | Steps 2 and 4 | [CLI](/next/cli) |
| **Studio** | Steps 2 and 3 | [Studio and the content protocol](/next/content-protocol) |

The SDK and CLI are open source and run without a Deco account. Local editing in Studio without an account is planned through a play workspace ([Roadmap](/roadmap#roadmap-platform--add-a-play-workspace-for-local-editing)).

## Key terms

<Terms>
  <Term name="Block">A piece of JSON that names a function to call, plus the inputs to call it with. See [Blocks](/next/blocks).</Term>
  <Term name="Block function">One of your functions with a typed first parameter, such as `PromoBanner`. See [Blocks](/next/blocks#functions-as-blocks).</Term>
  <Term name="Block map">An object from names to your block functions, such as `{ "promo-banner": PromoBanner }`, that you pass to `createCMS`. See [The block map](/next/blocks#the-block-map).</Term>
  <Term name="Saved block">A block stored under a name, as one JSON file in `.deco/blocks`, such as `SummerBanner.json`. Also called a saved entry. See [Blocks in your repository](/next/blocks#blocks-in-your-repository).</Term>
  <Term name="Schema">`.deco/schema.json`, the file `deco schema` generates from your types. See [Schema](/next/schema).</Term>
  <Term name="Studio">Deco's visual editor. See [Studio and the content protocol](/next/content-protocol).</Term>
  <Term name="Resolve">What `client.resolve` does: read a saved block and call its function with the saved inputs. See [How resolution works](/next/how-resolution-works).</Term>
</Terms>

### Other terms

<Terms>
  <Term name="Framework binding">`@decocms/tanstack` or `@decocms/nextjs`: an optional package for what depends on where your site runs, such as upstream and page caching. Not wired into these guides yet; see the [Roadmap](/roadmap#roadmap-api--cache-upstream-requests-in-the-bindings).</Term>
  <Term name="Platform template">A starter site per commerce platform (VTEX, Shopify, …) that you copy and then own. Not available yet; see the [Roadmap](/roadmap#roadmap-api--turn-the-apps-into-thin-instrumented-clients).</Term>
</Terms>

## Small on purpose

- **Content is plain JSON.** Read it, diff it, or generate it with a script. There's no database to host.
- **Block functions are plain functions.** You can call any of them directly in a test.
- **Data fetching is your code.** See [Upstream API clients](/next/upstream-clients).
- **Nothing is hidden.** The formats are documented in [Blocks](/next/blocks) and [Internals](/next/internals).
