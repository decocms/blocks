# Telemetry

Telemetry is a hosted feature. The framework doesn't send telemetry on its own: without the hosted Deco CMS, the instrumented fetch your [upstream clients](/next/upstream-clients) use measures every request but sends nothing, and the [Telemetry entry](#telemetry-settings-are-content) is inert. Teams that want their own observability instrument their own code with OpenTelemetry as usual (see [Your own tracing](/next/caching-and-observability#your-own-tracing)). With a connected site, those measurements reach Deco with no collector to run.

<Callout>**Status.** Telemetry, the Telemetry entry and its field names are proposed; see the [Roadmap](/roadmap#roadmap-platform--build-the-telemetry-collector).</Callout>

## What it is

**Telemetry** is sampled, aggregated measurements of your site's own requests and the third-party APIs it calls, so Deco can show you upstream latency and error rates for your site and spot regressions. It uses the same site ID and site token that load your releases, so there's nothing else to configure:

```ts title="cms.ts"
export const cms = createCMS({
  blocks,
  content,
  site: process.env.DECO_SITE,          // your site's ID in the hosted Deco CMS
  token: process.env.DECO_SITE_TOKEN,   // your site token (secret)
});
```

Without a site and a token, nothing is sent: in development, in tests, and on any site that doesn't use the hosted Deco CMS. See [Connect your site](/next/hosted#connect-your-site).

## What's sent

| Measurement | Labels | Reported by |
|---|---|---|
| Upstream latency: each request to a third-party API, timed until its response headers arrive | `provider`, `operation`, `status_class` (2xx, 4xx, 5xx, error), `cached`, `retries` | The framework's instrumented fetch, `createInstrumentedFetch`, which every [upstream client](/next/upstream-clients) uses |
| Inbound requests: duration and status of the requests your site serves | route kind, `status_class` | Your framework binding |
| Edge cache: hits and misses for rendered pages and upstream responses | cache layer, outcome | Your framework binding |
| Error logs | error code, block type, provider | The SDK and the bindings |

The bindings' caching and request metrics aren't in the framework guides yet. An app that uses only `@decocms/blocks` sends upstream latency and error telemetry from the instrumented fetch, but no binding-level cache or inbound metrics yet (see the [Roadmap](/roadmap#roadmap-api--add-observability-seams)).

A retried request counts once, with the number of retries as the `retries` label, so retries don't inflate request counts. Error logs are structured: they carry the error's code, message and where it happened, never upstream response bodies, tokens or cookies.

The instrumented fetch reports to the CMS in the same process; how that works with several instances is [under the hood](/next/hosted-releases-internals#telemetry-with-several-instances).

## Sampling

Telemetry is heavily sampled, so its cost stays flat as traffic grows:

- **Metrics are aggregated** in memory, per server, and sent in batches: counts, sums and latency buckets per combination of labels, not one record per request.
- **Error logs are sampled** at the rate the telemetry settings give, so a burst of identical errors sends a few examples, not thousands.
- **Sending never delays a response.** Batches go out in the background (on Cloudflare Workers, after the response, inside `ctx.waitUntil`), and a collector that's down only loses that batch.

## Telemetry settings are content

The settings live in a **Telemetry entry**: a well-known saved block named `Telemetry`, whose type, `telemetry`, the framework provides as a [built-in block](/next/blocks#built-in-blocks), so `deco schema` always includes it and [Studio](/next/how-it-works#studio) shows it as a form:

```json title=".deco/content/Telemetry.json"
{
  "__resolveType": "telemetry",
  "enabled": true,
  "metrics": true,
  "errorSampleRate": 0.05
}
```

The entry is an ordinary file in `.deco/content`: `deco content` scaffolds it in every repository (without a connected site it's inert, and you can delete it), and it travels with every release. To switch telemetry off, set `enabled` to `false`, in Studio or in a commit. Changing it in Studio works like any other content edit: Studio commits the change to your site's repository through its [GitHub backend](/next/hosted-studio), the Deco API serves that commit as the current release within seconds, and running servers pick it up with their next content check. There's no separate channel: a remote switch-off, during an incident for example, is that same commit, visible in your Git history. Without the entry, a connected site uses the values the scaffold writes, shown above: telemetry and metrics on, and 5% of error logs sent (proposed, like the field names).

## Real-user monitoring

Real-user monitoring (RUM) measures what visitors experience in their browsers: a customer-facing alternative to Google Analytics, linked to A/B tests through variant exposure events (see [Matchers and variants](/next/matchers-and-variants)). It's planned as a follow-up after the first release; see the [Roadmap](/roadmap#roadmap-later--add-real-user-monitoring).

## Troubleshooting

| Symptom | What to check |
|---|---|
| No telemetry reaches Deco | Telemetry needs both `site` and `token` on `createCMS`, and an enabled [Telemetry entry](#telemetry-settings-are-content). Error logs are sampled and metrics are sent in batches, so expect a delay and only a share of errors. |
| Upstream calls missing | Only requests made through `createInstrumentedFetch` are measured; check that your client uses it (see [Upstream API clients](/next/upstream-clients)). |
