# Releases and deployment

Your block functions and your content ship together. Both live in your repository: the functions as TypeScript, the content as JSON files in `.deco/blocks` (see [Blocks in your repository](/next/blocks#blocks-in-your-repository)). Upgrading a block means changing its function, its content, or both, in commits; your normal deploy pipeline ships them. This page covers how a change reaches visitors, how each response stays consistent, and how to roll back.

| Step | What happens |
|---|---|
| Commit | A developer, an agent, or an editor in Studio changes a function, an entry, or both. Review them in one pull request like any other change. |
| Build | `prebuild` runs `deco schema && deco content`. `deco content` turns `.deco/blocks` into the content module, `.deco/blocks.gen.ts`, which the app imports and the bundler includes like any other module. |
| Deploy | Your host serves the new build. Every server of that build serves exactly one revision: the content of the commit it was built from. |

A **revision** identifies one exact content map: `deco content` computes it as a hash of the whole map, so two copies of the content are the same exactly when their revisions match (see [Snapshots and revisions](/next/internals#snapshots-and-revisions)). A revision never changes once it exists: change any entry and you get a new revision. That makes a revision a safe cache key everywhere.

<h2 id="publishing">Publishing is committing</h2>

There's no separate publish step. A developer or an agent edits the entry files in `.deco/blocks` and pushes; an editor saves in Studio, which writes the files in your checkout (see [Edit your local checkout](/next/content-protocol#edit-your-local-checkout)), and the change is committed like any other. Once it's on your production branch, your next deploy serves it. In development, editing a file hot-reloads, so you see a change before you commit it.

Because content and code share one history, a deploy and a content change are the same kind of event: a commit. That gives you, for free:

- **Review.** A content change is a diff in a pull request, next to the code it needs.
- **Branches.** A content change can wait on a branch, with its own preview deploy, until it's ready (see [Preview](/next/preview)).
- **Rollback.** Redeploy the previous build: its content and code roll back together, so they always fit. Reverting a single code commit doesn't revert content committed after it, so check that content first (see [Keep the schema compatible](/next/schema#keep-the-schema-compatible)).

A commit's content must only use block types and fields its code has; the rules, and a CI workflow that checks code changes against saved content before they merge, are in [Keep the schema compatible](/next/schema#keep-the-schema-compatible).

<Hosted to="/next/hosted-publishing" label="Publishing without a deploy">**Skip the deploy wait.** With the hosted Deco CMS, a commit to your production branch is served as a release within seconds, and running servers pick it up within about a minute, with no rebuild.</Hosted>

## One revision per response

Content can change while a server is running: in development, when you edit a file, or with a `content` loader that updates (see [Loaders](/next/api-reference#loaders)). Two reads a few milliseconds apart could then see different revisions; a header from one and a footer from the other make an inconsistent page. A client prevents that: its first call picks a revision, and every later `list` and `resolve` on it, including concurrent ones, uses the same one. So make one client per request.

Follow-up requests from the browser may land on a newer revision. If data must match the HTML, render it in the same response. (A way to read and pin the served revision is on the [Roadmap](/roadmap#roadmap-api--add-a-revision-handle).)

A revision only selects content; it isn't a secret and unlocks nothing. Drafts are branches; protect their preview deploys with your host's access controls.

## Deploying on Workers

Workers need nothing special. The content module is bundled into the Worker like any other import, and the CMS keeps it in memory for the life of the isolate. The [deployment checklist](/next/tanstack-start-descriptors#deployment-checklist) in the TanStack Start guide lists every step.
