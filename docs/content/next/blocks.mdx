# Blocks

A block is a function call written as JSON: it names one of your functions and lists the inputs to call it with. When your app resolves a block, Deco calls the function with those inputs and hands you back the result. Blocks are what editors and agents change instead of your code; [How it works](/next/how-it-works) has the big picture.

This page covers what a block looks like, how blocks nest and get reused, the block map that decides which functions they can call, and how saved blocks live in your repository.

## Functions as blocks

Here's the free-shipping bar at the top of a store, an ordinary React component:

```tsx title="src/promo-banner.tsx"
export interface PromoBannerProps {
  title: string;
  href: string;
}

export function PromoBanner({ title, href }: PromoBannerProps) {
  return <a href={href}>{title}</a>;
}
```

And here's a block that calls it. `"promo-banner"` is the name your site gives `PromoBanner`; [The block map](#the-block-map) shows where names come from.

```jsonc
// Stored as JSON
{
  "__resolveType": "promo-banner",
  "title": "Free shipping over $50",
  "href": "/summer"
}

// Means
PromoBanner({ title: "Free shipping over $50", href: "/summer" });
```

The function is code; the call is data. Changing the headline or the link touches no code, and the same works for anything your site needs: UI, product data, SEO, navigation, campaign settings.

What a block can contain:

- **`__resolveType`**, a string: the name of the function to call. It's a reserved key; the underscores keep it from clashing with your props.
- **Any JSON value as an argument**: strings, numbers, booleans, `null`, arrays and objects. Anything JSON can't hold, such as a function or a `Date`, can't be an argument.
- **Other blocks**, anywhere inside an argument. That's the next section.

## Composing blocks

A block inside an argument is a call inside a call. Here a product card gets its product from a second function, `catalogProduct`, which fetches it from your catalog:

```jsonc
// Stored as JSON
{
  "__resolveType": "product-card",
  "title": "Summer collection",
  "product": { "__resolveType": "catalog-product", "slug": "summer-shirt" }
}

// Means
productCard({
  title: "Summer collection",
  product: catalogProduct({ slug: "summer-shirt" }),
});
```

Resolving a block evaluates it from the inside out, like the TypeScript you'd write. `catalog-product` has plain arguments, so it runs first. Its result becomes the `product` argument of `product-card`, so `productCard` receives the resolved `Product`, never a pending call. If a function is `async`, its result is awaited first.

So type the prop as what the function receives, `product: Product`, not as a block. [Schema](/next/schema#from-types-to-forms) shows how [Studio](/next/how-it-works#studio) then offers the functions that return a `Product`, such as `catalogProduct`.

To resolve a block from your code, pass it to `client.resolve`. Get a client with `cms.forRelease()` (`cms` is set up in [The `deco content` command](#the-deco-content-command)), one per request ([why](/next/releases-and-deployment#one-revision-per-response)):

```tsx
import { cms } from "./cms";

const client = cms.forRelease();
const [card, error] = await client.resolve({
  "__resolveType": "product-card",
  "title": "Summer collection",
  "product": { "__resolveType": "catalog-product", "slug": "summer-shirt" },
});
// card = <ProductCard title="Summer collection" product={{ name: "Summer shirt", … }} />
```

`resolve` never throws: it returns `[value, null]`, or `[null, error]` if something failed. It accepts any JSON value, not only a block: blocks anywhere inside are resolved, and everything else comes back as it is. Pass an array of blocks and you get an array of results.

<Callout>**Reading without running.** `client.resolve(target, { run: false })` returns the JSON that would be called, with nothing run. It's most useful with saved blocks ([next section](#reusing-blocks)), which it writes in place, and handy for previews, tooling and debugging. Code that handles this saved JSON types it as `Block`, `{ __resolveType: string; …inputs }`; props never do. See [`client.resolve`](/next/api-reference#client-resolve-target-options).</Callout>

## Reusing blocks

In code, you'd give a call you use often a name. A **saved block** is a block with a name. Here's the card from the previous section, saved as `SummerCard`:

```jsonc
// Saved as SummerCard
{
  "__resolveType": "product-card",
  "title": "Summer collection",
  "product": { "__resolveType": "catalog-product", "slug": "summer-shirt" }
}
```

Resolve it by name. A string passed to `resolve` is always the name of a saved block:

```tsx
const [card, error] = await client.resolve("SummerCard");
```

Other blocks can use it too. `{ "__resolveType": "SummerCard" }` means whatever is saved under `SummerCard`, written in place, so a home page and a campaign page can show the same card, and changing the saved block changes both.

What's saved is the call, not its result, so a reference can override some of its arguments for one use:

```jsonc
// Saved as SummerSEO
{ "__resolveType": "seo", "title": "Sunny!", "description": "Light layers for long days." }

// A reference to it, anywhere in your content
{ "__resolveType": "SummerSEO", "title": "Summer sale" }

// Means
seo({ title: "Summer sale", description: "Light layers for long days." });
```

Overrides are shallow. The merge is `{ ...saved, ...arguments }`, so an override replaces a whole top-level property, and the saved block itself doesn't change.

### The block map

So far, names like `"product-card"` simply worked. They come from your **block map**: the object you pass to `createCMS` that decides which functions blocks can call. Each key is a **block type**, the name a block's `__resolveType` uses; each value is a function:

```ts title=".deco/blocks.ts"
import type { Blocks } from "@decocms/blocks";
import { catalogProduct } from "../src/catalog-product";
import { productCard } from "../src/product-card";
import { PromoBanner } from "../src/promo-banner";

export default {
  "catalog-product": catalogProduct,
  "product-card": productCard,
  "promo-banner": PromoBanner,
} satisfies Blocks;
```

The block map lives in `.deco/blocks.ts` (or `.deco/blocks.tsx`), next to your content, and imports your components from `../src/`. Content chooses the arguments; code chooses which functions exist. A block can only call what's in this map. For lazy loading and more, see [Block maps](/next/block-maps).

### Built-in blocks

Every website needs pages and redirects, so the framework adds these functions to your block map for you:

- **`page`** takes `name`, `path`, `seo` and `sections` (the page's blocks, in order), and returns the page with `seo` and every block in `sections` resolved. Its type is `interface Page extends Route { seo: Seo; sections: ReactNode[] }`. [Routes and redirects](/next/routes-and-redirects) shows how to find the page for a URL.
- **`redirect`** takes `from`, `to` and `permanent` (`true` for a 301, `false` for a 302), and returns them as saved. [Routing](/next/routing) turns redirects into responses.
- **`telemetry`** holds settings read by the [hosted Deco CMS](/next/hosted-telemetry); it does nothing otherwise.

**Changing a built-in.** Declare `page` in your block map to replace it, for example to wrap every page in your layout. To only change the fields editors see, see [Override a built-in](/next/schema#override-a-built-in).

### The lookup rule

Every `__resolveType` is looked up in one registry, `{ ...savedBlocks, ...builtIns, ...blocks }`, where later keys win. A function is called with its arguments, after they're resolved. A saved block is replaced by its contents, merged with your overrides, and that result is looked up the same way. Any other name fails with `UNKNOWN_BLOCK`. Give saved blocks and functions different names; if they clash, the function wins and you'll get a warning. What happens when a block fails, or when saved blocks refer to each other in a loop, is in [The rule in full](/next/how-resolution-works#the-rule-in-full).

## Blocks in your repository

Everything Deco lives in one folder, `.deco/`, in your app root (the folder with your app's `package.json`). Saved blocks are files there: one JSON file per saved block in `.deco/content`, and the file name without `.json` is its name.

```text
.deco/
├── blocks.ts          your block map
├── content/           your saved blocks
│   ├── HomePage.json
│   ├── PromoBanner.json
│   └── SummerCard.json
├── schema.gen.json    generated by deco schema, committed
└── blocks.gen.ts      generated by deco content, gitignored
```

Don't edit `schema.gen.json` or `blocks.gen.ts`; `blocks.ts` and `content/` are yours. The `.gen.` in a name marks a generated file. Despite its name, `blocks.gen.ts` is built from `content/`, not from `blocks.ts`: it's your saved blocks as a module. The [CLI](/next/cli) page has a table of which file is which.

Edit saved blocks as files, with an AI agent, or in Studio (see [Edit on your machine](/next/content-protocol#edit-on-your-machine)). Because they're files in Git, every edit is a commit you can review and revert, and publishing is pushing to your production branch: your next deploy serves it (see [Releases and deployment](/next/releases-and-deployment#publishing)).

### The `deco content` command

The `deco` CLI, which comes with `@decocms/blocks`, turns `.deco/content` into a module your app imports, so the SDK never touches the filesystem and runs anywhere: Node, Cloudflare Workers, Deno, Bun or a browser.

```bash
npx @decocms/blocks content
```

It writes `.deco/blocks.gen.ts`: one JSON import per file, exported together, so your bundler packs your content into the build like any other module:

```ts title=".deco/blocks.gen.ts (excerpt)"
// Generated by deco content; don't edit.
import HomePage from "./content/HomePage.json" with { type: "json" };
import PromoBanner from "./content/PromoBanner.json" with { type: "json" };
// … one import per file, exported together
```

Pass it to `createCMS`, next to your block map:

```ts title="cms.ts"
import { createCMS } from "@decocms/blocks";
import blocks from "./.deco/blocks";
import content from "./.deco/blocks.gen";

export const cms = createCMS({ blocks, content });
```

The generated file belongs in `.gitignore`, like TanStack Router's `routeTree.gen.ts`. Run it before your dev server and your build, after `deco schema` (see [Run it before dev and build](/next/cli#run-it-before-dev-and-build)).

Editing a file reloads through your framework's hot module replacement (HMR), with no rerun. Adding or removing a file needs the command again: rerun `npx @decocms/blocks content`, or leave `npx @decocms/blocks content --watch` running beside your dev server.

It reads only the JSON files in `.deco/content`, never your block map. Like every command, it finds `.deco/` by walking up from the current folder, or takes `--root`. Every option is in the [CLI reference](/next/cli#deco-schema-and-deco-content).
