# Routing

The CMS doesn't route. It lists and resolves. Routing is three steps in your request handler: list the types you want at URLs, hand them to `matchRoute`, resolve the winner. Do all three with one client, so they see the same content even if it changes mid-request (see [One revision per response](/next/releases-and-deployment#one-revision-per-response)).

## The example used here and in the guides

This page and the framework guides share these files: the model in `src/model.ts`, the post type in `src/post.ts` (from [Your own routable types](/next/routes-and-redirects)), and two content entries, stored as files in `.deco/blocks`, which `deco content` turns into the content module (see [Blocks in your repository](/next/blocks#blocks-in-your-repository)). The page is a product page with two blocks: a `promo-banner` (a free-shipping bar) and a `product-hero`. Each guide's block map (`src/blocks.tsx` or `src/blocks.ts`) registers `seo`, `promo-banner`, `product-hero` and `post: (props: Post) => props` (see [Your own routable types](/next/routes-and-redirects#your-own-routable-types)). `page` and `redirect` are [built-in blocks](/next/blocks#built-in-blocks), so the block maps don't register them.

In `src/model.ts`, `BlockDescriptor` is what a block returns in data mode (see [Rendering](/next/rendering)), `StoredPage` is a page exactly as saved, before any of its blocks run, and `ResolvedPage<T>` is what the built-in `page` block returns, with `T` being what your blocks return.

```ts title="src/model.ts"
import type { Block, Route, Seo } from "@decocms/blocks";

export interface PromoBannerProps { title: string; href: string }
export interface ProductHeroProps { name: string; price: number; currency: string; image: string }

// What a block returns in data mode: a component name and its props.
export type BlockDescriptor =
  | { component: "promo-banner"; props: PromoBannerProps }
  | { component: "product-hero"; props: ProductHeroProps };

// A saved page, as client.list returns it by default (nothing run): seo and sections are still JSON.
export interface StoredPage extends Route {
  seo: Seo | Block;
  sections: Block[] | Block;   // a list of blocks, or one variant block that picks a whole list
}

// What client.resolve returns for a page: seo and every block in sections resolved.
export interface ResolvedPage<T> extends Route { seo: Seo; sections: T[] }
```

`Seo` is the built-in page's SEO type, exported from `@decocms/blocks`. `Block` is the type of a block as stored, `{ "__resolveType": "…", …inputs }`. `StoredPage` needs it because `client.list` returns pages before anything runs, which lets the optional [streaming step](/next/nextjs#7-stream-each-block-optional) resolve each block separately. Its `sections` is usually a list, but an editor can wrap the whole list in a [variant](/next/matchers-and-variants), which makes it one block. Block inputs never use `Block` ([they're resolved values](/next/schema#from-types-to-forms)): the JSX guides keep the built-in `Page`, and the [descriptor guide](/next/tanstack-start-descriptors) overrides it with `ResolvedPage<BlockDescriptor>`.

```json title=".deco/blocks/ShirtPage.json"

  "seo": {
    "__resolveType": "seo",
    "title": "Summer shirt | Deco example",
    "description": "Light cotton shirt for hot days."
  },
  "sections": [
    { "__resolveType": "promo-banner", "title": "Free shipping on orders over $50", "href": "/shipping" },
    {
      "__resolveType": "product-hero",

      "currency": "USD",

    }

}
```

```ts
{
  name: "Summer shirt",
  path: "/:slug/p",

// Each guide's block map decides what these return: JSX in Next.js and TanStack RSC, a descriptor in data mode
```

```json title=".deco/blocks/LegacyProduct.json"
{
  "__resolveType": "redirect",
  "from": "/old-products/:slug",
  "to": "/:slug/p",
  "permanent": true

```

The redirect sends `/old-products/summer` to `/summer/p`. The hero uses literal product values to keep the example small. On a real store, the hero's block function fetches the product for the slug through an [upstream client](/next/upstream-clients#write-a-client), reading `match.params` from your app's request state (see [Block maps](/next/block-maps)).

## Route a request

With those files in place, this is the whole request handler:

```ts
import { matchRoute, type Redirect } from "@decocms/blocks";
import type { ReactNode } from "react";
import type { ResolvedPage, StoredPage } from "./model";
import type { Post } from "./post";
// cms comes from cms.ts (see Quickstart); request is the incoming Request; render/renderPost are your own view code
// error handling omitted: check the second tuple element in real code, and catch matchRoute's throw (see below)

const client = cms.forRelease();
const [pages]     = await client.list<StoredPage>("page");   // as saved: seo and sections are still blocks
const [posts]     = await client.list<Post>("post");
const [redirects] = await client.list<Redirect>("redirect");

const match = matchRoute(request, { routes: [...pages, ...posts], redirects });

switch (match.kind) {
  case "not-found":
    return new Response("Not found", { status: 404 });
  case "redirect":
    return Response.redirect(new URL(match.location, request.url), match.status);
  case "match":
    switch (match.entry.__resolveType) {
      case "page": {
        const [page] = await client.resolve<ResolvedPage<ReactNode>>(match.entry);   // built-in page: seo and sections resolved
        return render(page.seo, page.sections);
        // To stream blocks one by one instead, resolve match.entry.seo and each block in sections separately.
      }
      case "post":
        return renderPost(match.entry);                                        // already the saved post
    }
}
```

`match.entry` is already the saved post. Call `client.resolve(match.entry)` only if a post contains blocks.

Mount this handler as your app's catch-all route, the one that runs when no other route matches.

| `kind` | Fields |
|---|---|
| `"match"` | `entry` (the stored route you passed in) and `params` from the path template. |
| `"redirect"` | `location` with parameters filled in, and `status` (`301` or `302`). |
| `"not-found"` | None |

<Callout>**`matchRoute` is a helper, not a requirement.** The CMS has no idea what a URL is. If your framework already routes, or you'd rather open a page by name (`client.resolve("SummerPage")` returns it ready to render) or find it by a field of your own, skip it. It exists because "an editor typed a path into [Studio](/next/how-it-works#studio) and that page is now live" is the common case, and getting precedence and parameters right by hand is tedious.</Callout>

Which types route is your decision, per handler: a blog lists `post`, a docs site lists `doc`. `match.params` holds the URL parameters; hand them to your code however your app shares request state. The CMS never injects them into blocks.

For example, with Node's `AsyncLocalStorage`: `export const routeParams = new AsyncLocalStorage<Record<string, string>>()`. Wrap rendering in `routeParams.run(match.params, () => render(…))`, and a block reads `routeParams.getStore()?.slug`. The [Block maps](/next/block-maps) page covers request-scoped state in more detail.

Matching is a lookup, not a scan: entries are compiled into a segment trie (a tree keyed by path segment), so a lookup costs the URL's depth, not the number of routes. The trie is cached per `routes` array object, so passing the same array again skips the build. The handler above builds a new array per request, which rebuilds the trie each time; that's one pass over the paths, fine for most sites. Reusing one array per revision needs the client to expose its revision, which is on the [Roadmap](/roadmap#roadmap-api--add-a-revision-handle). The algorithm is described [under the hood](/next/router-internals).

## Path templates and match order

A route's `path` and a redirect's `from` accept literal segments and named parameters. A route at `/:slug/p` matches `/summer/p` with `params.slug = "summer"`. Redirects are checked before routes, so a redirect overrides a route at the same path. Within each group, exact paths win over templates. Two entries with the same path, or two templates that can match the same URL, make `matchRoute` throw. `deco schema` reports the same conflict, so run it in CI on every commit, content-only commits included. Content merged without that check can still make `matchRoute` throw at request time, so catch the error and return a 500 rather than crash (removing the throw is on the [Roadmap](/roadmap#roadmap-api--add-a-splat-to-matchroute-and-stop-request-time-throws)). Serve framework endpoints, API routes and static assets from their own routes, so they never reach this catch-all.

## Linking and listing

Because the URL is a field, linking to an entry is reading it, and listing a routable type gives you an index for free:

```ts
const [posts] = await client.list<Post>("post", { sort: (a, b) => b.date.localeCompare(a.date) });
for (const post of posts) link(post.path, post.name);          // "/blog/hello-world", "Hello, world"
// link() stands in for your framework's <Link> or an <a href>

const match = matchRoute("/blog/hello-world", { routes: posts });
// { kind: "match", entry: { __resolveType: "post", name: "Hello, world", path: "/blog/hello-world", … }, params: {} }
```
