# Blocks

Most of what changes on a website isn't the code. It's the values the code is given: a headline, a banner image, the share of visitors who see the new checkout. Deco is built on that idea: developers write the functions, and the people who run the site decide what goes into them.

Blocks are how they make those decisions. A block is a small piece of JSON that names one of your functions and lists the inputs to call it with. Editors change the inputs in Studio, and agents edit the file directly. When your app resolves the block, Deco calls the function with whatever is saved and gives you back the result. This page shows what a block looks like, how blocks fit inside each other, and exactly how they turn into values.

## Functions as blocks

A block is a function call written as JSON. `__resolveType` names the function, and the other properties are its arguments.

Here's the free-shipping bar at the top of a store, an ordinary React component:

```tsx title="promo-banner.tsx"
export interface PromoBannerProps {
  title: string;
  href: string;
}

export function PromoBanner({ title, href }: PromoBannerProps) {
  return <a href={href}>{title}</a>;
}
```

And here's a block that calls it. `"promo-banner"` is the name your site gives `PromoBanner`; [Reusing blocks](#reusing-blocks) shows where names come from.

```jsonc
// Stored as JSON
{
  "__resolveType": "promo-banner",
  "title": "Free shipping over $50",
  "href": "/summer"
}

// Means
PromoBanner({ title: "Free shipping over $50", href: "/summer" });
```

The function is code, and only developers change it. The call is plain JSON, so anyone can change it: editors through a form in Studio, and AI agents by editing the JSON directly. Changing the headline or the link touches no code. Use the same model for anything your site needs: UI, product data, SEO, navigation, campaign settings.

What a block can contain:

- **`__resolveType`**, a string: the name of the function to call. It's a reserved key; the underscores keep it from clashing with your props.
- **Any JSON value as an argument**: strings, numbers, booleans, `null`, arrays and objects. Anything JSON can't hold, such as a function or a `Date`, can't be an argument.
- **Other blocks**, anywhere inside an argument. That's the next section.

## Composing blocks

A block inside an argument is a call inside a call. Here a product card gets its product from a second function, `catalogProduct`, which fetches it from your catalog:

```jsonc
// Stored as JSON
{
  "__resolveType": "product-card",
  "title": "Summer collection",
  "product": { "__resolveType": "catalog-product", "slug": "summer-shirt" }
}

// Means
productCard({
  title: "Summer collection",
  product: catalogProduct({ slug: "summer-shirt" }),
});
```

Resolving a block evaluates it from the inside out, like the TypeScript you'd write. `catalog-product` has plain arguments, so it runs first. Its result becomes the `product` argument of `product-card`, so `productCard` receives a product, never a pending call. If a function is `async`, its result is awaited first.

To resolve a block from your code, pass it to `client.resolve`. `cms` is created once with `createCMS` (see [The `deco content` command](#the-deco-content-command)). `cms.forRelease()` gives you a client that reads your published content; create one per request so a response sees one consistent version:

```tsx
import { cms } from "./cms";

const client = cms.forRelease();
const [card, error] = await client.resolve({
  "__resolveType": "product-card",
  "title": "Summer collection",
  "product": { "__resolveType": "catalog-product", "slug": "summer-shirt" },
});
// card = <ProductCard title="Summer collection" product={{ name: "Summer shirt", … }} />
```

`resolve` never throws: it returns `[value, null]`, or `[null, error]` if something failed. It accepts any JSON value, not only a block: blocks anywhere inside are resolved, and everything else comes back as it is. Pass an array of blocks and you get an array of results.

<Callout>**Reading without running.** `client.resolve(target, { run: false })` returns the JSON that would be called, with nothing run. It's most useful with saved blocks ([next section](#reusing-blocks)), which it writes in place, and handy for previews, tooling and debugging. See [`client.resolve`](/next/standalone#client-resolve-target-options).</Callout>

## Reusing blocks

In code, you'd give a call you use often a name. A **saved block** is a block with a name (the rest of the docs also call it a saved entry). Here's the card from the previous section, saved as `SummerCard`:

```jsonc
// Saved as SummerCard
{
  "__resolveType": "product-card",
  "title": "Summer collection",
  "product": { "__resolveType": "catalog-product", "slug": "summer-shirt" }
}
```

Resolve it by name. A string passed to `resolve` is always the name of a saved block:

```tsx
const [card, error] = await client.resolve("SummerCard");
```

Other blocks can use it too. `{ "__resolveType": "SummerCard" }` means whatever is saved under `SummerCard`, written in place, so a home page and a campaign page can show the same card, and changing the saved block changes both.

What's saved is the call, not its result, so a reference can override some of its arguments for one use:

```jsonc
// Saved as SummerSEO
{ "__resolveType": "seo", "title": "Sunny!", "description": "Light layers for long days." }

// A reference to it, anywhere in your content
{ "__resolveType": "SummerSEO", "title": "Summer sale" }

// Means
seo({ title: "Summer sale", description: "Light layers for long days." });
```

Overrides are shallow. The merge is `{ ...saved, ...arguments }`, so an override replaces a whole top-level property, and the saved block itself doesn't change.

### The block map

So far, names like `"product-card"` simply worked. They come from your **block map**: the object you pass to `createCMS` that decides which functions blocks can call. Each key is a name, each value a function:

```ts title="blocks.ts"
import type { Blocks } from "@decocms/blocks";
import { catalogProduct } from "./catalog-product";
import { productCard } from "./product-card";
import { PromoBanner } from "./promo-banner";

export default {
  "catalog-product": catalogProduct,
  "product-card": productCard,
  "promo-banner": PromoBanner,
} satisfies Blocks;
```

Content chooses the arguments; code chooses which functions exist. A block can only call what's in this map. For lazy loading and more, see [Block maps](/next/manifest).

### Built-in blocks

Every website needs pages and redirects, so the framework adds these functions to your block map for you:

- **`page`** takes `name`, `path`, `seo` and `sections` (the page's blocks, in order), and returns the page with `seo` and every block in `sections` resolved. [Routes and redirects](/next/content-types) shows how to find the page for a URL.
- **`redirect`** takes `from`, `to` and `permanent` (`true` for a 301, `false` for a 302), and returns them as saved. [Routing](/next/routing) turns redirects into responses.
- **`telemetry`** holds settings read by the [hosted Deco CMS](/next/hosted-telemetry); it does nothing otherwise.

**Changing a built-in.** Declare `page` in your block map to replace it, for example to wrap every page in your layout. To change the fields editors see, see [Schema generation](/next/schema#content-that-is-only-data).

### The lookup rule

Every `__resolveType` is looked up in one registry, `{ ...savedBlocks, ...builtIns, ...blocks }`, where later keys win. A function is called with its arguments, after they're resolved. A saved block is replaced by its contents, merged with your overrides, and that result is looked up the same way. Any other name fails with `UNKNOWN_BLOCK`. Give saved blocks and functions different names; if they clash, the function wins and you'll get a warning. What happens when a block fails, or when saved blocks refer to each other in a loop, is in [The rule in full](/next/walkthrough#the-rule-in-full).

## Blocks in your repository

Saved blocks are files in your repository: one JSON file per saved block in `.deco/blocks`, and the file name without `.json` is its name.

```text
.deco/blocks/
├── HomePage.json
├── PromoBanner.json
└── SummerCard.json
```

Developers edit them like any other file, AI agents edit them with the file tools they already use, and editors edit them in Studio, which shows each one as a form (see [Edit your local checkout](/next/studio-protocol#edit-your-local-checkout)). Because they're files in Git, you get what you already have for code: history, review in pull requests, branches, and rollback by reverting a commit.

Publishing is committing and pushing. There's no separate publish step: push the change to your production branch (usually `main`), and your next deploy serves it, like any other change (see [Releases and deployment](/next/releases#publishing)).

<Hosted to="/next/hosted-publishing" label="Publishing without a deploy">**Go live without a deploy.** With the hosted Deco CMS, a published commit goes live in about a minute, without a rebuild or deploy.</Hosted>

### The `deco content` command

The CLI turns `.deco/blocks` into a module your app imports, so the SDK never touches the filesystem and runs anywhere: Node, Cloudflare Workers, Deno, Bun or a browser.

```bash
npx deco content
```

It writes `.deco/blocks.gen.ts`: one JSON import per file, exported together, so your bundler packs your content into the build like any other module:

```ts title=".deco/blocks.gen.ts (excerpt)"
// Generated by deco content; don't edit.
import HomePage from "./blocks/HomePage.json" with { type: "json" };
import PromoBanner from "./blocks/PromoBanner.json" with { type: "json" };
// … one import per file, exported together
```

Pass it to `createCMS`, next to your block map:

```ts title="cms.ts"
import { createCMS } from "@decocms/blocks";
import content from "./.deco/blocks.gen";
import blocks from "./blocks";

export const cms = createCMS({ blocks, content });
```

The generated file belongs in `.gitignore`, like TanStack Router's `routeTree.gen.ts`. Run `deco content` before your dev server and your build:

```json title="package.json"
{
  "scripts": {
    "predev": "deco content",
    "prebuild": "deco content"
  }
}
```

Editing a file reloads through your framework's hot module replacement (HMR), with no rerun. Adding or removing a file needs `deco content` again, or leave `deco content --watch` running beside your dev server. Every option is in the [CLI reference](/next/schema#the-cli-commands).
