# Schema

When an editor opens a block in [Studio](/next/how-it-works#studio), they see a form: a text box for the headline, an image picker, a calendar for the end date, a rich-text editor for the description. You never build that form. It comes from the types of your function's inputs, through the schema, and it only accepts values your function can take.

This page shows how types become fields, how to pick widgets, how to describe content that has no function, and how to change types without breaking saved content.

## From types to forms

`deco schema` reads the TypeScript types of your [block map](/next/blocks#the-block-map) and writes `.deco/schema.json` (see [CLI](/next/cli)):

```bash
npx @decocms/blocks schema
```

Pass `--entry` if the CLI can't find your block map ([where it looks](/next/cli)). Commit `.deco/schema.json` with your code.

For each block, the compiler reads the type of the function's first parameter. Each property becomes a field:

| TypeScript type | Field in Studio |
|---|---|
| `string` | A text box |
| `number` | A number field |
| `boolean` | A toggle |
| A union of string literals (`"sm" \| "md" \| "lg"`), or an `enum` | A select |
| An array | A list editors can add to and reorder |
| An object, such as `Product` or `Seo` | A group of fields, or a block (see below) |
| An optional property (`endsOn?: string`) | An optional field |
| `ReactNode` / `ReactNode[]` | A choice of components: one, or a list (see [Interchangeable blocks](#interchangeable-blocks)) |

**Think in functions.** A field's type is the value your function *receives*, already resolved. Studio fills the field with a plain value of that type or, for objects and JSX, with a block whose function returns that type. The return type is awaited, so a function that returns `T` and one that returns `Promise<T>` both fit:

```ts
interface ProductCardProps {
  title: string;
  product: Product;   // Studio offers any block whose function returns a Product, e.g. catalogProduct
}
```

`deco schema` reads each block function's return type to know which functions fit which fields:

- **Objects** (`product: Product`, `seo: Seo`) take a plain value, or a block whose function returns that type, such as `catalogProduct` or `seo`.
- **`ReactNode` and `ReactNode[]`** (`sections: ReactNode[]`) take functions that return JSX, sync or async (Server Components): one, or as many as you like. Only JSX counts. TypeScript's `ReactNode` also includes strings, numbers and booleans, but functions that return those aren't offered here, so a matcher never shows up as a section.
- **Simple types** (`string`, `number`, `boolean`, a union of literals) get a plain input only. A function that returns a `string` isn't offered for `title: string`, and matchers aren't offered for `permanent: boolean`.

Two things work on top of this. Any field can be a [variant](/next/matchers-and-variants): `multivariate<T>` is generic, so `T` becomes the field's type, a `string` for a title or `ReactNode[]` for a whole `sections` list. It returns `undefined` when no rule matches, so keep an `always()` variant last. And a variant's `rule` is the one `boolean` field that offers blocks: any function that returns a `boolean` (a [matcher](/next/matchers-and-variants#write-your-own-matcher)).

Never type a prop as a block. `Block` is only the shape of saved JSON (see [Composing blocks](/next/blocks#composing-blocks)).

<Callout>**Status. `deco schema` doesn't match fields to functions by return type yet.** This section describes how it will work. See the [Roadmap](/roadmap#roadmap-cli--define-the-loader-picker-rule).</Callout>

A date, an image and rich text are all `string`s to TypeScript; a JSDoc `@format` tag tells Studio which input to show (see [Widgets](#widgets)).
### Interchangeable blocks

Any block whose function returns the field's type can fill it, so editors can swap one for another without touching code. (This is polymorphism: Studio matches functions by their return type, the way TypeScript does.) For such a field, Studio offers two kinds of choices:

- **A new block**: pick one of the functions that fit, and fill in its form right there.
- **A saved block**: Studio reads the saved blocks with `blocks.list` and shows the ones whose function returns the field's type. Picking one stores a reference, `{ "__resolveType": "SummerCard" }`, so editing `SummerCard` updates every place that uses it (see [Reusing blocks](/next/blocks#reusing-blocks)).

## Widgets

Each type gets a default widget, such as a text box for a `string`. JSDoc tags on a field change the label, add help text and limits, or swap in a richer widget: a date picker, an image uploader, a color picker or a rich-text editor.

| Tag | Effect in the editor | Example |
|---|---|---|
| `@title` | The field's label (the default is the property name) | `@title Headline` |
| `@description` | Help text under the field | `@description Shown above the fold` |
| `@default` | The value a new block starts with, parsed as JSON when it can be | `@default 10` |
| `@minimum` / `@maximum` | The allowed range of a number | `@maximum 100` |
| `@minLength` / `@maxLength` | The allowed length of a string | `@maxLength 60` |
| `@format` | A specialized input for a string, such as `date`, `date-time`, `rich-text`, `textarea`, `color` or `image-uri`. `password` marks a credential, which Studio shows read-only in this version: keep credentials in environment variables. | `@format rich-text` |
| `@options` | A select over a `string` field, from a list of allowed values, without narrowing the TypeScript type | `@options ["sm", "md", "lg"]` |
| `@ignore` | Leaves the field out of the form | `@ignore` |

Put each tag on its own line. This type:

```ts
export interface PromoBannerProps {
  /**
   * @title Headline
   * @maxLength 60
   */
  title: string;
  /**
   * @title Image
   * @format image-uri
   */
  image: string;
  /** @title Link */
  href: string;
  /**
   * @title Ends on
   * @format date
   */
  endsOn?: string;
}
```

becomes a form with a *Headline* text box limited to 60 characters, an *Image* picker, a *Link* field and an optional *Ends on* date picker.

**Options are written into the schema.** A union of string literals, a TypeScript `enum` and an `@options` list all become an `enum` in the schema, so Studio shows a select without asking your site for the options. A picker whose options come from a function falls back to a text field in this version (see [Features that need your site's code](/next/content-protocol#features-that-need-your-site-s-code)).

## Content without a function

A blog post or a navigation menu has a shape but no function. Your app reads it, by type with `client.list("post")` or by URL with `matchRoute` (see [Routing](/next/routing)), and resolves the blocks *inside* it. It still needs a schema so Studio can create it, so declare it in a type-level map named `Content`, next to the block map. You declare only your own types, like `post: Post`; pages and redirects are built in (see below).

```ts title="blocks.ts"
import type { Blocks } from "@decocms/blocks";
import type { Post } from "./post";
import seo from "./seo";
import hero from "./hero";

export default { seo, hero } satisfies Blocks;          // code: a schema per function parameter

export type Content = {                                  // data: a schema per type
  post: Post;                                            // page and redirect are built-in blocks; no need to declare them
};
```

`deco schema` reads both exports. Keys of the default export get a schema from each function's parameter type; keys of `Content` get one from the type itself. The CMS never sees `Content`, so a type declared only there runs nothing: resolving a saved `post` block by name fails with `UNKNOWN_BLOCK`.

**Built-ins: override or opt out.** The schema always includes the [built-in blocks](/next/blocks#built-in-blocks), `page`, `redirect` and `telemetry`. `Page`, `Seo`, `Redirect` and `Route` are exported from `@decocms/blocks`. Declaring a built-in key in `Content` replaces its form. Extend the exported type to add fields:

```ts
import type { Page } from "@decocms/blocks";

interface StorePage extends Page { theme: "light" | "dark" }

export type Content = { page: StorePage; post: Post };
```

An app that isn't a website opts out with `page: never` or `redirect: never`, which removes them from the schema. The CMS never reads `Content`, so the built-in blocks stay defined at runtime either way.

**Names must not clash.** Block types and `Content` types share one list of names, so a key can't be in both, except a built-in key. `deco schema` also checks your saved content: it fails if a saved block in `.deco/blocks` has the name of a block type, or if an alias (a second name for a block type, used when you rename one; see [Renaming and migrating](/next/renames-and-migrations)) matches either. It doesn't yet check each saved block's values against the schema; that's part of the first release (see the [Roadmap](/roadmap#roadmap-cli--add-validation-commands-to-the-cli)).

## Change types safely

Content and code live in one repository but change independently: an editor's content branch and a developer's code branch can merge in either order. Nothing at runtime checks that they fit, because the CMS doesn't compare schemas. So keep them compatible before anything merges, in two directions:

- **New code still renders all existing content.** A code change must not break content that's already saved. A planned `--check` flag for `deco schema`, which compares your schema with the one on `main`, will enforce this in CI (see [Run it in CI](#run-it-in-ci)).
- **Content only uses types its commit's code has.** Content and code ship in the same build, so each commit's content must use only block types and fields that the same commit's code defines. Studio reads the schema next to the content it edits (your working tree, with [`deco serve`](/next/cli#deco-serve)), so it only offers what that code has. A saved block written by hand or by an agent that uses a type the code lacks fails that block with `UNKNOWN_BLOCK` (see [Errors](/next/api-reference#errors)); merge the code that adds a type before, or with, the content that uses it. Rolling code back by reverting a commit has the same catch: content that already uses the newer types or fields fails on the older code until you revert that content too. Redeploying a previous build doesn't, because it ships that build's own content. No tool checks this yet; the content validation commands on the [Roadmap](/roadmap#roadmap-cli--add-validation-commands-to-the-cli) will.

What counts as breaking:

| Change | Breaking? |
|---|---|
| Removing a block type (a function in the block map) or a `Content` type | Yes. The check compares schemas only, so any removal counts, whether or not saved content uses the type. Remove a type in a later change, once no content uses it. To rename a block type, keep the old name as an alias (see [Rename a type with an alias](/next/renames-and-migrations#rename-a-type-with-an-alias)); the old name stays in the schema, so the check passes. Don't rename a `Content` type this way yet: the check would pass, but Content aliases don't work at runtime (see the [Roadmap](/roadmap#roadmap-cli--emit-a-runtime-alias-table)). |
| Removing or renaming a field | Yes. Fields have no aliases, so rename in steps: add the new name as an optional field, move the content over, then remove the old field once no content uses it. |
| Adding a required field, or making an optional field required | Yes: existing entries don't have it |
| Narrowing a field's type: a `string` becoming a union of allowed values, a union losing a member, a tighter limit (a lower `@maximum` or `@maxLength`, or a higher `@minimum` or `@minLength`) | Yes: saved values may fall outside it |
| Adding a block type, a `Content` type or a built-in type | No |
| Adding an optional field | No |
| Widening a field's type: a union gaining a member, a required field becoming optional | No |

<Hosted to="/next/hosted-publishing#keep-running-code-compatible" label="Keep running code compatible">**Publishing without a deploy adds a direction.** With the hosted Deco CMS, content goes live on code that's already running, so that code must also render content published after it shipped.</Hosted>

### Run it in CI

Optional, but recommended. This GitHub Actions workflow runs on every pull request, regenerates the schema and fails if `.deco/schema.json` changed or was never committed:

```yaml title=".github/workflows/schema.yml"
name: Schema
on: pull_request

jobs:
  schema:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - name: The committed schema matches the code
        run: |
          npx @decocms/blocks schema
          if [ -n "$(git status --porcelain -- .deco/schema.json)" ]; then
            git diff -- .deco/schema.json
            echo ".deco/schema.json is missing or out of date: run npx @decocms/blocks schema and commit it."
            exit 1
          fi
```

`npm ci` already installed `@decocms/blocks`, so `npx` runs the CLI at the version in your lockfile. If you use `--root`, pass it to the schema command too and replace `.deco/schema.json` with `<dir>/.deco/schema.json`. Make the job a required check in your branch protection rules, so a failing pull request can't merge.

<Callout>**Status. The compatibility check, `deco schema --check <base>`, isn't built yet; it ships with the first release.** It will generate the schema from your code, compare it with `<base>`, an earlier `.deco/schema.json` such as the one on `main`, list every breaking change from the table above and exit with a non-zero code if it finds one, writing nothing. Once it's out, add a step that runs `git show "origin/$BASE_REF:.deco/schema.json" > base-schema.json`, then `deco schema --check base-schema.json`. Until then, review schema diffs against the table by hand. See the [Roadmap](/roadmap#roadmap-cli--add-deco-schema-check-a-compatibility-check).</Callout>

Content-only changes, from Studio, an agent or by hand, never change the schema, so `--check` always passes them, and `deco schema` still checks the content model (saved block names, aliases and route collisions) in the same pull request.
