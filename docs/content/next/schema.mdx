# Schema generation

Studio builds its editor from a JSON Schema, and the CLI writes that schema from your TypeScript. Studio only reads the schema; it never edits it (see [Studio and the content protocol](/next/studio-protocol)). The CLI reads the file that exports your block map, the `blocks.ts` from the [quickstart](/next/quickstart), and writes `.deco/schema.json`. It looks for that file as `blocks.ts` or `blocks.tsx`, in the project root or in `src/`. If your block map lives somewhere else, pass its path with `--entry`, for example `deco schema --entry app/cms/blocks.ts`:

```bash
npx deco schema
```

For each block type in the map, the CLI reads the type of the function's first parameter and turns it into a form definition. Commit `.deco/schema.json` with your code, and run the command in CI so the schema never drifts from your types (see [Keep the schema compatible](#keep-the-schema-compatible)). The commands and flags are in the [CLI reference](#the-cli-commands) at the end of this page.

The CLI also checks your content model: it fails if a saved entry in `.deco/blocks` has the name of a block type, or if an alias (a second name for a block type, used when you rename one; see [Renaming and migrating](/next/adoption)) collides with either. It doesn't yet check each entry's values against the schema; that command is part of the first release (see the [Roadmap](/roadmap#roadmap-cli--add-validation-commands-to-the-cli)).

## Annotate fields with JSDoc

The TypeScript type decides what kind of field each input gets: a `string` is a text box, a `number` a number field, a union of string literals a select, an array a list editors can add to and reorder. JSDoc tags on a field refine the form:

| Tag | Effect in the editor | Example |
|---|---|---|
| `@title` | The field's label (the default is the property name) | `@title Headline` |
| `@description` | Help text under the field | `@description Shown above the fold` |
| `@default` | The value a new block starts with, parsed as JSON when it can be | `@default 10` |
| `@minimum` / `@maximum` | The allowed range of a number | `@maximum 100` |
| `@minLength` / `@maxLength` | The allowed length of a string | `@maxLength 60` |
| `@format` | A specialized input for a string, such as `date`, `date-time`, `rich-text`, `textarea`, `color` or `image-uri`. `password` marks a credential, which Studio shows read-only in this version: keep credentials in environment variables. | `@format rich-text` |
| `@options` | A select over a `string` field, from a list of allowed values, without narrowing the TypeScript type | `@options ["sm", "md", "lg"]` |
| `@ignore` | Leaves the field out of the form | `@ignore` |

Put each tag on its own line. This type:

```ts
export interface PromoBannerProps {
  /**
   * @title Headline
   * @maxLength 60
   */
  title: string;
  /**
   * @title Image
   * @format image-uri
   */
  image: string;
  /** @title Link */
  href: string;
  /**
   * @title Ends on
   * @format date
   */
  endsOn?: string;
}
```

becomes a form with a *Headline* text box limited to 60 characters, an *Image* picker, a *Link* field and an optional *Ends on* date picker.

**Options are written into the schema.** A union of string literals, a TypeScript `enum` and an `@options` list all become an `enum` in the schema, so Studio shows a select without asking your site for the options. Studio never runs your code, so a picker whose options would come from a function falls back to a text field in this version.

## Content that is only data

A blog post or a navigation menu has a shape but no function. Your app reads it, by type with `client.list("post")` or by URL with `matchRoute` (see [Routing](/next/routing)), and resolves the blocks *inside* it. It still needs a schema so Studio can create it, so declare it for the CLI in a type-level map next to the block map. You declare only your own types, like `post: Post`; pages and redirects are built in (see below).

```ts title="blocks.ts"
import type { Blocks } from "@decocms/blocks";
import type { Post } from "./post";
import seo from "./seo";
import hero from "./hero";

export default { seo, hero } satisfies Blocks;          // code: a schema per function parameter

export type Content = {                                  // data: a schema per type
  post: Post;                                            // page and redirect are built-in blocks; no need to declare them
};
```

The CLI reads both exports. Keys of the default export get a schema from each function's parameter type; keys of `Content` get one from the type itself. The two share one namespace, and a key in both is an error, except a built-in key (below). The CMS never sees `Content`, so a type declared only there runs nothing: resolving a `post` entry by name fails with `UNKNOWN_BLOCK`.

**Built-ins: override or opt out.** `deco schema` always includes the schemas of the [built-in blocks](/next/model#built-in-blocks), `page`, `redirect` and `telemetry`. `Page`, `Redirect` and `Route` are exported from `@decocms/blocks`. Declaring a built-in key in `Content` replaces its form; see [Built-in blocks](/next/model#built-in-blocks). Extend the exported type to add fields, or to narrow `sections`, a page's ordered list of blocks:

```ts
import type { Page } from "@decocms/blocks";

interface StorePage extends Page { theme: "light" | "dark" }

export type Content = { page: StorePage; post: Post };
```

An app that isn't a website opts out with `page: never` or `redirect: never`, which removes them from the schema. The CMS never reads `Content`, so the built-in blocks stay defined at runtime either way.

Studio learns the shape of your content only from the schema this command writes. What it looks for, how it reads and writes your files, and how the CLI bridges Studio's existing conventions are covered in [Studio and the content protocol](/next/studio-protocol) and [under the hood](/next/studio).

## Keep the schema compatible

Content and code live in one repository but change independently: an editor's content branch and a developer's code branch can merge in either order. Nothing at runtime checks that they fit, because the CMS doesn't compare schemas. They're kept compatible before anything merges, in two directions. The first is checked in CI by `deco schema --check`, which isn't built yet; it's part of the first release (see the [Roadmap](/roadmap#roadmap-cli--add-deco-schema-check-a-compatibility-check)). The second is a rule you follow when merging: no tool checks entry values against the schema until the content validation commands on the [Roadmap](/roadmap#roadmap-cli--add-validation-commands-to-the-cli) ship.

- **Backward compatible: new code still renders all existing content.** A code change must not break content that's already saved. `deco schema --check <base>` enforces this. It generates the schema from your code and compares it with `<base>`, the path to an earlier `.deco/schema.json`, such as the one on `main`. It lists every breaking change and exits with a non-zero code if it finds one. It writes nothing.
- **Content only uses types its commit's code has.** Content and code ship in the same build, so each commit's content must use only block types and fields that the same commit's code defines. Studio reads the schema next to the content it edits (your working tree, with [`deco serve`](#edit-local-content-from-studio)), so it only offers what that code has. An entry written by hand or by an agent that uses a type the code lacks fails that block with `UNKNOWN_BLOCK` (see [Errors](/next/standalone#errors)); merge the code that adds a type before, or with, the content that uses it. Rolling code back by reverting a commit has the same catch: content that already uses the newer types or fields fails on the older code until you revert that content too. Redeploying a previous build doesn't, because it ships that build's own content.

What `--check` treats as breaking:

| Change | Breaking? |
|---|---|
| Removing a block type (a function in the block map) or a `Content` type | Yes. `--check` compares schemas only, so any removal counts, whether or not saved content uses the type. Remove a type in a later change, once no content uses it. To rename a block type, keep the old name as an alias (see [Rename a type with an alias](/next/adoption#rename-a-type-with-an-alias)); the old name stays in the schema, so the check passes. Don't rename a `Content` type this way yet: the check would pass, but Content aliases don't work at runtime (see the [Roadmap](/roadmap#roadmap-cli--emit-a-runtime-alias-table)). |
| Removing or renaming a field | Yes. Fields have no aliases, so rename in steps: add the new name as an optional field, move the content over, then remove the old field once no content uses it. |
| Adding a required field, or making an optional field required | Yes: existing entries don't have it |
| Narrowing a field's type: a `string` becoming a union of allowed values, a union losing a member, a tighter limit (a lower `@maximum` or `@maxLength`, or a higher `@minimum` or `@minLength`) | Yes: saved values may fall outside it |
| Adding a block type, a `Content` type or a built-in type | No |
| Adding an optional field | No |
| Widening a field's type: a union gaining a member, a required field becoming optional | No |

Run the schema check in CI on every pull request. This GitHub Actions workflow regenerates the schema and fails if `.deco/schema.json` changed or was never committed:

```yaml title=".github/workflows/schema.yml"
name: Schema
on: pull_request

jobs:
  schema:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - name: The committed schema matches the code
        run: |
          npx --no-install deco schema
          if [ -n "$(git status --porcelain -- .deco/schema.json)" ]; then
            git diff -- .deco/schema.json
            echo ".deco/schema.json is missing or out of date: run deco schema and commit it."
            exit 1
          fi
```

`--no-install` makes `npx` fail if `@decocms/blocks-cli` isn't installed, instead of downloading some other package named `deco`. If you use `--root`, pass it to `deco schema` and replace `.deco/schema.json` with `<dir>/.deco/schema.json`. Make the job a required check in your branch protection rules, so a failing pull request can't merge.

<Callout>**Status. The compatibility step needs `deco schema --check`, which isn't built yet; it ships with the first release.** Once it's out, add a step that compares the schema with the one on the pull request's target branch (`git show "origin/$BASE_REF:.deco/schema.json" > base-schema.json`, then `deco schema --check base-schema.json`). Until then, review schema diffs against the table above by hand. See the [Roadmap](/roadmap#roadmap-cli--add-deco-schema-check-a-compatibility-check).</Callout>

Content-only changes, from Studio, an agent or by hand, never change the schema, so `--check` always passes them, and `deco schema` still checks the content model (entry names, aliases and route collisions) in the same pull request.

<h2 id="the-cli-commands">CLI reference</h2>

The CLI has three commands, and each does one job:

- **`deco schema`** turns the types in your block map into `.deco/schema.json`. Commit this file.
- **`deco content`** turns the files in `.deco/blocks` into the [content module](/next/content#the-content-module), `.deco/blocks.gen.ts`. It's generated, so gitignore it. If `.deco/blocks` has no `Telemetry.json`, it also scaffolds one: settings only the [hosted Deco CMS](/next/hosted-telemetry) reads. Without a connected site the entry is inert, and you can delete it.
- **`deco serve`** is the local server Studio edits your checkout through (see [below](#edit-local-content-from-studio)).

```bash
deco schema [--entry <path>] [--root <dir>] [--watch] [--check <base>]
deco content [--root <dir>] [--watch]
deco serve [--root <dir>] [--port <n>] [--host <addr>] [--app-url <url>] [--token <t>] [--allow-origin <origin>]… [--assets <dir>] [--read-only]
```

- `--entry <path>` (`deco schema` only): the file that exports your block map. By default the CLI looks for `blocks.ts` or `blocks.tsx` in the project root or in `src/`.
- `--root <dir>`: the folder that contains `.deco`, such as `apps/storefront` in a monorepo. By default, the CLI walks up from the current directory to the first folder with a `.deco`.
- `--watch`: regenerate as files change.
- `--check <base>` (`deco schema` only): compare the schema your code generates now with an earlier one, and fail on breaking changes. It writes nothing. It isn't built yet and ships with the first release (see the [Roadmap](/roadmap#roadmap-cli--add-deco-schema-check-a-compatibility-check)). See [Keep the schema compatible](#keep-the-schema-compatible).

There's no separate dev command: run `deco schema` and `deco content` before your dev server and your build. Why the content module is gitignored, and what reloads without a rerun, is in [The content module](/next/content#the-content-module).

```json title="package.json"
{
  "scripts": {
    "predev": "deco schema && deco content",
    "prebuild": "deco schema && deco content"
  }
}
```

### Edit local content from Studio

`deco serve` is the local server for Studio. Over the [content protocol](/next/studio-protocol), it serves three things from your working tree:

- **Your content**: the entries in `.deco/blocks`, which Studio reads and writes.
- **Your schema**: `.deco/schema.json`, read-only. Studio builds its forms from it; `deco schema` writes it.
- **Upload URLs**: where Studio sends the images and other files editors upload. Each one is written to `.deco/assets/` (or the folder `--assets` names), and the field stores `/assets/<name>`.

See [Edit your local checkout](/next/studio-protocol#edit-your-local-checkout) for the flow. Besides `--root`, it takes:

- `--port <n>`: the port to listen on (default 4545).
- `--host <addr>`: the address to listen on. The default is 127.0.0.1; any other address prints a warning, because the server would be reachable from other machines.
- `--app-url <url>`: your dev app, which Studio's canvas opens. By default, the port from your Vite config, else `http://localhost:5173`.
- `--token <t>`: a fixed token instead of a random one per run (or `DECO_SERVE_TOKEN`).
- `--allow-origin <origin>`: another browser origin allowed to call the server, besides Studio's (repeatable).
- `--assets <dir>`: the folder Studio's uploads are written to, relative to the folder that contains `.deco` (default `.deco/assets`). The field always stores `/assets/<name>`, whatever this folder is, so point it at a folder your app serves at `/assets/`, such as `public/assets`; see [Images and other uploads](/next/studio-protocol#images-and-other-uploads).
- `--read-only`: serve the content without accepting writes or uploads.
