# Matchers and variants

A store's content often depends on a condition: a summer sale banner that shows only between two dates, a different hero for visitors on mobile, a new checkout for 25% of shoppers. You don't need a feature for each. A **matcher** is a block function that returns `true` or `false`. A **variant** is one option: a `rule`, which takes a matcher, and a `value`. The `multivariate` block picks the value of the first variant whose rule is `true`. You write matchers in code; editors pick and fill both in [Studio](/next/how-it-works#studio), like any other [block](/next/blocks).

This page shows the matchers that ship, the function that picks a variant, how to write your own matcher, and what to check before you rely on variants in production.

## Matchers

A matcher is a function that returns a `boolean`. It's a block like any other. Three ship with Deco, because they depend only on the clock:

```ts
import { always, never, date } from "@decocms/blocks/matchers";

// always()                               => true
// never()                                => false
// date({ start?: string; end?: string }) => boolean, true when now is between start and end
```

Here's the summer sale as a `date` block:

```jsonc
// Stored as JSON
{ "__resolveType": "date", "start": "2026-06-21T00:00:00-04:00", "end": "2026-07-31T23:59:59-04:00" }

// Means
date({ start: "2026-06-21T00:00:00-04:00", end: "2026-07-31T23:59:59-04:00" });   // true during the sale
```

`start` and `end` are ISO 8601 strings. A date without a time, like `"2026-07-31"`, means midnight UTC, so add a time and offset to end on your own clock.

A device, a cookie, a country or a loyalty tier depends on your app, so those matchers are yours to write (see [Write your own matcher](#write-your-own-matcher)).

## Variants

`multivariate` (named after multivariate testing) is three lines in your own code, so you can change how it picks:

```ts title="src/multivariate.ts"
export function multivariate<T>({ variants }: { variants: { rule: boolean; value: T }[] }) {
  return variants.find((v) => v.rule)?.value;
}
```

Add it to your [block map](/next/blocks#the-block-map) with the matchers:

```ts title=".deco/index.ts"
import type { Blocks } from "@decocms/blocks";
import { always, never, date } from "@decocms/blocks/matchers";
import { multivariate } from "../src/multivariate";
import { PromoBanner } from "../src/promo-banner";

export default { always, never, date, multivariate, "promo-banner": PromoBanner } satisfies Blocks;
```

Now the promo banner's title can change for the sale:

```jsonc
// Stored as JSON
{
  "__resolveType": "promo-banner",
  "title": {
    "__resolveType": "multivariate",
    "variants": [
      { "rule": { "__resolveType": "date", "start": "2026-06-21T00:00:00-04:00", "end": "2026-07-31T23:59:59-04:00" }, "value": "Summer sale: 30% off" },
      { "rule": { "__resolveType": "always" }, "value": "Free shipping over $50" }
    ]
  },
  "href": "/summer"
}

// Means
PromoBanner({
  title: multivariate({
    variants: [
      { rule: date({ start: "2026-06-21T00:00:00-04:00", end: "2026-07-31T23:59:59-04:00" }), value: "Summer sale: 30% off" },
      { rule: always(), value: "Free shipping over $50" },
    ],
  }),
  href: "/summer",
});
```

Blocks resolve from the inside out (see [Composing blocks](/next/blocks#composing-blocks)), so every rule runs first, and an `async` rule is awaited; `multivariate` sees only booleans. `PromoBanner` gets a plain string and never knows a variant was involved.

The first match wins, so keep the `always()` variant last, as the fallback. If no rule matches, `multivariate` returns `undefined`, and so the component gets `undefined` instead of a title.

Any field can be a variant: one block in a page's `sections`, or the whole list, which is how Studio varies a page. [Schema](/next/schema#from-types-to-forms) shows how the field's type flows through `multivariate<T>`. In Studio, each variant is a tab, and its rule is picked from the matchers in your map.

## Write your own matcher

Any block function that returns a `boolean` is a matcher. It reads the current request the way the rest of your app does (see [Reading the request](/next/blocks#reading-the-request)). These examples use Next.js's `next/headers`; on TanStack Start, read the request with `getRequest()` from `@tanstack/react-start/server`.

A visitor's device:

```ts title="src/matchers.ts"
import { headers } from "next/headers";

export async function device({ is }: { is: "mobile" | "desktop" }) {
  const ua = (await headers()).get("user-agent") ?? "";
  return (/Mobi|Android/i.test(ua) ? "mobile" : "desktop") === is;
}
```

A share of shoppers, for an A/B test. Each visitor needs a bucket from 0 to 99 that stays the same on every visit, so they keep seeing the same variant. A cookie holds it:

```ts title="src/matchers.ts"
import { cookies } from "next/headers";

export async function inExperiment({ percent }: { percent: number }) {
  const bucket = Number((await cookies()).get("bucket")?.value ?? 100);   // no cookie: not in the experiment
  return bucket < percent;   // { "percent": 25 } matches buckets 0 to 24
}
```

Your app sets the cookie once, before the page renders. In Next.js that's `proxy.ts` (Next.js 16's name for `middleware.ts`):

```ts title="src/proxy.ts"
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  if (request.cookies.has("bucket")) return NextResponse.next();
  const bucket = String(Math.floor(Math.random() * 100));   // 0 to 99
  request.cookies.set("bucket", bucket);                      // so this first request sees it too
  const response = NextResponse.next({ request: { headers: request.headers } });
  response.cookies.set("bucket", bucket, { maxAge: 60 * 60 * 24 * 365 });   // and every later visit
  return response;
}
```

Unlike `experiments` in the [Quickstart](/next/quickstart), which rolls the dice on every call, this keeps each shopper in the same variant.

Add both to your block map, then run `npx @decocms/blocks schema` again (see [Give editors a form](/next/quickstart#2-give-editors-a-form)). Studio's rule picker now lists them next to `date`, because Deco treats every block function that returns a `boolean` as a matcher (see [what Studio reads](/next/studio-compatibility#what-studio-reads-from-the-schema)):

```ts title=".deco/index.ts"
import type { Blocks } from "@decocms/blocks";
import { always, never, date } from "@decocms/blocks/matchers";
import { device, inExperiment } from "../src/matchers";
import { multivariate } from "../src/multivariate";
import { PromoBanner } from "../src/promo-banner";

export default {
  always, never, date, device, inExperiment, multivariate,
  "promo-banner": PromoBanner,
} satisfies Blocks;
```

Now a page's hero can differ on mobile. `MobileHero` and `DesktopHero` are [saved blocks](/next/blocks#blocks-in-your-repository):

```jsonc
// Stored as JSON, one entry in a page's sections
{
  "__resolveType": "multivariate",
  "variants": [
    { "rule": { "__resolveType": "device", "is": "mobile" }, "value": { "__resolveType": "MobileHero" } },
    { "rule": { "__resolveType": "always" }, "value": { "__resolveType": "DesktopHero" } }
  ]
}

// Means
multivariate({
  variants: [
    { rule: await device({ is: "mobile" }), value: MobileHero },
    { rule: always(), value: DesktopHero },
  ],
});
```

And the cart's checkout link can send 25% of shoppers to the new checkout:

```jsonc
// Stored as JSON, the checkoutUrl field of a cart block
{
  "__resolveType": "multivariate",
  "variants": [
    { "rule": { "__resolveType": "inExperiment", "percent": 25 }, "value": "/checkout/new" },
    { "rule": { "__resolveType": "always" }, "value": "/checkout" }
  ]
}

// Means
multivariate({
  variants: [
    { rule: await inExperiment({ percent: 25 }), value: "/checkout/new" },
    { rule: always(), value: "/checkout" },
  ],
});
```

Matchers aren't tied to a website: a mobile app can read the shopper's loyalty tier from its own state. `and`, `or` and `not` are one-line matchers, if you want them.

## Before you go live

### Every variant resolves

Every variant's `value` resolves before `multivariate` picks one. For a title that's free. For two heroes that each fetch products, it costs both fetches, and a failure in a variant that wasn't picked still fails the whole block. Studio hides a block by wrapping it in a variant whose only rule is `never()`, so a hidden block still runs, and its result is `undefined`.

To run only the picked one, make the values the names of saved blocks, as plain strings. A string isn't a block, so nothing runs; `multivariate` returns a name, and you resolve it with [`client.resolve`](/next/blocks#composing-blocks):

```jsonc
// Stored as JSON, saved as HeroPick
{
  "__resolveType": "multivariate",
  "variants": [
    { "rule": { "__resolveType": "device", "is": "mobile" }, "value": "MobileHero" },
    { "rule": { "__resolveType": "always" }, "value": "DesktopHero" }
  ]
}

// Means
multivariate({
  variants: [
    { rule: await device({ is: "mobile" }), value: "MobileHero" },   // the values are names, so only the rules run
    { rule: always(), value: "DesktopHero" },
  ],
});
```

```ts
const [name, err] = await client.resolve<string>("HeroPick");   // "MobileHero"
if (err) throw err;
const [hero] = await client.resolve(name);                      // only this variant runs
```

<Callout type="warning">**A variant is not access control.** It chooses between values that are all fine to compute and show. Never use one to guard protected data or to decide whether a side effect runs; put that check inside the function that does the work.</Callout>

### Caching

If you cache rendered pages, at a CDN for example, anything a matcher reads must be part of the cache key: the device, the `bucket` cookie. Otherwise the first visitor's variant is served to everyone: a page that varies by device would show the cached desktop hero to mobile visitors. See [Caching](/next/caching-and-observability).
