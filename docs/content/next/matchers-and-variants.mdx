# Matchers and variants

Campaigns run on a schedule, and publishing each change at exactly the right moment is a hassle. The easy way out is to add the content ahead of time and let it switch on by itself, on time. Under the hood, that's an `if`/`else` on a condition. Matchers and variants let you write that kind of condition as blocks.

## Schedule a campaign

Say the promo banner should show a Black Friday title from Friday to the end of Cyber Monday, and the usual title the rest of the time:

```tsx
const now = new Date();
const start = new Date("2026-11-27T00:00:00-05:00");
const end = new Date("2026-12-01T00:00:00-05:00");
const title = now >= start && now < end ? "Black Friday: 40% off everything" : "Free shipping over $50";

<PromoBanner title={title} href="/deals" />;
```

It works, but the dates and the titles live in your code. Changing them is a code change and a deploy, and marketing can't do it themselves.

As blocks, the code above is analogous to this content, which editors can change:

```jsonc
{
  "__resolveType": "promo-banner",
  "title": {
    "__resolveType": "multivariate",
    "variants": [
      {
        "rule": { "__resolveType": "date", "start": "2026-11-27T00:00:00-05:00", "end": "2026-12-01T00:00:00-05:00" },
        "value": "Black Friday: 40% off everything"
      },
      {
        "rule": { "__resolveType": "always" },
        "value": "Free shipping over $50"
      }
    ]
  },
  "href": "/deals"
}
```

`multivariate` is a [built-in block](/next/blocks#built-in-blocks). It evaluates each variant's `rule` in order and returns the `value` of the first one that's `true`. Each rule is a block that returns `true` or `false`, such as the built-in `date` and `always`. Each piece of the code version has a block:

| In code | As blocks |
| --- | --- |
| The ternary, or a chain of `if`/`else if` | `multivariate` with a list of variants; the first whose rule is `true` wins. |
| The date condition | The built-in `date` matcher. |
| The final `else` | A last variant whose rule is `always`. |
| The constants | Saved values that editors change in [Studio](/next/how-it-works#studio). |

`end` takes the campaign down too, so there's nothing to do on Monday. `PromoBanner` gets a plain string: it never knows a variant was involved.

Any field can be a variant: a title, one block in a page's `sections`, or the whole list, which is how Studio varies a page. [Schema](/next/schema#from-types-to-forms) shows how the field's type flows through `multivariate<T>`.

### Only the chosen variant runs

There's a catch in the version above. Blocks resolve from the inside out (see [Composing blocks](/next/blocks#composing-blocks)): every argument is computed before the function that receives it runs. So every variant's `value` is computed before `multivariate` picks one, as if an `if` ran both of its branches. For a title, that costs nothing. But if each value were a hero section that fetches products, every hero would fetch, and all but one result would be thrown away.

The fix is a [lazy block](/next/blocks#lazy-blocks). Wrapped in `lazy`, a value isn't computed until `multivariate` chooses it, so only the winning branch runs, like `cond ? a() : b()`:

```jsonc
{
  "rule": { "__resolveType": "date", "start": "2026-11-27T00:00:00-05:00", "end": "2026-12-01T00:00:00-05:00" },
  "value": { "__resolveType": "lazy", "value": "Black Friday: 40% off everything" }
}
```

That's why `multivariate` takes lazy values, and why saved variants always carry the wrapper (`deco check` flags a value without it). Editors never see it: Studio adds it for them. Rules stay eager: they're cheap booleans.

## Why it goes live on time

Both titles are already in the [release](/next/releases-and-drafts#releases), the content everyone sees, since the deploy that followed your merge. So the switch isn't an event: at 00:00 there's no publish, no deploy and nothing that can fail.

Each time a page is rendered, the server evaluates the rule against its own clock. Hosting providers keep server clocks synced to within a fraction of a second, so they all switch together. A page cached before midnight can still show the old title; see [Troubleshooting](/next/troubleshooting).

## Check it before it starts

A scheduled campaign is a change to content files, so it's checked like any other change, days before it goes live:

- **Review it in a pull request.** Reviewers read the dates and the campaign value in the diff of `.deco/blocks`, and [`deco check`](/next/cli#deco-check) makes sure every block fits your code (see [On a branch](/next/releases-and-drafts#on-a-branch)).
- **Preview the page.** A [draft](/next/releases-and-drafts#preview) or your host's [preview deployment of the branch](/next/releases-and-drafts#on-a-branch) renders it at the current time, so before the start date it shows the fallback, exactly what visitors see until midnight.
- **Keep `always()` last.** The first match wins, so the `always()` variant is the fallback. If no rule matches, `multivariate` returns `undefined`, and the component gets `undefined` instead of a title. With `always()` last, the page never comes up empty, before the campaign or after it ends.

## Matchers: conditions for the marketing team

A block function that returns `true` or `false` is a **matcher**. Matchers are what make variants usable without code: Studio lists every matcher in your block map in each variant's rule picker, so the marketing team builds conditions by picking from a list and filling a short form. `date` is one; you can add your own (see [Write your own matcher](#write-your-own-matcher)), such as:

- **Temperature**: `true` when it's above a given temperature where the visitor is, to promote cold drinks on hot days.
- **Birthday**: `true` during a signed-in customer's birthday week, to show a gift.
- **Cart value**: `true` when the cart is over an amount, to offer free shipping.
- **Loyalty tier**: `true` for gold members, to show early access.

### Built-in matchers

Three matchers are [built-in blocks](/next/blocks#built-in-blocks), because they depend on nothing but the clock. Like every built-in, they need no import:

- **`always`** is always `true`. Use it for the fallback.
- **`never`** is always `false`.
- **`date`** is `true` from `start` until `end`. Both are optional.

`start` and `end` are ISO 8601 strings. Write them with the offset your store's time zone has on that date, like `"2026-11-27T00:00:00-05:00"` for New York in November, so the campaign starts at midnight on your clock. Daylight saving time changes the offset (New York is `-04:00` in summer), so check it for each date. A date without a time, like `"2026-11-27"`, means midnight UTC. `end` itself doesn't match, so a campaign that ends at midnight uses that midnight as its `end`.

`multivariate` and `lazy` are built in too.

### Write your own matcher

In code, a weekend title would be one more condition, like `today === "Sat" || today === "Sun"`. As a matcher, that condition moves into a function that returns a `boolean`. This one is `true` on the days of the week you pick, in your store's time zone:

```ts title="src/matchers.ts"
type Day = "Mon" | "Tue" | "Wed" | "Thu" | "Fri" | "Sat" | "Sun";

export function weekday({ days, timeZone = "America/New_York" }: { days: Day[]; timeZone?: string }) {
  const today = new Intl.DateTimeFormat("en-US", { weekday: "short", timeZone }).format(new Date());   // "Sat"
  return days.some((day) => day === today);
}
```

Add it to your block map and run `npx @decocms/blocks schema` (see [Give editors a form](/next/quickstart#2-give-editors-a-form)):

```ts title=".deco/index.ts"
import type { Blocks } from "@decocms/blocks";
import { weekday } from "../src/matchers";
import { PromoBanner } from "../src/promo-banner";

export default { weekday, "promo-banner": PromoBanner } satisfies Blocks;   // always, never, date, multivariate and lazy are built in
```

Studio's rule picker now lists `weekday` next to the built-in `date` (see [what Studio reads](/next/studio-compatibility#what-studio-reads-from-the-schema)). An editor can give weekends their own title:

```jsonc
// Stored as JSON, the title field of the promo banner
{
  "__resolveType": "multivariate",
  "variants": [
    {
      "rule": { "__resolveType": "weekday", "days": ["Sat", "Sun"] },
      "value": { "__resolveType": "lazy", "value": "Weekend: free shipping on everything" }
    },
    {
      "rule": { "__resolveType": "always" },
      "value": { "__resolveType": "lazy", "value": "Free shipping over $50" }
    }
  ]
}

// Means
multivariate({
  variants: [
    { rule: weekday({ days: ["Sat", "Sun"] }), value: async () => "Weekend: free shipping on everything" },
    { rule: always(), value: async () => "Free shipping over $50" },
  ],
});
```

A few more things you can do:

- **Make it `async`.** `multivariate` waits for it.
- **Match on the request.** To match on a cookie, a header or a country, read the request the way the rest of your app does (see [Reading the request](/next/blocks#reading-the-request)).
- **Combine rules.** `and`, `or` and `not` are one-line matchers, like `export const not = ({ rule }: { rule: boolean }) => !rule;`.
- **Skip an expensive rule.** Rules always run. A matcher can take an inner rule as [`Lazy<boolean>`](/next/blocks#lazy-blocks) and call it only when needed, like `export const and = async ({ a, b }: { a: boolean; b: Lazy<boolean> }) => a && (await b());`, where `b` runs only if `a` is `true`.
- **Pick variants your way.** Declare your own `multivariate` in your [block map](/next/blocks#the-block-map); it replaces the built-in. Type each value as `Lazy<T>` to keep running only the chosen one.

<Callout type="warning">**A variant is not access control.** Only the chosen value runs, but that's an optimization, not a guard: choose between values that are all fine to show. Never use one to guard protected data or to decide whether a side effect runs; put that check inside the function that does the work.</Callout>
