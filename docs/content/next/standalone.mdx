# API reference

Everything on this page is exported from `@decocms/blocks`. The ready-made matchers (`always`, `never`, `date`) are in `@decocms/blocks/matchers`, and the instrumented fetch for upstream clients is in `@decocms/blocks/fetch`.

## `createCMS(config)`

`createCMS` returns a **CMS**: your block map plus your content. Create it once, at module scope, and ask it for a client per request: `forRelease()` for visitors, `forDraft(pointer)` for [drafts](/next/preview#clients-for-drafts).

- **One revision per client.** A client loads one revision on first use and reads only that revision afterwards, so everything in one response agrees. Every later call, `list` or `resolve`, reuses that content, so a page's blocks can stream as separate calls. The next request's client sees the next revision, so don't share a client across requests.
- **Results are memoized per client and per block-map object**: build the map at module scope. An entry referenced three times runs its function once per client. Results are kept per function of the map you passed, so a map rebuilt inside your handler starts with an empty cache.
- **Clients are cheap**: the content cache lives in the CMS, shared by every client.
- **Same config, same instance**: see [One instance per process](#one-instance-per-process).

```ts
function createCMS(config: {
  blocks: Blocks;               // your block functions; the CMS uses { ...builtIns, ...blocks }, so a key here overrides a built-in
  content: Snapshot | Loader;   // the content module (.deco/blocks.gen.ts), or any Loader
  interval?: number;            // ms between update() checks of a content source that has one; default DECO_CONTENT_INTERVAL or 60_000; minimum 60_000

  // Hosted Deco CMS (optional), see /next/hosted
  site?: string;                // your site's ID, usually DECO_SITE
  token?: string;               // your site token (secret), usually DECO_SITE_TOKEN
}): CMS;

interface CMS {
  forRelease(): Client;                         // a client reading the current release
  forDraft(pointer: string): Client;            // a client reading the draft a pointer names; an invalid pointer, or a source without drafts, behaves like the release
  update(): Promise<{ updated: boolean }>;      // ask the content source for newer content now; never throws
}

interface Client {
  resolve<T = unknown>(target: unknown, options?: { run?: boolean }): Promise<Result<T>>;   // run: false reads without running
  list<T = Block>(type: string, options?: ListOptions<T>): Promise<Result<T[]>>;
}
```

`content` takes the content module or a `Loader` (see [Configuring content](/next/content#configuring-content)). `interval` paces a content source that can change while the process runs (see [Loaders](#loaders)); the content module never changes, so it ignores it. `site` and `token` connect the hosted Deco CMS and do nothing on their own: with either of them unset, the CMS reads `content` only and sends nothing anywhere. The [rule from Blocks](/next/model#the-rule) is how a client resolves.

<Hosted to="/next/hosted#connect-your-site" label="Connect your site">**Hosted options.** With `site` and `token` set, the CMS serves releases published without a deploy, loads drafts for `forDraft`, and sends sampled telemetry.</Hosted>

## Loaders

One interface. `load()` with no argument is production; `load(pointer)` is a draft. `update()` checks for newer content. Most sites never write one: they pass the content module (see [Configuring content](/next/content#configuring-content)). Here a loader is a source of content; it isn't Studio's "loaders" or a router's route loader.

```ts
interface Loader {
  load(pointer?: string | null): Promise<Snapshot>;   // Snapshot = { revision, blocks }; see Types
  update?(): Promise<{ updated: boolean }>;
}
```

| Content | Loads | Use it for |
|---|---|---|
| A snapshot `{ revision, blocks }` (the content module) | The content that ships with the app, generated by `deco content`. Ignores the pointer: there are no drafts in it. No `update()`. | Every site: the content your build ships. With the hosted Deco CMS, also the fallback before the first release |
| Any object with `load()` | The snapshot its `load()` returns, or the draft a pointer names if it has drafts. If it can change while the process runs, give it `update()`. | Content kept somewhere other than the build, such as your own storage |
| `remoteLoader(fallback: Snapshot \| Loader, { site, token, interval? })` | Hosted: releases and drafts from the Deco API, over the fallback. `createCMS` builds it for you when `site` and `token` are set. See [Publishing without a deploy](/next/hosted-publishing). | The hosted Deco CMS |

A loader with `update()` is checked on its own: every `interval` (default `DECO_CONTENT_INTERVAL` or 60 000 ms, never below 60 000), at the next idle moment, so a request never waits on it. On Cloudflare Workers, which run no timers between requests, a due check runs after the response inside `ctx.waitUntil`. `cms.update()` checks at once, for a webhook or an admin "refresh now" button; it refreshes only the server that runs it, and never throws. A snapshot, like the content module, never changes, and a loader without `update()` is always current by construction.

If `load(pointer)` fails, the client serves what a normal request would get, never a mix of draft and published entries.

A pointer comes from request input, so a loader that serves drafts must treat it as untrusted: allow-list the hosts it may fetch from, so a crafted pointer can't make your server fetch arbitrary URLs, and require a credential it can verify, such as a signed token, before serving unpublished content.

Caching, ETags, and fallbacks live inside the CMS, which any number of clients share. The client only ever sees `{ revision, blocks }`.

## One instance per process

`createCMS` instances (and hosted `remoteLoader` instances) are process-wide singletons. Each is stored on `globalThis` under a `Symbol.for("decocms.blocks…")` key derived from its configuration: the content's identity (for the content module, the `.deco` folder it was generated from; for a loader you write, the loader object; never the revision, so a hot reload that hands in new content keeps the same instance), and, with the hosted Deco CMS, also the site ID and token. So a package loaded twice, by two bundles or by a dev reload (hot module replacement, HMR), still shares one content cache and one schedule of `update()` checks. Different configurations, such as several sites in one app, get different instances. Calling it again with the same key but different options keeps the first instance and logs a warning that names the conflicting options. Tests can start clean:

```ts
function resetForTests(): void;   // clears every stored instance
```

## Draft pointers

A pointer is a string, `<host[:port]><path[?query]>@<version>`, that names where a draft lives and which version it is. `forDraft` passes it to your content source's `load(pointer)`; the content module ignores it (see [Clients for drafts](/next/preview#clients-for-drafts)). With the hosted Deco CMS, Studio makes them ([Drafts on your site](/next/hosted-drafts)). Two helpers cover everything in between:

```ts
interface DraftPointer {
  host: string;      // host[:port] of the content source that holds the draft (the Deco API, when hosted), e.g. "api.deco.example"
  path: string;      // starts with "/"; opaque to your app (hosted drafts put a token signed by Studio in its query)
  version: string;   // opaque, immutable: the branch head or ETag
}

function parseDraftPointer(raw: string | null | undefined): DraftPointer | null;
function formatDraftPointer(pointer: DraftPointer): string;
```

`parseDraftPointer` is strict and returns `null` on anything unexpected: a scheme, a stray `@`, an unrooted path, an odd character in the host or version. It's what `forDraft` calls, so an app only needs it to look inside a pointer, for example to show which version is being previewed, to key a cache on `version`, or to reject a pointer before storing it in a cookie. `formatDraftPointer` is the inverse, for building one from parts, as a mobile app might from a deep link.

For websites, two more helpers carry a pointer from a URL into a cookie, so the parameter and cookie names never appear in app code. The hosted draft flow uses them; see [Keep the draft across navigation](/next/hosted-drafts#keep-the-draft-across-navigation):

```ts
function draftPointer(request: Request | { url: string; headers: Headers }): string | null;
// ?__draft= from the URL first, then the deco-draft cookie. Null when neither is present.

function draftCookie(request: Request | { url: string; headers: Headers }): string | null;
// When the URL carries ?__draft=, the Set-Cookie value that stores it (HttpOnly, SameSite=Lax, Path=/),
// or one that expires the cookie when the value is empty. Null on every other request.

const DRAFT_COOKIE = "deco-draft";   // for frameworks whose cookie API has no Request, e.g. Next.js cookies()
```

Both take anything with a `url` and `headers`, so they work with a fetch `Request`, a Next.js `NextRequest`, or a framework's request wrapper. `DRAFT_COOKIE` is for the one place that has no request at all: reading the cookie in a Next.js Server Component.

```ts
const pointer = parseDraftPointer(cookie);
if (pointer) console.log(`previewing ${pointer.version} from ${pointer.host}`);

// the path is opaque: copy it, don't build it
formatDraftPointer({ host: "api.deco.example", path: "/drafts/acme/main?token=…", version: "9f3c1a" });
// "api.deco.example/drafts/acme/main?token=…@9f3c1a"
```

## `client.resolve(target, options?)`

Loads the content once and applies the [registry rule](/next/model#the-rule) to the target: saved entries expand, and each function the target names in your block map runs with its resolved inputs. [Built-in blocks](/next/model#built-in-blocks) are always defined.

| Call | Returns |
|---|---|
| `resolve("SummerSEO")` | The result of running the entry's function: for `SummerSEO`, `seo({ title: "Sunny!", description: "Light layers for long days." })` |
| `resolve("SummerSEO", { run: false })` | The saved entry, with references expanded and nothing run |
| `resolve("SummerPage")` | The built-in page block's result: the page with `seo` and every block in `sections` resolved |
| `resolve({ __resolveType: "seo", title: "Sale" })` | The result for an inline block: `seo({ title: "Sale" })` |
| `resolve(page.sections)` | An array of results, one per block in the list |
| `resolve({ title: "Store" })` | The same object: it contains no blocks |

A string target is always an entry name. Any other value is walked as is, so you can pass a page field without checking whether it's a block or a literal. `T` describes the result you expect, because an entry name can't carry a static type; it isn't validated at runtime.

**Reading without running.** With `{ run: false }`, `resolve` stops after expanding saved entries: references are replaced and merged, and no function runs. Use it for previews, tooling and debugging, and to get a page's blocks without running them, so you can resolve each one with its own call; the [Next.js guide](/next/nextjs#7-stream-each-block-optional) streams a page that way. `client.list` returns entries this way by default.

## `client.list(type, options?)`

Every saved entry whose `__resolveType` is `type` or an [alias](/next/adoption) of it (another key for the same type, used when renaming). By default nothing runs: each entry comes back as `resolve(name, { run: false })` would return it. With `run: true` each entry is resolved, so every block inside it, and the entry's own type, must be in the block map (built-ins included) or a saved entry, or it fails with `UNKNOWN_BLOCK`. `list("page", { run: true })` returns ready pages. Listing a `Content`-only type such as `post` with `run: true` fails.

```ts
interface ListOptions<T> {
  where?: (entry: T) => boolean;
  sort?: (a: T, b: T) => number;
  limit?: number;
  run?: boolean;
}

const today = new Date().toISOString().slice(0, 10);   // "YYYY-MM-DD", comparable as a string
const [posts] = await client.list<Post>("post", {
  where: (p) => p.date <= today,
  sort: (a, b) => b.date.localeCompare(a.date),
  limit: 20,
});
```

Filters run in memory over the loaded content map, the cost of content arriving as the whole map at once (see [Your content in Git](/next/content#snapshots-and-revisions)). Sites with tens of thousands of entries of one type should keep an index elsewhere.

## `matchRoute(url, items)`

A pure function. Given a URL and the entries you want to route, it returns the one that matches. The CMS doesn't know about URLs; this is the companion that does. See [Routing](/next/routing).

```ts
function matchRoute<T extends Route>(
  url: string | URL | Request,
  items: { routes: T[]; redirects?: Redirect[] },
): Match<T>;

type Match<T> =
  | { kind: "match";    entry: T; params: Record<string, string> }
  | { kind: "redirect"; location: string; status: 301 | 302 }
  | { kind: "not-found" };
```

Redirects win over routes, exact paths win over templates, and two entries that can match the same URL throw. Entries are compiled into a segment trie, cached per `routes` array object, so a lookup costs the URL's depth, not the number of routes, and passing the same array again skips the build. See [how it matches](/next/router-internals).

## `createInstrumentedFetch(options)`

<Callout>**Status.** `createInstrumentedFetch` and `@decocms/blocks/fetch` are proposed; see the [Roadmap](/roadmap#roadmap-api--turn-the-apps-into-thin-instrumented-clients).</Callout>

From `@decocms/blocks/fetch`. The fetch every [upstream client](/next/clients) uses: it times each request until its response headers arrive and labels the measurement. On its own it sends nothing anywhere: only the hosted Deco CMS consumes the measurements. For your own observability, instrument your code with OpenTelemetry as usual (see [Your own tracing](/next/operations#your-own-tracing)).

```ts
function createInstrumentedFetch(options: {
  provider: string;                                     // the provider label, e.g. "vtex", "acme-search"
  fetch?: typeof fetch;                                 // the fetch underneath; defaults to globalThis.fetch
  retry?: { attempts: number; backoffMs?: number };     // off unless set; a retried request is measured once
  circuitBreaker?: { failures: number; cooldownMs: number };   // off unless set
}): (input: string | URL | Request, init?: RequestInit & { operation?: string }) => Promise<Response>;
```

Each request is measured with `provider`, `operation`, `status_class`, `cached` and `retries` labels. It never logs request or response bodies, tokens or cookies. Writing a client with it is in [Write a client](/next/clients#write-a-client).

<Hosted to="/next/hosted-telemetry">**Telemetry without a collector.** When the CMS in the same process has a site ID and token, these measurements reach Deco as sampled upstream latency and error rates.</Hosted>

## Not in the SDK

v7's `/deco/invoke` endpoint (which runs loaders and actions over HTTP for Studio and the browser) and `cachedLoader` (see [v7 caching](/v7/caching)) aren't part of the next major. Call [upstream clients](/next/clients) from your framework's server functions or route handlers. Upstream caching belongs to the [framework binding](/next/architecture#key-terms), which isn't wired into these guides yet (see [Caching](/next/clients#caching)).

## Types

```ts
type Block = { __resolveType: string; [input: string]: unknown };
type VariantOf<T> = T | Block;   // T, or a block (usually a multivariate) that resolves to one

// A block map: what blocks.ts exports and the CLI reads.
type BlockFunction = (inputs: any) => unknown | Promise<unknown>;
type Blocks = Record<string, BlockFunction>;

// One fixed copy of the content: what the content module exports and load() returns.
type Snapshot = { revision: string; blocks: Record<string, unknown> };   // the content map: entry name → saved JSON

interface Loader {
  load(pointer?: string | null): Promise<Snapshot>;
  update?(): Promise<{ updated: boolean }>;
}

interface DraftPointer { host: string; path: string; version: string }

interface Route { name: string; path: string }                    // extend it to give a type a URL

// The built-in types. Their blocks are always in the registry: override the schema in Content with an
// interface that extends them, or the runtime block by declaring the key in your block map.
interface Page extends Route { seo: Block; sections: VariantOf<Array<VariantOf<Block>>> }
interface Redirect { from: string; to: string; permanent: boolean }

// The Telemetry entry's type (built in, always in the schema; read by the hosted Deco CMS, inert without it). Field names are proposed.
interface Telemetry { enabled: boolean; metrics: boolean; errorSampleRate: number }

type Match<T> =
  | { kind: "match";    entry: T; params: Record<string, string> }
  | { kind: "redirect"; location: string; status: 301 | 302 }
  | { kind: "not-found" };

type Result<T> = [T, null] | [null, CMSError];

interface CMSError {
  code: "NOT_FOUND" | "UNKNOWN_BLOCK" | "CYCLE" | "BLOCK_FAILED" | "LOADER_FAILED";
  message: string;
  path: (string | number)[];   // where in the tree it happened
  cause?: unknown;             // the original error, for BLOCK_FAILED and LOADER_FAILED
}
```

## Errors

Client calls never throw: `resolve` and `list` return `[value, null]` or `[null, error]`. The one exception in the SDK is `matchRoute`, which throws when two entries can match the same URL. That's a content bug `deco schema` also reports, so run it in CI on every commit, content commits included (see [Keep the schema compatible](/next/schema#keep-the-schema-compatible)), and catch the throw in your handler (see [Path templates and match order](/next/routing#path-templates-and-match-order)). Check the error, not the value, because a block function can legitimately return `null`.

| Code | When |
|---|---|
| `NOT_FOUND` | A string target or a reference names an entry that doesn't exist. |
| `UNKNOWN_BLOCK` | A `__resolveType` names neither a type in the block map nor a saved entry. [Built-in blocks](/next/model#built-in-blocks) never cause it. |
| `CYCLE` | References lead back to an entry that's already being expanded (see [The rule in full](/next/walkthrough#the-rule-in-full)). |
| `BLOCK_FAILED` | A block function threw. The original error is in `cause`. |
| `LOADER_FAILED` | The loader couldn't load the content. The original error is in `cause`. |

A `CMSError` has a `code`, a `message`, a `path` (where in the tree it happened, such as `["sections", 2, "product"]`), and an optional `cause`. Log it on the server, and show visitors a generic message.
