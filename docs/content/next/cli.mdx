# CLI

The Deco CLI is the `deco` command. It ships inside `@decocms/blocks`, so there's nothing extra to install, and it always matches your runtime version. Run it once with `npx` (`bunx` works the same):

```bash
npx @decocms/blocks schema
```

Once `@decocms/blocks` is installed, your `package.json` scripts call it by its short name, `deco` (for example `deco schema`). To call it from your own code, import it from `@decocms/blocks/cli`.

It has three commands, and each does one job:

- **`deco schema`** turns the types in your block map into `.deco/schema.json`. Commit this file. See [Schema](/next/schema).
- **`deco content`** turns the files in `.deco/blocks` into the [content module](/next/blocks#the-deco-content-command), `.deco/blocks.gen.ts`. It's generated, so gitignore it. If `.deco/blocks` has no `Telemetry.json`, it also scaffolds one: settings only the [hosted Deco CMS](/next/hosted-telemetry) reads. Without a connected site the entry is inert, and you can delete it.
- **`deco serve`** is the local server [Studio](/next/how-it-works#studio) uses to edit the files on your machine (see [below](#deco-serve)).

## Run it before dev and build

There's no separate dev command: run `deco schema` and `deco content` before your dev server and your build. Why the content module is gitignored, and what reloads without a rerun, is in [The `deco content` command](/next/blocks#the-deco-content-command).

```json title="package.json"
{
  "scripts": {
    "predev": "deco schema && deco content",
    "prebuild": "deco schema && deco content"
  }
}
```

With no arguments, both commands use the default paths below. If your block map or content lives somewhere else, pass its path, as in [the example below](#custom-paths).

## `deco schema` and `deco content`

```bash
deco schema  [input] [--out <file>] [--watch] [--check <base>]
deco content [input] [--out <file>] [--watch]
```

The first argument, `input`, is what the command reads. `--out` is where it writes. Both have defaults, so in most projects you pass neither. Paths are relative to the folder you run the command from. Unlike `deco serve`, they don't search parent folders.

| Command | `input` (what it reads) | `--out` (where it writes) |
| --- | --- | --- |
| `deco schema` | Your block map. By default, `blocks.ts` or `blocks.tsx` in the folder you run the command from, then in its `src/`. | `.deco/schema.json` |
| `deco content` | The folder of content files. By default, `.deco/blocks`. | `.deco/blocks.gen.ts` |

`deco content` only bundles the JSON files in that folder. It never reads your block map.

The other options:

- `--watch`: regenerate as files change.
- `--check <base>` (`deco schema` only): compare the schema your code generates now with an earlier one, and fail on breaking changes. It writes nothing. It isn't built yet and ships with the first release (see the [Roadmap](/roadmap#roadmap-cli--add-deco-schema-check-a-compatibility-check)). See [Change types safely](/next/schema#change-types-safely).

### Custom paths

If your block map lives somewhere else, pass its path:

```json title="package.json"
{
  "scripts": {
    "predev": "deco schema src/cms.ts && deco content",
    "prebuild": "deco schema src/cms.ts && deco content"
  }
}
```

Studio and `deco serve` always read the schema from `.deco/schema.json` and the content from `.deco/blocks`. Only move them if you don't use Studio. If you change `deco content --out`, change the `import content from "./.deco/blocks.gen"` line to match.

In a monorepo, run the commands from your app's folder (for example, as scripts in `apps/storefront/package.json`), so the defaults point at that app. Or pass both paths from the repository root:

```bash
deco schema apps/storefront/src/blocks.ts --out apps/storefront/.deco/schema.json
deco content apps/storefront/.deco/blocks --out apps/storefront/.deco/blocks.gen.ts
```

`--out` doesn't follow the input: without it, the output lands in `.deco/` of the folder you ran the command from.

## `deco serve`

```bash
deco serve [--root <dir>] [--port <n>] [--host <addr>] [--app-url <url>] [--token <t>] [--allow-origin <origin>]… [--assets <dir>] [--read-only]
```

`deco serve` is the local server Studio uses to edit the files on your machine, over the [content protocol](/next/content-protocol): it reads and writes `.deco/blocks`, reads `.deco/schema.json`, and accepts uploads into `.deco/assets/` (or `--assets`). See [Edit on your machine](/next/content-protocol#edit-on-your-machine) for the flow. It takes:

- `--root <dir>`: the folder that contains `.deco`, such as `apps/storefront` in a monorepo. By default, it walks up from the current directory to the first folder with a `.deco`.
- `--port <n>`: the port to listen on (default 4545).
- `--host <addr>`: the address to listen on. The default is 127.0.0.1; any other address prints a warning, because the server would be reachable from other machines.
- `--app-url <url>`: your dev app, which Studio's canvas opens. By default, the port from your Vite config, else `http://localhost:5173`.
- `--token <t>`: a fixed token instead of a random one per run (or `DECO_SERVE_TOKEN`).
- `--allow-origin <origin>`: another browser origin allowed to call the server, besides Studio's (repeatable).
- `--assets <dir>`: the folder Studio's uploads are written to, relative to the folder that contains `.deco` (default `.deco/assets`). The field always stores `/assets/<name>`, whatever this folder is, so point it at a folder your app serves at `/assets/`, such as `public/assets`; see [Images and other uploads](/next/content-protocol#images-and-other-uploads).
- `--read-only`: serve the content without accepting writes or uploads.
