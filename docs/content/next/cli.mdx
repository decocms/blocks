# CLI

The Deco CLI is the `deco` command. It ships inside `@decocms/blocks`, so there's nothing extra to install, and it always matches your runtime version. Run it once with `npx` (`bunx` works the same):

```bash
npx @decocms/blocks schema
```

Once `@decocms/blocks` is installed, your `package.json` scripts call it by its short name, `deco` (for example `deco schema`). To call it from your own code, import it from `@decocms/blocks/cli`.

Every command works on one folder, `.deco/`, in your app root (the folder with your app's `package.json`):

```text
.deco/
├── index.ts           your block map (.tsx also works)
├── blocks/            your saved blocks, one JSON file each
├── assets/            uploads from deco serve (only once you upload)
├── schema.gen.json    generated by deco schema, committed
└── blocks.gen.ts      generated by deco content, gitignored
```

Don't edit `schema.gen.json` or `blocks.gen.ts`; `index.ts` and `blocks/` are yours. The `.gen.` in a name marks a generated file. `blocks.gen.ts` is built from `blocks/`: it's your saved blocks as a module.

"Blocks" means three things here, so this table tells the files apart:

| File | What's in it | Who writes it | Commit it? |
| --- | --- | --- | --- |
| `index.ts` | Block types: the functions content can call | You | Yes |
| `blocks/` | Saved blocks, one JSON file each | You, an AI agent or Studio | Yes |
| `schema.gen.json` | The editor forms, built from `index.ts` | `deco schema` | Yes |
| `blocks.gen.ts` | The content module, built from `blocks/` | `deco content` | No, gitignore it |
| `assets/` | Uploaded images and files | `deco serve` | Yes |

It has four commands, and each does one job:

- **`deco schema`** turns the types in `.deco/index.ts` into `.deco/schema.gen.json`. Commit this file. See [Schema](/next/schema).
- **`deco content`** turns the files in `.deco/blocks` into the [content module](/next/blocks#the-deco-content-command), `.deco/blocks.gen.ts`. It's generated, so gitignore it. If `.deco/blocks` has no `Telemetry.json`, it also scaffolds one: settings only the [hosted Deco CMS](/next/hosted-telemetry) reads. Without a connected site the entry is inert, and you can delete it.
- **`deco check`** makes sure your saved blocks fit your code, and fails if one doesn't. It writes nothing. Run it in CI and before your build (see [below](#deco-check)).
- **`deco serve`** is the local server [Studio](/next/how-it-works#studio) uses to edit the files on your machine (see [below](#deco-serve)).

## Run it before dev and build

There's no separate dev command: run `deco schema` and `deco content` before your dev server and your build. The build also runs `deco check`, so content that doesn't fit the code fails the deploy instead of shipping; dev skips it, so a content error doesn't stop your dev server. Why the content module is gitignored, and what reloads without a rerun, is in [The `deco content` command](/next/blocks#the-deco-content-command).

```json title="package.json"
{
  "scripts": {
    "predev": "deco schema && deco content",
    "prebuild": "deco schema && deco content && deco check"
  }
}
```

## Finding the `.deco` folder

Every command takes `--root <dir>`: the folder that contains `.deco/`, relative to the current folder. You rarely pass it. By default, the command walks up from the current folder to the first folder with a `.deco/`, so it works from any subfolder of your app.

If no folder on the way up has a `.deco/`, the command stops with an error:

```text
no .deco/ found from /path/you/ran/it/in; run inside your app or pass --root
```

In a monorepo, walking up from the repository root never reaches `apps/storefront/.deco`, so the command fails there (or, if the root has a stray `.deco/`, it uses that one). Run the commands inside the app instead, for example as scripts in `apps/storefront/package.json`. Then `@decocms/blocks` must be a dependency of that app, so its scripts can find `deco`. Or pass the app from the repository root:

```bash
deco schema --root apps/storefront
deco content --root apps/storefront
```

[Studio](/next/how-it-works#studio)'s "app root" setting points at that same folder, both on your machine and when Studio reads your repository on GitHub in the [hosted version](/next/hosted-studio).

## `deco schema` and `deco content`

```bash
deco schema  [--root <dir>] [--watch]
deco content [--root <dir>] [--watch]
```

| Command | Reads | Writes |
| --- | --- | --- |
| `deco schema` | `.deco/index.ts` (or `.deco/index.tsx`) | `.deco/schema.gen.json` |
| `deco content` | `.deco/blocks/` | `.deco/blocks.gen.ts` |

`deco content` only bundles the JSON files in `.deco/blocks`. It never reads your block map.

The options:

- `--root <dir>`: the folder that contains `.deco/` (see [above](#finding-the-deco-folder)).
- `--watch`: regenerate as files change.

## `deco check`

```bash
deco check [--root <dir>]
```

`deco check` makes sure your saved blocks fit your code. It reads `.deco/schema.gen.json` and `.deco/blocks` as they are, writes nothing, and validates every saved block against that schema:

- Each saved block's props match its block type's schema: required fields are present, and values respect enums and limits.
- Every `__resolveType` names a block type (built-ins and aliases included) or a saved block that exists.
- A reference in a typed field points to a block that returns that type.
- No saved block has the name of a block type, a built-in or an alias (see [Names must not clash](/next/schema#names-must-not-clash)).
- No two entries can match the same URL (see [Path templates and match order](/next/routing#path-templates-and-match-order)).

It doesn't generate the schema or load your TypeScript. Run `deco schema` first, so the schema matches your code: `deco schema && deco check`.

Because it checks the content itself, it catches both directions: a code change that breaks saved content, and content that uses a block type or field your code doesn't have. It runs on content-only changes too (from you, an AI agent or Studio), and works the same on your machine as in CI.

When everything fits, it exits with 0. Otherwise it lists the problems per file and exits with 1:

```text
.deco/blocks/HomePage.json
  sections[2].title: required
.deco/blocks/Promo.json
  unknown block type "promo-banner"
```

Run it on every pull request as a required check; the workflow is in [Backward compatibility](/next/schema#backward-compatibility). It also runs in `prebuild` (see [Run it before dev and build](#run-it-before-dev-and-build)), so a build with broken content fails instead of deploying.

## `deco serve`

```bash
deco serve [--root <dir>] [--port <n>] [--host <addr>] [--app-url <url>] [--token <t>] [--allow-origin <origin>]… [--assets <dir>] [--read-only]
```

`deco serve` is the local server Studio uses to edit the files on your machine, over the [content protocol](/next/content-protocol): it reads and writes `.deco/blocks`, reads `.deco/schema.gen.json`, and accepts uploads into `.deco/assets/` (or `--assets`). It tells Studio which root it serves through the content protocol's `describe`. See [Edit on your machine](/next/content-protocol#edit-on-your-machine) for the flow. It takes:

- `--root <dir>`: the folder that contains `.deco/`, such as `apps/storefront` in a monorepo. By default, it walks up from the current folder to the first folder with a `.deco/`, like every command.
- `--port <n>`: the port to listen on (default 4545).
- `--host <addr>`: the address to listen on. The default is 127.0.0.1; any other address prints a warning, because the server would be reachable from other machines.
- `--app-url <url>`: your dev app, which Studio's canvas opens. By default, the port from your Vite config, else `http://localhost:5173`.
- `--token <t>`: a fixed token instead of a random one per run (or `DECO_SERVE_TOKEN`).
- `--allow-origin <origin>`: another browser origin allowed to call the server, besides Studio's (repeatable).
- `--assets <dir>`: the folder Studio's uploads are written to, relative to the folder that contains `.deco` (default `.deco/assets`). The field always stores `/assets/<name>`, whatever this folder is, so point it at a folder your app serves at `/assets/`, such as `public/assets`; see [Images and other uploads](/next/content-protocol#images-and-other-uploads).
- `--read-only`: serve the content without accepting writes or uploads.
