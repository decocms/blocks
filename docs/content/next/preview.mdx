# Preview

Previewing a content change means rendering the same code against different content. Block *functions* ship with your app and only *content* changes, so a preview never needs different code: it needs your app pointed at the changed files. A **draft** is a content change that isn't on your production branch yet, kept on a branch until someone merges it.

## Preview locally

Your dev app already renders your working tree. Each file in `.deco/blocks` is an ordinary import of the content module, so editing one reloads through your framework's hot module replacement (HMR), and the running CMS gets the new content (see [The `deco content` command](/next/blocks#the-deco-content-command)). Change a file, by hand, with an agent or in [Studio](/next/how-it-works#studio), and the page in your browser shows it.

To edit through Studio's forms instead of JSON, run [`deco serve`](/next/cli#deco-serve) beside your dev server. Studio writes the files in your working tree, and its canvas opens your dev app with `--app-url`, so each save shows up on the real page (see [Edit on your machine](/next/content-protocol#edit-on-your-machine)).

```bash
npm run dev                                                # your app, on http://localhost:3000
npx @decocms/blocks serve --app-url http://localhost:3000  # Studio edits .deco/blocks; the canvas opens your app
```

Nothing is committed. Review the diff and commit it when the page looks right.

## Drafts are branches

A content change is a change to files, so it gets the review flow your code already has. Commit it on a branch and open a pull request: reviewers read the diff of `.deco/blocks`, and CI runs `npx @decocms/blocks schema && npx @decocms/blocks check`, which validates the saved blocks against the schema in the same pull request (see [Backward compatibility](/next/schema#backward-compatibility)).

To let others see the draft rendered, use your host's preview deployments. Each branch builds its own app, and `prebuild` runs `deco content`, so each preview bundles that branch's content module and serves exactly the content on that branch, at its own URL:

```bash
git switch -c summer-sale
# edit .deco/blocks/SummerSale.json, by hand or with deco serve
git add .deco/blocks && git commit -m "Summer sale page"
git push -u origin summer-sale
# open a pull request; the preview deploy renders /summer with the branch's content
```

Merging the pull request publishes the draft: the next production deploy ships it (see [Releases and deployment](/next/releases-and-deployment#publishing)). A content-only branch and a branch that also changes a block function preview the same way, which is how you check a new field and the content that uses it together.

<Hosted to="/next/hosted-drafts">**Drafts on your real site.** With the hosted Deco CMS, Studio opens your real site with a `?__draft=` link and the draft renders in place, with no preview deploy.</Hosted>

## Clients for drafts

Previewing a branch needs no code: you never call `cms.forDraft(pointer)` for it. `forDraft` hands a draft pointer to a [loader's](/next/api-reference#loaders) `load(pointer)`; a loader you write can serve drafts that way, and the content module ignores the pointer and serves its release (see [Draft pointers](/next/api-reference#draft-pointers) and, for the hosted flow, [Drafts on your site](/next/hosted-drafts)).
