# Studio and the content protocol

[Studio](/next/how-it-works#studio) edits your content without running your code. It reads and writes your files through a small protocol, the **content protocol**, so Studio works on the files on your machine or, through the hosted Deco CMS, on your GitHub repository.

<Callout>**Status.** The content protocol, its package and `deco serve` are proposed and not built yet. See the [Roadmap](/roadmap#roadmap-blockers--let-studio-talk-to-a-next-major-site).</Callout>

## What Studio needs

- **The schema**, `.deco/schema.json`, generated from your types (see [Schema](/next/schema)). Studio only reads it: no editor action changes it. To change a form, change the type and run `npx @decocms/blocks schema` again.
- **The saved blocks**, one JSON file per block in `.deco/blocks` (see [Blocks in your repository](/next/blocks#blocks-in-your-repository)). This is all Studio writes.

The `.deco` folder can be anywhere in the repository, such as `apps/storefront/.deco` in a monorepo. Studio needs no deployed site, and your app serves nothing for it: no endpoints, no handlers. A project with only a schema and a content folder can be edited before its first deploy.

## Where edits go

  <FlowNode title="Storage">Your working tree, or your GitHub repository</FlowNode>
</Flow>

Two implementations serve the protocol:

| Backend | Edits | Studio checks for changes |
|---|---|---|
| **[`deco serve`](/next/cli#deco-serve)**, from the Deco CLI | The files in your working tree. Your app hot-reloads after each save, and you commit when you're ready. | About every 2 seconds |
| **Studio's GitHub backend**, part of the hosted Deco CMS | Your repository on GitHub, with draft branches and publishing. | About every 30 seconds |

There's no event stream. Studio polls with one batched request, and when nothing changed the answer is a short "not modified". Saving is last-writer-wins in this version: if two people edit the same saved block at once, the later save replaces the earlier one.

<Hosted to="/next/hosted-studio" label="Editing in Studio on GitHub">**Edit without a local copy.** With the hosted Deco CMS, Studio's GitHub backend commits each save to a draft branch, and publishes by bringing the draft to your production branch, so editors need no copy of the code, dev server or Git.</Hosted>

## Edit on your machine

1. Start your app's dev server.
2. Run `npx @decocms/blocks serve`. It finds the nearest `.deco` folder (or takes `--root`) and prints its address, a bearer token and a connect link:

   ```text
   Deco server          http://127.0.0.1:4545/rpc
   Root                 apps/storefront/.deco   (schema.json, 214 blocks)
   Assets               apps/storefront/.deco/assets   (PUT /assets/<name>)
   App preview          http://localhost:5173
   Connect Studio       https://<studio-origin>/connect#endpoint=…&token=…
   ```

3. Open the link and pick the site in Studio to edit. Editing on your machine is planned to need no Deco account: without one, the link opens a play workspace in Studio, which isn't built yet (see the [Roadmap](/roadmap#roadmap-platform--add-a-play-workspace-for-local-editing)).
4. The first time, Chrome asks whether Studio may reach a server on your machine (Local Network Access, formerly Private Network Access). Allow it.

Each save writes `.deco/blocks`. Editing an existing file hot-reloads through your framework. The server also regenerates the content module when a save adds or removes a file, and after every save on Next.js, so you don't need `deco content --watch` as well. The canvas opens your dev app (`--app-url`). Nothing is committed: review the diff and commit it like any other change.

The server listens on 127.0.0.1 unless you pass `--host`, answers only requests that carry its token, and accepts browser requests only from Studio's origins. What it serves (your content, your schema and upload URLs) and its options are in the [`deco serve` reference](/next/cli#deco-serve).

### Images and other uploads

When an editor uploads an image or another file in Studio, `deco serve` writes it into your repository, in `.deco/assets/`, and the field stores the file's path, such as `/assets/summer-banner.jpg`. Like your entries, uploads are ordinary files: you review them and commit them with the rest of your content.

<Callout>**Status.** Uploads with `deco serve` are proposed and not built yet. See the [Roadmap](/roadmap#roadmap-cli--store-uploads-in-the-repository-with-deco-serve).</Callout>

The field always stores `/assets/<name>`, whatever folder the files are written to, so your app has to serve that folder at `/assets/`. Nothing serves `.deco/assets` by default: a field pointing there shows a broken image until your app serves the folder. The simplest way is to write uploads into the folder your app already serves. Vite, TanStack Start and Next.js all serve `public/` at the site root, so with

```bash
npx @decocms/blocks serve --assets public/assets
```

uploads land in `public/assets/` and are served at `/assets/`, in development and in production, with no other configuration: the build copies `public/` into its output. The folder is relative to the folder that contains `.deco` (see `--root` in the [`deco serve` options](/next/cli#deco-serve)), so in a monorepo it's your app's own `public/`. If you keep the default `.deco/assets`, you have to serve it at `/assets/` yourself and make sure it ships with your build, which it doesn't on its own.

With Vite, `public/assets/` ends up in the same `dist/assets/` folder as the build's hashed JavaScript and CSS. That's safe: the server never reuses a file name, so an upload's address always means the same file, and hosts that cache `/assets/*` for a long time serve it correctly.

Uploads make your repository bigger: every clone carries every image, and a replaced image stays in the history. Keep uploads small, for example by resizing and compressing images before you upload them, and link large media such as video from wherever you host it instead of uploading it.

<Hosted to="/next/hosted-studio#uploads" label="Uploads in hosted storage">**Uploads without growing your repository.** With the hosted Deco CMS, Studio stores uploads in Deco's asset storage and saves their CDN address in the field, so images are served from a CDN and never enter your repository.</Hosted>

## Features that need your site's code

Forms, variants and their rules, pages and redirects need only the schema and the files, so they work the same as on the legacy path. Uploads work too: they're stored in your repository with `deco serve` (see [Images and other uploads](#images-and-other-uploads)) and in Deco's asset storage with the hosted Deco CMS. A few features ran your site's code; without it they degrade:

| Feature | In this version |
|---|---|
| Block previews: gallery thumbnails, saved-block previews, in-place renders | A card with the block's name, its `@title` and description, and the `@image` thumbnail if the schema has one. The main canvas opens the real page: your dev app with `deco serve`, or, with the hosted Deco CMS, your deployed site showing the draft (see [Drafts on your site](/next/hosted-drafts)). |
| Pickers whose options come from your code | The options declared in the schema, else a text field. `deco schema` writes static lists into the schema (string-literal unions, enums and `@options` lists), so those stay selects; see [Widgets](/next/schema#widgets). |
| Secret and password fields (`@format password`) | Read-only. Keep credentials in environment variables, never in content. |
| Running a loader or action from Studio, and installing apps from the store | Unavailable. A platform client is added in code (see [Upstream API clients](/next/upstream-clients)). |
| Studio screens that find a type by name: pages, variants, hiding a block | Keep working with short type names, through the alias table the CLI writes into the schema (see [Studio compatibility](/next/studio-compatibility#well-known-types-and-the-alias-table)). Redirects are still saved in the legacy shape; see [Studio compatibility](/next/studio-compatibility#well-known-types-and-the-alias-table). |

Sites on Fresh and Deno keep Studio's legacy path, where Studio reads from the running site. v7 sites commit `.deco/meta.gen.json`, so they can use either path: the protocol edits without the site running, and the legacy path keeps runtime previews and running loaders. A project setting in Studio picks one (see [Legacy endpoints](/next/studio-compatibility#legacy-endpoints)).

## The protocol in brief

The content protocol is JSON-RPC 2.0 (a small standard for calling named methods with JSON) over one HTTP endpoint, `POST /rpc`, and a request can batch several calls. It has four methods:

| Method | Does |
|---|---|
| `describe` | What this endpoint is: whether it writes git commits or a working tree, where the `.deco` folder is, its limits, and how often to poll |
| `schema.get` | Reads the schema. There's no method that writes it. |
| `blocks.list` | Reads every saved block at once, with a revision for the whole set |
| `blocks.apply` | The only write: sets and deletes saved blocks together, all or nothing, optionally only if a block is still at a given version |

Both reads take the version they already have and answer "not modified" when it's current, which is what makes polling cheap. Studio and the CLI share one implementation, proposed as `@decocms/blocks-protocol`: the method types, a client, a server core over a storage interface, and a filesystem storage. The methods, errors, limits and file-name rule are [under the hood](/next/studio-compatibility#the-content-protocol).
