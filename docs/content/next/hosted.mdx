# The hosted Deco CMS

Your editors want a fix live within seconds, without waiting for a build, and they want to edit without cloning the repository. That's what the hosted Deco CMS is for: an optional service Deco runs on top of the same files. It changes how fast content reaches visitors and where editors work, not how your code is written.

The Deco SDK and CLI are complete without it: your functions, your content files and your deploys are all you need. This page shows what the hosted Deco CMS adds and how to connect your site.

## What it adds

Deco runs these services for a connected site:

| Service | What it changes | Without it |
|---|---|---|
| **Studio on GitHub** | Editors use [Studio](/next/how-it-works#studio) on your GitHub repository, with nothing to clone or install: each save is a commit on a draft branch, and publishing brings it to production. Uploads go to Deco's asset storage and are served from a CDN. See [Editing in Studio on GitHub](/next/hosted-studio). | Studio on your machine through [`deco serve`](/next/cli#deco-serve), and you commit the changes ([Edit on your machine](/next/cli#edit-on-your-machine)); uploads are files in `.deco/assets/` or the folder you pass with `--assets` ([Images and other uploads](/next/cli#images-and-other-uploads)). |
| **Drafts** | The Deco API serves an editor's draft to your real site, so Studio previews it in place. See [Previewing drafts](/next/hosted-drafts). | Drafts are branches you preview with your own preview deploys ([Releases and drafts](/next/releases-and-drafts#on-a-branch)). |
| **Publishing** | The Deco API serves each commit to your production branch as a **release**, so content is live within seconds without a deploy. See [Publishing without a deploy](/next/hosted-publishing). | Content ships with your next deploy ([Deployment](/next/releases-and-deployment#publishing)). |
| **Telemetry** | Sampled upstream latency and error rates for your site, collected by Deco, switched on and off from a content entry. See [Telemetry](/next/hosted-telemetry). | Nothing is sent, and the Telemetry entry is inert (see [Measuring upstream calls](/next/caching-and-observability#measuring-upstream-calls)). |

## What stays the same

- **Your repository is the source of truth.** Content is still the JSON files in `.deco/blocks`, and every edit is still a commit.
- **Your code doesn't change.** Block functions, the [block map](/next/blocks#the-block-map), [`resolve`](/next/api-reference#client-resolve-target-options), [`list`](/next/api-reference#client-list-type-options) and [routing](/next/routing) work the same way. The same [`createCMS`](/next/api-reference#createcms-config) call takes two more options, `site` and `token`.
- **The content module stays.** Your build still bundles [`.deco/blocks.gen.ts`](/next/blocks#the-deco-content-command). It's what a server serves before it has fetched its first release, and what it keeps serving if the Deco API is unreachable.

## Connect your site

A site is connected by two values: its **site ID** in the hosted Deco CMS and its **site token**. Read them from environment variables, by convention `DECO_SITE` and `DECO_SITE_TOKEN`, and pass them to `createCMS` next to your content:

```ts title="cms.ts"
import { createCMS } from "@decocms/blocks";
import blocks from "./.deco";
import content from "./.deco/blocks.gen";

export const cms = createCMS({
  blocks,
  content,
  site: process.env.DECO_SITE,          // your site's ID in the hosted Deco CMS
  token: process.env.DECO_SITE_TOKEN,   // your site token (secret)
});
```

The site ID isn't a secret; the token is, so keep it out of the repository. When either value is undefined, in development or in tests for example, the CMS reads `content` only and sends nothing, exactly like `createCMS({ blocks, content })`. So the same line works everywhere, and a site keeps working if you disconnect it.

Releases and telemetry follow from these two values with nothing else to configure. Drafts need a few lines of wiring in your app; see [Wire drafts into your app](/next/hosted-drafts#wire-drafts-into-your-app). How often servers check for a release is the `interval` option of `createCMS`; see [Check interval](/next/hosted-publishing#check-interval).

### Next.js

Set `DECO_SITE` and `DECO_SITE_TOKEN` in your host's environment (and in `.env.local`, which you keep out of Git, to try it locally). Create the CMS in a module that starts with `import "server-only"`, or import it only from one that does, as the [Next.js guide](/next/nextjs) does: the build then fails if a Client Component imports it, which keeps the token out of the browser.

### Cloudflare Workers

On Workers, environment variables come from `env` in `cloudflare:workers`:

```ts title="src/cms.ts"
import { createCMS } from "@decocms/blocks";
import { env } from "cloudflare:workers";
import blocks from "../.deco";
import content from "../.deco/blocks.gen";

export const cms = createCMS({ blocks, content, site: env.DECO_SITE, token: env.DECO_SITE_TOKEN });
```

Locally, `wrangler dev` reads them from a `.dev.vars` file you keep out of Git. In production, set the site ID as a plain variable in `wrangler.jsonc` (`vars`) and the token as a secret:

```bash
npx wrangler secret put DECO_SITE_TOKEN
```

Release checks on Workers run after the response, inside `ctx.waitUntil`, on their own; see [How a commit becomes a release](/next/hosted-publishing#how-a-commit-becomes-a-release). Sites with several megabytes of content should read [Large content on Workers](/next/hosted-publishing#large-content-on-workers).

## Terms

<Terms>
  <Term name="Site ID and site token">The two values that connect your app to the hosted Deco CMS, usually the `DECO_SITE` and `DECO_SITE_TOKEN` environment variables, passed to `createCMS` as `site` and `token`. They load releases and drafts and send telemetry. Only the token is secret.</Term>
  <Term name="Deco API">The HTTP service that serves your site's releases and drafts, and receives its telemetry.</Term>
  <Term name="Release">A [release](/next/releases-and-drafts#releases) as the Deco API serves it: the content of one commit to your production branch, live without a deploy. See [Publishing without a deploy](/next/hosted-publishing).</Term>
  <Term name="Draft pointer">The string Studio puts in a `?__draft=` link: where a draft lives on the Deco API, with a token Studio signed, and which version. [`cms.forDraft(pointer)`](/next/api-reference#draft-pointers) reads it. See [Previewing drafts](/next/hosted-drafts).</Term>
  <Term name="Draft branch">The branch Studio's GitHub backend commits an editor's saves to, created on the first save. Publishing brings it to your production branch. See [Editing in Studio on GitHub](/next/hosted-studio).</Term>
</Terms>
