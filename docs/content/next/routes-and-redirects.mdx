# Routes, redirects, and content types

A **content type** is a block type whose entries you save and list, such as a page, a blog post or a redirect; this page calls it that, but it's an ordinary block type. Its name is the value of `__resolveType`. `page` and `redirect` are [built-in blocks](/next/blocks#built-in-blocks), and `deco schema` always includes their schemas. Your own types, like `post`, are blocks too, declared in your block map (see [Data-only blocks](/next/schema#data-only-blocks)). The framework also ships the `Route` interface, which any content type can extend to get a URL.

```ts
/** An entry that lives at a URL. Extend it to make a type routable. */
interface Route {
  /** @title Name */
  name: string;
  /** @title Path */
  path: string;        // "/summer", or a template like "/:slug/p"
}

/** A saved block of the built-in `redirect` content type. */
interface Redirect {
  from: string;        // literal or template
  to: string;
  permanent: boolean;  // 301 or 302
}
```

A page is a route with SEO and a list of [blocks](/next/blocks) (its `sections` field). It's not special to the router: it's the first type that extends `Route`. A saved page carries `"__resolveType": "page"` so the CMS can list it by type, plus a `name` and `path`, so the router can find it. It's built in, so you don't declare it. To add fields, override it in your block map with `page: (props: StorePage) => props`, where `interface StorePage extends Page { … }` (see [Override a built-in](/next/schema#override-a-built-in)). It's exported from `@decocms/blocks`:

```ts
/** The built-in `page` content type. */
interface Page extends Route {
  seo: Seo;
  sections: ReactNode[];
}
```

Each field is typed as what the page receives, already resolved: a `Seo` object and a list of rendered blocks ([how Studio fills them](/next/schema#from-types-to-forms)). In the saved JSON below, `seo` is a block and `sections` is a list of blocks.

```json title="Saved as SummerPage"
{
  "__resolveType": "page",
  "name": "Summer campaign",
  "path": "/summer",
  "seo": { "__resolveType": "SummerSEO" },
  "sections": [
    { "__resolveType": "hero", "title": "Summer starts here", "image": "https://cdn.example.com/summer.jpg" }
  ]
}
```

```ts
// What client.resolve("SummerPage") returns: the built-in page block resolves seo and every block in sections.
{
  name: "Summer campaign",
  path: "/summer",
  seo: seo({ title: "Sunny!", description: "Light layers for long days." }),   // SummerSEO, expanded
  sections: [hero({ title: "Summer starts here", image: "https://cdn.example.com/summer.jpg" })],
}
```

```json title="Saved as LegacySummer"
{
  "__resolveType": "redirect",
  "from": "/campaigns/summer",
  "to": "/summer",
  "permanent": true
}
```

Two SDK functions turn these entries into URLs. `client.list("page")` returns every saved block whose `__resolveType` is `page`. `matchRoute(url, { routes, redirects })` picks the entry that matches a URL. [Routing](/next/routing) puts them together.

**The router's rule is one line: an entry with a string `path` matches at that path.** `Route` is what makes that intentional. The CLI checks that any type declaring `path` extends `Route`, so a stray `path` field on an unrelated block is a schema error rather than a surprise URL. Editors see `name` and `path` as ordinary fields on every routable thing, in [Studio](/next/how-it-works#studio), which is how a marketing team gets `/summer-sale` live without a developer. Keep `path` and `from` plain strings, not blocks, so the router can match without running code.

## Your own routable types

A blog doesn't want a `page` entry per post. Make `Post` extend `Route`, declare it in your block map as `post: (props: Post) => props`, and pass the saved posts to `matchRoute` along with your pages (see [Routing](/next/routing)). Each post is then served at its own `path`:

```ts title="src/post.ts"
import type { Route } from "@decocms/blocks";

export interface Post extends Route {
  /**
   * @title Published on
   * @format date
   */
  date: string;
  /** @format rich-text */
  body: string;
}
```

```ts title=".deco/index.ts"
const post = (props: Post) => props;   // data only: returns what the editor saved
export default { seo, hero, post } satisfies Blocks;
```

The function just returns what the editor saved (see [Data-only blocks](/next/schema#data-only-blocks)).

```json title="Saved as HelloWorld"
{ "__resolveType": "post", "name": "Hello, world", "path": "/blog/hello-world", "date": "2026-09-01", "body": "…" }
```

Two entries with the same path, or two templates that can match the same URL, are rejected by the CLI and by `matchRoute` (see [Path templates and match order](/next/routing#path-templates-and-match-order)).

## Resolving pages and redirects

`page` and `redirect` are [built-in blocks](/next/blocks#built-in-blocks): `client.resolve("SummerPage")`, or `client.resolve(match.entry)` after routing, returns the page with `seo` and every block in `sections` resolved. That's the simplest way to render a page; to send each block as soon as it's ready instead, see [Stream each block](/next/nextjs#7-stream-each-block-optional). `matchRoute` reads redirects as listed, so routing never needs to resolve them.

Your own types work the same way: `client.resolve("HelloWorld")` returns the post with any blocks inside it resolved, and `client.list("post")` lists every saved post.

## Content types without a URL

Navigation, email templates, and campaign settings work the same way, minus `Route`: declare a function in your block map, such as `menu: (props: Menu) => props`, then save entries with `"__resolveType": "menu"`.
