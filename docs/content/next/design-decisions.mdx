# Design decisions

Each of these was argued over. The one-line version, and why it won.

| Decision | Why |
|---|---|
| **The CMS is pure.** A block function gets its inputs and nothing else. | No context object means block functions are ordinary functions you can call and test, and the same code runs in a website, a mobile app, or a background job. Request state comes from your framework's own request scope, where it already lives. |
| **Git is the source of truth for content.** Publishing is committing: a deploy ships the commit, or the hosted Deco CMS serves it as a release without one. | History, review, branches, and rollback come for free, and agents can edit content with the tools they already have. There is no publish command because there is nothing to publish that a commit doesn't already express. `deco publish` exists only as a signpost for AI agents: it prints this explanation and exits, so an agent that tries it learns to commit instead. |
| **A block is either a function (code) or saved content (JSON).** One namespace: an entry is merged in and checked again; a function gets its inputs resolved, then runs, and its result is returned as is. Built-in functions such as `page` share the same namespace, under yours. | Saved blocks are named compositions, not a second concept. A function that returns its input, like `seo`, can't loop, because results are never looked up again. The only recursion is over saved blocks, and a cycle check stops it. |
| **The CMS at module scope, a client per request, pinned to one revision.** | Everything a response renders agrees with itself, a page's blocks can be resolved and streamed to the browser one at a time, and the next request sees the next revision. Clients are cheap because the content cache lives in the CMS, shared by every client. |
| **`content` is a snapshot or one `Loader` interface**: `load(pointer?)`, plus an optional `update()`. | Production, drafts, and staying current are uses of the same interface, so the content module and `remoteLoader` replace each other in one option, and the rest of your code never knows which one it has. |
| **A production request never waits for the network.** | Requests read content from memory. A content source that can change is checked with `update()` at idle moments, never in front of a request. |
| **The CMS doesn't route.** `matchRoute` is a helper over entries you list. | Which types have URLs is an app decision, a non-website has none, and the framework's file-system router still owns code routes. Editors get pages at arbitrary paths because the path is a field. |
| **`page`, `redirect` and `telemetry` are [built-in blocks](/next/blocks#built-in-blocks); everything else, data included, is a function in your block map.** `deco schema` reads only the default export, and every key gets its schema from its function's first parameter. | One list of names for the CLI and the CMS, so a type that has a form always resolves. Data-only types such as posts use a function that returns its input (`(props: Post) => props`), so there's no second, type-level map to keep in sync. The framework spreads its built-ins under your block map, so pages and redirects are always in the schema and always resolve, and a page resolves to its ready, fully resolved form. Almost every website needs them, and Studio's page list and redirects screen look for them. A key in your map overrides one, such as `page: (props: StorePage) => props` with `StorePage extends Page`. |
| **Lazy loading belongs to your web framework, not the CMS.** | What's heavy is the component, and React and Next.js already load components lazily. The block map stays a plain object the CLI can read. |
| **Three matchers ship; the rest is app code.** | `always`, `never`, and `date` depend on nothing but the clock. A device or cookie matcher is an opinion about the request, and the app owns those. |
| **Short type names; aliases for the old file-path names.** | A type name is a column name, not a file path. Content saved under the Fresh and Deno and v7 names, like `website/pages/Page.tsx`, keeps working through aliases, while new code uses names that survive a refactor. |
| **Packages export TypeScript source and depend on each other in one direction.** | Bundling one package into another can leave two copies of a module that must be one, like the block registry. Importing source keeps one copy, and the one-way graph keeps the core free of framework code. Instances also live on `globalThis`, so a module loaded twice still shares one cache and one poller. |
| **The SDK never touches the filesystem.** | One setup for every runtime: Node, Workers, Deno, Bun, React Native and browsers. The CLI turns files into a module, and your framework's hot module replacement gives hot reload. |
| **The CLI ships inside `@decocms/blocks`.** It's the package's single bin, `deco`. | One install, and the CLI's version can't drift from the runtime's. The CLI never reaches an app bundle: apps don't import its subpath, and `typescript` loads only when a command runs (see [How the CLI ships](/next/internals#how-the-cli-ships)). |
| **Three CLI commands, no dev wrapper.** | `deco schema` and `deco content` each do one job and run from `predev` and `prebuild`. Both take `--root` and `--watch`; `deco schema` also takes `--entry`, for a block map outside the default locations, and `--check`, for CI. [`deco serve`](/next/cli#deco-serve), the third, is the only server, and you run it only while you want Studio on your working tree. |
| **Studio needs only the schema and the files.** It reads the schema, reads and writes `.deco/blocks` through a four-method [content protocol](/next/content-protocol), and never runs site code. | Editing doesn't depend on a deployed, reachable site, a `.deco` folder can live anywhere in a monorepo, and one editor works on GitHub and on a local checkout. Features that ran site code (previews in Studio's gallery, dynamic pickers, Run, secret encryption) degrade in this version; the running site remains the preview: your dev server, a preview deploy, or, with the hosted Deco CMS, a `?__draft=` link. |
| **Poll with conditional reads; no event stream.** | One batched request that answers "not modified" when nothing changed costs a few bytes, needs no reconnect logic, and works through any proxy. Two seconds locally and thirty on GitHub is fast enough for an editor watching their own edits. |
| **The framework doesn't fetch data.** Platform integrations are thin, instrumented [API clients](/next/upstream-clients); there's no `/deco/invoke` and no `cachedLoader`. | Data fetching is the part of a site that differs most between platforms and frameworks, and frameworks already have server functions and route handlers for it. Thin clients keep every call measured the same way while converters, hooks and flows live in templates the site owns. Caching depends on the platform, so it lives in the bindings. |
| **Telemetry is hosted-only, and its settings are content.** One well-known entry, `Telemetry`, sampled errors, aggregated metrics, sent only to the hosted Deco CMS, with a site ID and token. The framework sends nothing on its own; teams that want their own observability instrument their code with OpenTelemetry. | Switching telemetry off is a content edit: a commit to the entry (from Studio on GitHub or by hand), and with hosted releases running servers pick it up with their next content check, without a deploy or a separate channel. Editors can see what's sent. Sampling and aggregation keep the cost flat as traffic grows. OpenTelemetry is already the standard for your own tracing, so the framework ships no second export path. |
| **Compatibility is a CI check, not a runtime gate.** | Content and code merge independently, and with the hosted Deco CMS content goes live without a deploy, so code that's already live must render new content; holding content back until a deploy would undo that. `deco schema --check`, part of the first release, flags a code change that would break saved content before it merges. Studio reads the schema committed on the branch it edits, falling back to your default branch when that branch has none. |
| **Hosted releases: poll a hash once a minute, at idle moments; no push.** | A few bytes per server per minute, no infrastructure to reach every server, and never in front of rendering. Until the first release arrives, or if the Deco API is unreachable, a server keeps serving the content the build shipped with or the newest release it has. Eventual consistency for visitors, strict consistency for drafts. |
