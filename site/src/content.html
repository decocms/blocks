How it works

Deco Blocks has two pieces you install, and one you don't:

You write functions with typed inputs, for example a hero section that takes a title and an image. The CLI turns those types into a schema, and Studio turns the schema into forms. Editors, and AI agents, save content as JSON files in .deco/blocks, in your repository.

Delivery: from files to your app

Your appNext.js, TanStack Start, or any server

At request time, the SDK reads that content through a loader (by default, those same files), follows references between entries, and runs each block through the function you mapped to its type in your block map. What you render, and how, is up to your framework.

With the hosted Deco CMS, production reads the same content from the Deco API instead of disk, but a request never waits for it: content is served from memory and refreshed in the background, and the files the build shipped with are always there as the fallback. See how the loader stays current.

Small on purpose

Deco Blocks stays out of your way, and every piece is replaceable:

  • Content is plain JSON. Open it in any editor, grep it, diff it, or generate it with a script. There's no database and no content API to run.
  • Blocks are plain functions. No framework plugin, no base classes, no magic directories. The block map is a plain object, and you can call any block function directly in a test.
  • Loaders are one method. Loading from the filesystem, KV, or your own store is a load() that returns { revision, blocks }. Swap it and nothing else changes (see Content and loaders).
  • The schema is a file. Commit it, inspect it, or generate it another way. Studio only needs the JSON.
  • Nothing is hidden. If the SDK doesn't do what you need, read the files yourself. The format is documented in Blocks.

Getting started

Quickstart

Suppose your app has a function that decides which A/B tests a visitor sees. It takes the traffic split for each experiment and returns whether each one is enabled:

The split is hardcoded at the call site. Ramping the new checkout from 10% to 25% means a pull request and a deploy. In this guide you'll move those numbers into content that your team edits in Studio, and that AI agents edit as files, while the function stays exactly as it is. It runs in plain Node, with no framework.

Prerequisites: Node.js 22 or later and a way to run TypeScript, such as tsx.

npm install @decocms/blocks

1. Make the function configurable

Any function with a typed first parameter can be a block. Give it a name in a block map. The key, experiments, is the block type that content will refer to. This file is plain data: the CLI reads it, and your app hands it to createCMS.

2. Give editors a form

The CLI reads the map and turns the Experiments type into a JSON Schema. The JSDoc tags become labels and validation. Studio builds the editor form from it:

npx deco schema --entry ./blocks.ts --out ./.deco/schema.json

Commit the file. From now on, Studio shows each experiment as a number field clamped to 0–100.

3. Add content

There are two ways to create content, and they produce the same thing:

  • In Studio. Open the editor, pick the experiments block type, fill in the form, and save. Studio writes the JSON file into your repository.
  • Manually. Create the JSON file yourself, or let an AI agent asked to "ramp the new checkout to 25%" do it. Either way the result is the same file, so both routes are equivalent.

Either way, the file lands in .deco/blocks, which is where the CMS reads content from by default. The filename is the entry's name, and __resolveType is the block type:

4. Read the content from your code

Create the CMS once with your block map. It reads the .deco directory by default, so there's nothing else to configure (to read it from somewhere else, or connect the hosted Deco CMS, see Configuring the loader). Ask it for a client, then fetch the entry by name. The client runs experiments on the saved inputs, so you get the same result as the direct call, with the same type:

Every call returns a [value, error] tuple, so a missing entry or a failing function never throws.

That's it. The function didn't change, but its inputs now live in a file that editors change through a form and agents change directly, and every change is a commit. A real implementation would hash a visitor ID from a cookie instead of rolling a die, so each visitor gets a stable result. The CMS doesn't hand blocks the request; read it the way the rest of your app does (see Block maps).

Core concepts

Blocks

Most of what changes on a website isn't the code. It's the values the code is given: a headline, a banner image, the share of visitors who see the new checkout. Deco is built on that idea: developers write the functions, and the people who run the site decide what goes into them.

Blocks are how they make those decisions. A block is a small piece of JSON that names one of your functions and lists the inputs to call it with. Editors change the inputs in Studio, and agents edit the file directly. When your app resolves the block, Deco calls the function with whatever is saved and gives you back the result. This page shows what a block looks like, how blocks fit inside each other, and exactly how they turn into values.

Start from code you already write

Here's the kind of code you write every day:

productCard({
  title: "Summer collection",
  product: catalogProduct({ slug: "summer-shirt" }),
})

It's function composition. The inner call runs first, and its result becomes an input to the outer one, so productCard receives product data, never a pending call. The functions are the developer's job. The composition is a decision: which product, which title, which function fetches the data. Written in code, changing that decision means editing code and deploying it.

A block is that composition, stored as data

Write the same composition as JSON and nobody has to edit code to change it. __resolveType names the function, the other properties are its inputs, and a block inside an input is a call inside a call. Here productCard and catalogProduct are the functions your map registers as "product-card" and "catalog-product":

// Stored as JSON
{
  "__resolveType": "product-card",
  "title": "Summer collection",
  "product": { "__resolveType": "catalog-product", "slug": "summer-shirt" }
}

// Means
productCard({
  title: "Summer collection",
  product: catalogProduct({ slug: "summer-shirt" }),
})

Now an editor can change the title or the slug in Studio, and an agent can even point product at a different function, and the composition changes without a deploy. The functions are whatever your block map registers, and each one's input type is what deco schema turns into the editor form. Use the same model for anything your site needs: UI sections, product data, SEO, navigation, campaign settings. The CMS doesn't reserve any directories or categories.

Name a composition, reuse it

In code, you'd give a composition you use often a name and reuse it. Saved entries do that. Alongside the block map of functions, the CMS reads a second map, the content map, where each name holds a piece of saved JSON. { "__resolveType": "SummerSEO" } means whatever is saved under the name SummerSEO, written in place. The map can come from files in your repository, the hosted Deco CMS, or your own store; see Content and loaders.

Unlike a const that holds a result, what's named here is the call itself, inputs and all. That's why you can add inputs to a reference to override the saved block's inputs for this one use:

// Saved as SummerSEO
{ "__resolveType": "seo", "title": "Sunny!", "description": "Light layers for long days." }

// A reference to it, anywhere in your content
{ "__resolveType": "SummerSEO", "title": "Summer sale" }

// Means
seo({ title: "Summer sale", description: "Light layers for long days." })
  • Overrides are shallow. The merge is { ...entry, ...inputs }, so an override replaces the whole top-level property, and the saved entry itself doesn't change. It isn't currying or partial application: the reference is expanded into one complete call.
  • An entry doesn't have to be a block. It can be any JSON that contains blocks, like a page with a list of sections: an object literal with calls inside. Resolving it calls each block inside and leaves the rest of the JSON as it is.

Resolving a page, step by step

Resolving a block is evaluating its composition: named entries expand, then calls run from the inside out. Here's a page saved as pages-summer. It uses the SummerSEO entry with an override, and one Carousel section. The block map has two functions: seo returns its inputs, and Carousel returns a { component, props } descriptor.

// Saved as pages-summer
{
  "seo": { "__resolveType": "SummerSEO", "title": "Summer sale" },
  "sections": [{ "__resolveType": "Carousel", "banners": [] }]
}

Call client.resolve("pages-summer") and follow the page as it changes.

Step 1. The reference expands. SummerSEO is a saved entry, so it's data. The entry merges under the override, and its __resolveType now names a function.

{
  "seo": { "__resolveType": "seo", "title": "Summer sale", "description": "Light layers for long days." },
  "sections": [{ "__resolveType": "Carousel", "banners": [] }]
}

Step 2. The functions are called. What's left is a composition of plain calls. Both blocks have plain inputs, so both functions run. They're siblings, so neither waits for the other.

{
  seo: seo({ title: "Summer sale", description: "Light layers for long days." }),
  sections: [Carousel({ banners: [] })]
}

Step 3. The result. Each return value takes its block's place. The page itself was never a block, so its shape stays the same.

{
  seo: { title: "Summer sale", description: "Light layers for long days." },
  sections: [{ component: "Carousel", props: { banners: [] } }]
}

To step through a deeper example, see How resolution works.

Reading without running. Pass { resolve: false } to read content without calling any functions. client.resolve("pages-summer", { resolve: false }) stops after step 1: saved entries like SummerSEO still expand, and blocks that name a function, like seo and Carousel, come back as JSON, untouched. Nothing runs. That's useful for previews, editor tooling, and debugging. To read an entry exactly as stored, with its references left in place, look it up in the map your loader returns, for example (await localLoader("./.deco").load()).blocks["pages-summer"].

The rule

Every __resolveType is a name looked up in one registry, and a name is either data or code: a named composition to expand, or a function to call.

const registry = { ...savedEntries, ...blocks };   // name → saved JSON | function

Saved entries are the content map your loader returns. Functions come from the block map you give createCMS. The CMS applies one rule to every object with a __resolveType:

  1. Look up the name.
  2. Data: replace the object with { ...entry, ...inputs }, so your inputs override the entry's, and apply the rule to the result again.
  3. Function: resolve the inputs first, children before parents and siblings concurrently, then call the function. Its return value takes the block's place.
  4. Neither: fail with UNKNOWN_BLOCK.

The rule in detail

  • Failures stop the parent. If a nested block fails, its parent never runs and resolve returns the error, much as an outer call never runs when an inner one throws. A reference to an entry that doesn't exist fails with NOT_FOUND.
  • Results are opaque. The CMS never walks a function's return value. Return plain data, a descriptor, or JSX. This is also why a function that returns its input, like seo above, can't loop: __resolveType is stripped before the call, and whatever comes back is never looked up again.
  • Only data can loop. A data hit is the one branch that applies the rule again, so two entries that reference each other, or an entry that references itself, would recurse forever. The CMS tracks the entries expanded on the current path and fails with CYCLE the moment one repeats, with the chain in error.path.

Entry names and block types share one registry. If a name is both, the function wins, so a saved entry called seo and a seo function can't coexist. deco schema fails when an entry name matches a block type, so rename the entry.

Core concepts

Content and loaders

Resolving takes two maps. The block map holds your functions, and it ships with your code. The content map holds your saved entries: each name points at a piece of JSON. A loader supplies the content map, and it's the only part of the runtime that knows where content lives. Your functions, the resolver, and your pages never do. (This isn't the same thing as the data-fetching block functions some Deco apps call loaders, like catalogProduct in Blocks. Those are ordinary functions in your block map.)

A loader returns the whole map at once, with a revision that identifies it:

{
  "revision": "b1946ac92492d2347c6235b4d2611184",
  "blocks": {
    "SummerSEO": { "__resolveType": "seo", "title": "Sunny!", "description": "Light layers for long days." },
    "pages-summer": {
      "seo": { "__resolveType": "SummerSEO", "title": "Summer sale" },
      "sections": [{ "__resolveType": "Carousel", "banners": [] }]
    }
  }
}

Each key under blocks is an entry name. It's the name a __resolveType refers to, and the name you pass to client.resolve("SummerSEO"). Despite the field name, these are saved entries: any JSON, never functions. Functions only ever come from the block map you give createCMS. The revision names this exact set of entries, so any change to any entry must give a new revision. The built-in loaders use a hash of the whole map. How releases use it is in Releases and deployment.

Where content comes from

The content map can come from anywhere that can return JSON. These are the usual sources:

Content inLoaderUse it for
Files in your repository (the default)localLoader("./.deco"): one JSON file per entry in .deco/blocks; the file name without .json is the entry name (.deco/blocks/SummerSEO.json → "SummerSEO")Development, tests, and the fallback of remoteLoader in production

When you edit with Studio or an agent, content is authored as files: they write to .deco/blocks in your repository, and every change is a commit. The loader only decides where your app reads that content from at runtime. With the hosted Deco CMS, each commit becomes a release, a published version of your content that reaches your app without a deploy, and the files the build shipped with are the fallback (see Releases and deployment). If you load from your own store, how content gets there is up to you.

Configuring the loader

Most apps never pass a loader: createCMS reads the ./.deco directory by default. Pass an object to keep your content somewhere else, to connect the hosted Deco CMS, or both. These are shortcuts for the loaders in the table above: { root } is localLoader(root), and adding token wraps it as remoteLoader(localLoader(root), { token }).

token is the site's API key for the Deco API. Keep it in an environment variable, never in the repository. When it's undefined, in development for example, the CMS reads the files only, so the same line works everywhere. For anything else, such as content bundled into a Workers build or your own store, pass a Loader (see API reference).

Core concepts

Schema generation

Studio builds its editor from a JSON Schema, and the CLI writes that schema from your TypeScript. Point it at the file that exports your block map, the blocks.ts from the quickstart:

npx deco schema --entry ./blocks.ts --out ./.deco/schema.json

For each block type in the map, the CLI reads the type of the function's first parameter and turns it into a form definition. Commit .deco/schema.json with your code, and run the command in CI so the schema never drifts from your types.

The CLI also checks your content model: it fails if a saved entry's name collides with a block type, or if an alias collides with either.

Content that is only data

A page, a blog post, a redirect: these have a shape but no function. Nothing runs when they resolve; your app reads them and resolves the blocks inside them. They still need a schema so Studio can create them, so declare them for the CLI in a type-level map next to the block map:

The CLI reads both exports. Keys of the default export get a schema from each function's parameter type; keys of Content get one from the type itself. The two share one namespace, and a key in both is an error. The runtime never sees Content: list("page") works because the entries exist, and resolving a page means resolving its fields, not the page.

Studio reads the schema this command writes, and nothing else about your code. What it looks for, and how the CLI bridges today's Studio conventions, is covered under the hood.

There is no publish command. Content is published by changing it: commit a file in .deco/blocks and push, or save in Studio, which commits for you. Both land in the repository, and the Deco API serves the latest commit of the production branch as the current release. If an agent runs deco publish, the CLI only says this.

Core concepts

Preview

Editors want to see a change before it's published. Because block functions ship with your app and only content changes, previewing a draft needs no deploy: the app renders the same code against different content.

Here's the whole mechanism. Studio opens your site with a draft pointer in the URL:

https://store.example.com/summer?__draft=studio.decocms.com/api/acme/decofile/store/feat-summer%3Ftoken%3D…@9f3c1a

The pointer is a string, <host><path>@<version>: where the draft content lives, and which version. draftPointer(request) reads it, from ?__draft= or from the cookie described below, and the CMS gives you a client over that draft. Everything after that line is the same code that serves visitors:

forDraft hands the pointer to the loader. remoteLoader fetches that exact version from Studio's content API, waits for it, and caches it by version, so the second request for the same draft is a memory read. A draft replaces the whole revision, deletions included, so a page in preview looks exactly as it will after publishing. localLoader ignores the pointer: in development you're already looking at the files. That's why the code above never checks which loader it has.

Keep the draft across navigation

The pointer is only in the URL of the first page Studio opens. draftCookie(request) gives you the Set-Cookie value that response needs, and null on every other request. Append it, and draftPointer reads the cookie from then on, so every link the editor clicks stays in preview:

Studio ends a preview by opening the site with an empty ?__draft=; draftCookie returns an expiring cookie for that, so the same two lines cover leaving preview. The parameter and cookie names never appear in your code. In Next.js the two steps split across proxy.ts, which appends the cookie, and a server helper that reads it with cookies(). The Next.js guide has both files.

Not a website

forDraft takes the pointer string and nothing else, so nothing here assumes HTTP. A mobile app takes it from the deep link Studio opens, or from a "preview" field on a debug screen, and keeps it in app state:

// React Native, on a deep link like mystore://preview?__draft=...
const pointer = new URL(url).searchParams.get('__draft')
setClient(pointer ? cms.forDraft(pointer) : cms.forRelease())

A script passes it as an argument. To look inside a pointer, or build one from parts, use parseDraftPointer and formatDraftPointer from the reference; forDraft parses on its own, so normally you don't have to.

Who may preview

Two checks, and neither needs configuration in your app. remoteLoader uses its token to learn the site's content API from decocms, and forDraft ignores any pointer whose authority isn't that API, so a pointer can never turn into a request to an arbitrary origin. The pointer's path carries a signed grant that the content API verifies, so a draft is only served to someone Studio let in.

If a website wants to show drafts on its preview domain only, it checks the request's host before calling forDraft:

const host = new URL(request.url).host
const pointer = host === 'preview.store.example.com' ? draftPointer(request) : null
const client = pointer ? cms.forDraft(pointer) : cms.forRelease()

The token is the only secret. The site holds no other credential. Invalid or unexpected pointers are ignored and the request falls back to published content, never to an error page.

Advanced

Block maps

A block map is the code half of the registry: a plain object from block type to function. The quickstart's blocks.ts is one. This section covers what else can go in it.

Each key is a block type. Each value is a function (inputs) => value, where inputs is the block without its __resolveType, with nested blocks already resolved. Use satisfies Blocks rather than a type annotation: it checks the shape while keeping the concrete keys and function types, which is what makes resolve<T> inference and the schema work.

Keep the map a plain object at module level. The CLI reads the file without running it, so build it once and give it to createCMS. Only functions go in the map. Types that are pure data, such as pages, posts, and redirects, have nothing to run; they're declared for the CLI instead, see content that is only data.

The CMS is pure. It passes your function the block and nothing else: no context object, no request, no hidden state. When a block needs the current request, a cookie, or a route parameter, read it the way the rest of your app does, usually through the AsyncLocalStorage your server or framework already provides (next/headers in Next.js, getRequest() in TanStack Start). That keeps block functions ordinary functions you can call and test directly.

Lazy loading

The map above imports every block at the top, so they all load with the map. That's fine for functions like seo. It's not what you want for a section that drags in a charting library, or for the two hundred sections a large store has when any page uses five.

What's heavy is the component a block renders, and your framework already knows how to load components lazily. So do it in one place, the map, and let the block files stay plain components:

Swap dynamic for React's lazy on TanStack RSC, with the sections rendered under a Suspense boundary. In TanStack's data mode the blocks return descriptors and the browser-side view registry is the map to do this in: const views = { product: lazy(() => import('./sections/Product')) }. In every case the section files know nothing about the CMS, the map stays a plain object the CLI can read, and the bundler splits on the import().

For a block that's heavy for a non-UI reason, say a data function that pulls in a large SDK, a dynamic import inside the function body is enough. It's one line and needs no helper:

"catalog-product": async (input: ProductQuery) => {
  const { fetchProduct } = await import("./commerce")   // loaded on first call, cached by the runtime
  return fetchProduct(input)
},

Keep import paths literal in both cases. A bundler can split import("./sections/Product") into its own chunk; it can't split import(`./sections/${name}`).

Choose type names that last

A type name is what content stores in __resolveType, so pick it like a database column, not like a file path: short (seo, hero) or namespaced when a site has many (commerce/product). Moving a file only means updating an import; the name doesn't change. Renaming a type means migrating every block that uses it, or adding an alias.

Advanced

Matchers and variants

Editors often want content that depends on a condition: a banner that only shows during a campaign, a title that changes on a date, an experiment. Two small ideas cover all of it, and neither knows what a website is, so they work the same in a storefront, a mobile app, or a job.

A matcher is a block function that returns a boolean. A multivariate is a block function that takes a list of { rule, value } pairs, where each rule is a matcher, and returns the first value whose rule matched. Because the CMS resolves inputs before calling a function, the multivariate never sees a matcher, only booleans.

The three matchers that ship

They depend on nothing but the clock, so they're the only ones the framework provides:

import { always, never, date } from "@decocms/blocks/matchers";

// always()                              => true    the default rule of a variant
// never()                               => false   how Studio hides a section without deleting it
// date({ start?: string; end?: string }) => boolean, true when now is inside [start, end]

Everything else that could gate content, a device, a cookie, a country, a user's plan, depends on where your app runs and how it sees its environment. Those are yours to write, below.

The multivariate is three lines you own

Editors compose them in Studio: a variant is a tab, its rule is picked from the matchers in your map, and the first tab is the default. A hero whose title changes for a campaign is a hero whose title is a multivariate:

Resolution does the rest: each rule runs and yields a boolean, multivariate runs with those booleans and yields a string, hero runs with a plain title. Nothing in hero knows a variant was involved. The same shape wraps a whole section, or a page's whole sections array, which is how Studio does page-level variants.

Write your own matcher

A matcher is any block function that returns a boolean. It reads whatever your app knows about the current request or user the way every other block does, through the context your runtime already provides:

Add them to the map and Studio's rule picker shows them beside date: it lists every function in the manifest's matchers group, which the CLI fills with every block function that returns a boolean. Combinators are matchers too: and, or, and not are one-liners over booleans, if you want them.

Every variant resolves

Inputs resolve before a function runs, so every variant's value resolves before multivariate picks one. For a title that's free. For two product queries it isn't, and a failure in a variant you didn't pick still fails the whole thing.

The lazy form is to make the values entry names instead of inline blocks. A string isn't a block, so nothing runs; the multivariate returns a name, and whoever holds the client resolves it:

{
  "__resolveType": "multivariate",
  "variants": [
    { "rule": { "__resolveType": "date", "start": "2026-11-20", "end": "2026-11-30" }, "value": "BlackFridayHero" },
    { "rule": { "__resolveType": "always" }, "value": "DefaultHero" }
  ]
}
const [name] = await client.resolve(section);   // "BlackFridayHero"
const [hero] = await client.resolve(name);      // only this variant ran

A variant is not access control. It chooses between values that are all fine to compute and show. Never use one to guard protected data or to decide whether a side effect runs; put that check inside the function that does the work.

Anything a matcher looks at is a cache dimension. If a page varies by device, the device belongs in the cache key.

Websites

Routes, redirects, and content types

The framework ships two content types. Everything that has a URL is built from them.

/** An entry that lives at a URL. Extend it to make a type routable. */
interface Route {
  /** @title Name */
  name: string;
  /** @title Path */
  path: string;        // "/summer", or a template like "/:slug/p"
}

/** A saved entry of the built-in `redirect` type. */
interface Redirect {
  from: string;        // literal or template
  to: string;
  permanent: boolean;  // 301 or 302
}

A page is a route with SEO and sections. It's not special to the router; it's just the first type that extends Route. Like every data-only type, it's declared in Content, not in the block map:

interface Page extends Route {
  seo: PageSeo;
  sections: VariantOf<Array<VariantOf<Block>>>;
}

matchRoute's rule is one line: an entry with a string path matches at that path. Route is what makes that intentional. The CLI checks that any type declaring path extends Route, so a stray path field on an unrelated block is a schema error rather than a surprise URL. Editors see name and path as ordinary fields on every routable thing, in Studio, which is how a marketing team gets /summer-sale live without a developer. Keep path and from plain strings, not blocks, so the router can match without running code.

Your own routable types

A blog doesn't want a page entry per post. Extend Route and every saved post routes on its own:

Studio pre-fills path from a per-type template such as /blog/{slug}, so editors get consistent URLs by default and can still change one. Two entries with the same path, or two templates that can match the same URL, are rejected by the CLI and by matchRoute.

Pages are data; resolve their fields

A page has no function, so you don't resolve the page. You resolve the blocks it holds: client.resolve(page.seo), and one client.resolve(section) per section, so sections can stream as they finish (see the framework guides). A redirect is never resolved at all; matchRoute reads it. If you do want code to run for a whole page, such as validation or a layout step, add a page function to the block map and move Page out of Content; then client.resolve(page) runs it after every section has resolved.

Content types without a URL

Navigation, email templates, and campaign settings work the same way, minus Route: declare the type in Content if it's data, or register a function if something should run, and save entries of that type. Block is a stored block. VariantOf<T> accepts a T or a flag that picks one.

Websites

Routing

The CMS doesn't route. It lists and resolves. Routing is three steps in your request handler: list the types you want at URLs, hand them to matchRoute, resolve the winner. Because the client is made per request, all three see the same revision.

import { matchRoute, type Redirect } from "@decocms/blocks";

const client = cms.forRelease();
const [pages]     = await client.list<Page>("page");
const [posts]     = await client.list<Post>("post");
const [redirects] = await client.list<Redirect>("redirect");

const match = matchRoute(request, { routes: [...pages, ...posts], redirects });

switch (match.kind) {
  case "not-found":
    return new Response("Not found", { status: 404 });
  case "redirect":
    return Response.redirect(new URL(match.location, request.url), match.status);
  case "match":
    switch (match.entry.__resolveType) {
      case "page": {
        const sections = match.entry.sections.map((s) => client.resolve(s));   // start them all
        const [seo] = await client.resolve(match.entry.seo);                   // then await
        return render(seo, sections);
      }
      case "post":
        return renderPost(match.entry);                                        // data: nothing to resolve
    }
}
kindFields
"match"entry (the stored route you passed in) and params from the path template.
"redirect"location with parameters filled in, and status (301 or 302).
"not-found"None

matchRoute is a helper, not a requirement. The CMS has no idea what a URL is. If your framework already routes, or you'd rather look up a page by name (client.resolve("SummerPage")) or by a field of your own, skip it. It exists because "an editor typed a path into Studio and that page is now live" is the common case, and getting precedence and parameters right by hand is tedious.

Which types route is your decision, per handler: a blog lists post, a docs site lists doc. match.params holds the URL parameters; hand them to your code however your app shares request state. The CMS never injects them into blocks.

Matching is a lookup, not a scan: entries are compiled into a segment trie once per list, so a match costs the URL's depth, not the catalogue's size. The algorithm is described under the hood.

Path templates and match order

A route's path and a redirect's from accept literal segments and named parameters. A route at /:slug/p matches /summer/p with params.slug = "summer". Redirects are checked before routes, so a redirect overrides a route at the same path. Within each group, exact paths win over templates. Two entries with the same path, or two templates that can match the same URL, make matchRoute throw, and the CLI reports them at schema time. Serve framework endpoints, API routes, and static assets before the CMS catch-all; those paths don't belong to the CMS.

Linking and listing

Because the URL is a field, linking to an entry is reading it, and listing a routable type gives you an index for free:

const [posts] = await client.list<Post>("post", { sort: (a, b) => b.date.localeCompare(a.date) });
for (const post of posts) link(post.path, post.name);          // "/blog/hello-world", "Hello, world"

const match = matchRoute("/blog/hello-world", { routes: posts });
// { kind: "match", entry: { __resolveType: "post", name: "Hello, world", path: "/blog/hello-world", … }, params: {} }

Rendering

The CMS returns whatever your block function returns. Your framework decides how that value reaches the browser:

IntegrationBlock returnsStreamingShips to the browser

Block functions run on the server

In all three integrations, block functions run on the server, so data fetching belongs there. In data mode, a block returns a descriptor and a synchronous React view renders its props. With RSC, a block returns JSX that can include Client Components.

Render interactive components as elements, such as <CartButton />. Don't register a Client Component as a block function: the "use client" boundary preserves a reference, not a callable function.

Errors, streaming, and cancellation

  • Start every section first. Await critical data, such as SEO, only after all sections have started.
  • One Suspense boundary per section lets each section appear as soon as it's ready.
  • Suspense handles loading, not errors. Check each section's error and render a fallback. Errors thrown later while React renders need an error boundary.
  • Cancellation is your app's job. The CMS never sees the request. A block that fetches upstream should take the request's signal from wherever your app keeps request state.
  • Once streaming starts, the status code is fixed. A later error can't change it.

Choose a transport

Use descriptors when views must render in an ordinary browser React app. Use RSC when your framework supports it and you want server-only view code to stay off the client. RSC doesn't guarantee smaller responses, so measure payload size, hydration, and navigation on real pages.

API reference

Everything is exported from @decocms/blocks.

createCMS(config)

Two levels. A CMS is a loader plus a block map, created once at module scope. It hands out clients, one per request, for the release or for a draft, and keeps content current. A client resolves and lists, and that's all. Both are cheap: content caches in the loader, and dynamically imported modules are cached by the runtime.

function createCMS(config: {
  loader?:                               // optional: defaults to "./.deco"
    | string                             // a content directory: localLoader(path)
    | { root?: string; token?: string }  // local content in root (default "./.deco"); with a token, remote releases over it
    | Loader;                            // anything else: bundled content, KV, your own
  blocks: Blocks;
}): CMS;

interface CMS {
  forRelease(): Client;                         // a client reading loader.load()
  forDraft(pointer: string): Client;            // a client reading loader.load(pointer); an invalid pointer behaves like the release
  update(): Promise<{ updated: boolean }>;      // loader.update(), or a no-op
}

interface Client {
  resolve<T = unknown>(target: unknown, options?: { resolve?: boolean }): Promise<Result<T>>;   // resolve: false reads without running
  list<T = Block>(type: string, options?: ListOptions<T>): Promise<Result<T[]>>;
}

The loader option covers the common cases by shape. Leave it out and the CMS reads the files in ./.deco. A path is the files in that directory. { token } is releases from the Deco API with the files in ./.deco as fallback, and root changes the directory. Leave token undefined and it's just the files, which is what makes one line work in development and production. Anything else is a Loader you built yourself (examples in Content and loaders). Create the CMS once, at module scope, and ask it for a client per request: forRelease() for visitors, forDraft(pointer) when the request carries one. Clients are free to make and hold nothing you'd want to share. Everything either does is a few lines over a loader, and the registry rule from Blocks is how it resolves; those internals aren't part of the public API.

Draft pointers

A pointer is a string, <host[:port]><path[?query]>@<version>, that names where a draft lives and which version it is. Studio makes them; forDraft reads them. Two helpers cover everything in between:

interface DraftPointer {
  host: string;      // content-API authority, e.g. "studio.decocms.com"
  path: string;      // rooted path, with the signed grant in its query
  version: string;   // opaque, immutable: the branch head or ETag
}

function parseDraftPointer(raw: string | null | undefined): DraftPointer | null;
function formatDraftPointer(pointer: DraftPointer): string;

parseDraftPointer is strict and returns null on anything unexpected: a scheme, a stray @, an unrooted path, an odd character in the host or version. It's what forDraft calls, so an app only needs it to look inside a pointer, for example to show which version is being previewed, to key a cache on version, or to reject a pointer before storing it in a cookie. formatDraftPointer is the inverse, for building one from parts, as a mobile app might from a deep link.

For websites, two more helpers do the handshake, so the parameter and cookie names never appear in app code:

function draftPointer(request: Request | { url: string; headers: Headers }): string | null;
// ?__draft= from the URL first, then the deco-draft cookie. Null when neither is present.

function draftCookie(request: Request | { url: string; headers: Headers }): string | null;
// When the URL carries ?__draft=, the Set-Cookie value that stores it (HttpOnly, SameSite=Lax, Path=/),
// or one that expires the cookie when the value is empty. Null on every other request.

const DRAFT_COOKIE = "deco-draft";   // for frameworks whose cookie API has no Request, e.g. Next.js cookies()

Both take anything with a url and headers, so they work with a fetch Request, a Next.js NextRequest, or a framework's request wrapper. DRAFT_COOKIE is for the one place that has no request at all: reading the cookie in a Next.js Server Component.

const pointer = parseDraftPointer(cookie);
if (pointer) console.log(`previewing ${pointer.version} from ${pointer.host}`);

formatDraftPointer({ host: "studio.decocms.com", path: "/api/acme/decofile/store/main?token=…", version: "9f3c1a" });
// "studio.decocms.com/api/acme/decofile/store/main?token=…@9f3c1a"

Caching, ETags, and fallbacks live inside the loader, which may be shared by any number of clients. The client only ever sees { revision, blocks }.

client.resolve(target, options?)

Loads the content once and applies the registry rule to the target: saved entries expand, and each block type in the map runs with its resolved inputs. { resolve: false } expands entries but runs nothing.

CallReturns
resolve("SummerSEO")The result of running the entry's function
resolve("SummerSEO", { resolve: false })The saved entry, with references expanded and nothing run
resolve({ __resolveType: "seo", title: "Sale" })The result for an inline block

A string target is always an entry name. Any other value is walked as is, so you can pass a page field without checking whether it's a block or a literal. T describes the result you expect; it isn't validated at runtime.

A client reads one revision for its lifetime. Its first call loads; every later call, list or resolve, reuses that content and shares a cache. That's why a client is made per request: everything a response renders agrees with itself, sections can stream as separate calls, and the next request sees the next revision. Two clients can see different revisions, so don't share one across requests.

client.list(type, options?)

Every saved entry of a block type, through aliases. Returns stored entries by default; resolve: true runs each one.

  sort?: (a: T, b: T) => number;
  limit?: number;
  resolve?: boolean;

const [posts] = await client.list<Post>("post", {
  where: (p) => p.date <= today,
  sort: (a, b) => b.date.localeCompare(a.date),

});

Filters run in memory over the loaded content, which is the honest cost of a file-based store. Sites with tens of thousands of entries of one type should keep an index elsewhere.

matchRoute(url, items)

A pure function. Given a URL and the entries you want to route, it returns the one that matches. The CMS doesn't know about URLs; this is the companion that does. See Routing.

function matchRoute<T extends Route>(

Production

Releases and deployment

Every loader returns a revision with its content (see Content and loaders). localLoader, the CLI, and the Deco API all compute it as the same hash of the entries, so "is what I have current?" is one string comparison.

Content fromDeployment
localLoaderThe content that ships with the app: a directory on Node, or JSON bundled into the build on Workers. On its own, changing content means redeploying (or, on Node, editing files); as the fallback of remoteLoader, it's what the app serves when the API is down.
remoteLoader(fallback, …)The Deco API serves each commit of the production branch as an immutable release. The loader reads the current one at request time, cached by revision, with the content the build shipped with as the fallback. A content change reaches visitors without a deploy. This is what "instant deploys" means.

Revisions are immutable: change any entry and the hash changes. A revision is a safe cache key everywhere.

One revision per response

A client reads one revision for its lifetime: its first call loads, and every later list and resolve reuses that content, even concurrent ones. Two clients can see different revisions, so make one client per request and do everything the response needs through it.

When the browser requests more data for a page it has already rendered, send the page's revision along so the data matches the HTML. A revision ID picks content; it doesn't grant access. Preview access is the draft pointer's signed grant and the site's preview hosts on decocms, see Preview.

Publishing

Publishing is committing. A developer or an agent edits .deco/blocks and pushes; an editor saves in Studio, which commits to the same repository. Either way the production branch moves, and the Deco API turns that commit into a release. remoteLoader resolves the production channel to a revision once per load, caches immutable releases indefinitely, and polls for a new revision every five minutes, so a change reaches every visitor within about five minutes of the commit. Because content and code share one history, a deploy and a content change are the same kind of event: a commit. Rolling content back is reverting one.

The API skips a release whose schema doesn't match the running app's, so content can't get ahead of code: if a commit adds a block type the deployed build doesn't have, the loader keeps serving the previous release until the build catches up.

Never waiting on the network

A production request never waits for the API. load() returns from memory, immediately, every time, and the loader checks for newer content in the background every five minutes. Publishing reaches visitors within about that long. How that works, step by step, is under the hood.

Fallback

The fallback loader is the only fallback, and it's always available: it's the content the build shipped with, which is the content the deploy was tested against, so it's always compatible with the code. It always swaps whole revisions: mixing entries from different revisions breaks references and can bring back deleted content. The loader reports the revision it actually served.

To point the CMS at a different source, or to write a loader for your own store, see Content and loaders.

Each cache layer has its own lifetime and key:

Tracing

Make each request span the parent of block resolution spans and outbound HTTP spans. Record the block type, revision, duration, errors, and cache outcome, and keep credentials and customer data out of attributes. Export telemetry asynchronously, so an unavailable collector never blocks rendering. OpenTelemetry covers traces, metrics, and logs.

Studio and MCP tools build authoring and publishing workflows on these sources. They're not part of a storefront's request path.

Production

Upgrading and compatibility

Block type names and input shapes are persistent interfaces: saved content depends on them. Moving a file is free. Renaming a type or removing an input affects every block that uses it.

Rename a type with an alias

An alias is another key pointing at the same thing: the same function in the block map, or the same type in Content. Content that stores the old name keeps working, and routing is unaffected because it looks at path, not the type name:

An alias only works while both names take the same inputs. If the old shape differs, register a function that converts it, or migrate the content first. deco schema rejects an alias that collides with an entry name.

Upgrade checklist

  1. Keep existing names. Register existing path-like types as they are, or alias them.
  2. Check inputs. Regenerate the schema and validate saved content. Review new required fields, narrowed unions, and changed defaults.
  3. Migrate into a new revision. Keep unknown fields for inspection, and report unresolved references instead of dropping them.
  4. Test the integration. Check routing, metadata, streamed sections, error fallbacks, and client navigation against the migrated content.
  5. Keep a rollback pair. Keep the previous build with compatible content. Rolling back content alone can't restore removed code.

Test behavior, not just schemas. A function can keep its input type and still change its output, defaults, or upstream calls.

Under the hood

The developer docs describe how to use Deco Blocks. This part describes how it works as a whole: the resolution algorithm, how the production loader stays current without ever blocking a request, how the router matches, what Deco Studio reads and how the framework stays compatible with it, and the decisions behind all of that. Contributing

The framework is a Bun workspace at decocms/blocks. Five packages, one-way dependency graph, and that direction is load-bearing:

packages/

bun install

Two rules worth knowing before a first PR. A site must never need a local shim for something a package should export: if a symbol is missing from a package's public surface, add the export. Fetch, verify, swapWhole revision at once. Any error: keep what's there.
  1. Serve from memory. load() returns the newest release this process has fetched, or, if it hasn't fetched one yet, the fallback loader's content. A cold start serves the content the build shipped with on its very first request.
  2. Ask for the hash. In the background, on first use and then every five minutes, update() fetches the current revision hash from the API. That's a few bytes. Each wait is jittered by up to 30 seconds, so a fleet of servers that started together doesn't poll together.
  3. Compare. If the hash equals what's in memory, there's nothing to do. If it equals the fallback loader's revision, the disk is current: the loader uses that content and never downloads it. This is the common case right after a deploy.
  4. Fetch and swap. Otherwise it fetches that revision, checks that the content hashes to it and that its schema matches the running app, and swaps it in whole. Requests in flight keep the revision they started with.
  5. Fail quietly. Any network or validation error leaves memory as it was. Nothing reaches a request.

So production content is eventually consistent, by design, with the polling interval as the bound: a commit is live everywhere within about five minutes, and one process only ever does one tiny request per interval, however many requests it serves. Drafts are the opposite: a preview must show exactly the version Studio asked for, so load(pointer) fetches that version and waits for it, cached by version afterwards. If the draft can't be fetched, it serves published content, never the disk.

Under the hood

How matchRoute matches

The naive version of this function walks every entry and tests each path against the URL. That's fine for fifty pages and wrong for fifty thousand. matchRoute instead compiles the entries into a segment trie, once per list, and matches in time proportional to the URL's length, not the catalogue's size.

/summer                 /:slug/p                /blog/:slug             /blog/archive
                                    ┌── root ──┐
                                    │           │
            ┌───────────────────────┼───────────┼──────────────────┐
         "summer"                "blog"                        :slug
            │                       │                            │
        [SummerPage]     ┌──────────┴──────────┐                "p"
                     "archive"                :slug               │
                         │                      │           [ProductPage]
                    [BlogArchive]           [Post …]
  1. Build, once per list. Every path is split on / and inserted segment by segment. A literal segment becomes a named child; a :param segment becomes the node's single parameter child. The entry is stored at the leaf. Cost is the total number of segments, and the result is cached in a WeakMap keyed by the array you passed, so the second request with the same list skips this entirely.
  2. Reject ambiguity while building. Two entries reaching the same leaf, or two parameter children under one node (/:slug/p and /:id/p), throw with both names in the message. The CLI runs the same build at schema time, so this surfaces in CI, not in production.
  3. Match, one segment at a time. Walk the URL's segments from the root. At each node try the literal child first, then the parameter child. If a branch dead-ends, backtrack once to the parameter child of the last node that had one. Backtracking is bounded by the URL's depth, so a lookup is O(segments), typically four or five steps, regardless of how many entries exist.
  4. Precedence falls out of the walk order. Trying the literal child before the parameter child at every node is exactly "exact paths win over templates", per segment rather than per path: /blog/archive beats /blog/:slug for /blog/archive, and /blog/:slug still serves /blog/hello-world. No sorting, no regex.
  5. Redirects are a second trie, checked first, with the same rules. A hit fills the parameters into to and returns { kind: "redirect" }.

Before matching, the URL is normalised: percent-decoded, query and fragment dropped, trailing slash removed except for /. Parameters capture one segment and never contain a slash. That's the whole algorithm; it's the same shape as the routers in Fastify and Hono, and it's about a hundred lines.

Deco Studio compatibility

What Studio reads

Studio never calls the SDK. It reads two things: the schema the CLI wrote, served as /live/_meta, and the content files. So everything Studio knows about your site is inferred from your types, and the CLI does the inferring. It groups every key into a manifest by what the type says:

Manifest groupWhat lands thereStudio uses it for
sectionsBlock functions that return JSX or a render descriptorThe section catalog when composing a page
matchersBlock functions that return booleanThe rule picker on a variant
loadersEvery other block functionData fields that can point at a function
pagesContent types that extend RouteThe page list, "new page", the URL field
redirectsRedirectThe redirects screen
contentEvery other Content typePlain entries: navigation, settings, posts

Three conventions follow from this, and they're the ones the rest of the doc already uses. A key is a module type if it's in the manifest and a saved entry if it isn't, so short names like hero are fine. A variant is { "variants": [{ "rule", "value" }] } with the default first. A redirect is a flat { from, to, permanent } entry.

Studio compatibility today

Today's Studio predates this design and hardcodes a few of the things above: it tells modules from saved entries by whether the key has a file extension, and it looks for pages, the default and hidden rules, and variant wrappers by their old module paths (website/pages/Page.tsx, website/matchers/always.ts, website/flags/multivariate.ts, …). Until it reads the manifest instead, the CLI bridges the gap: for every key in a framework-known group it also emits the legacy path as an alias, and content Studio saves under a legacy name resolves through the same alias mechanism your own renames use. Your code uses page and always; the manifest carries both spellings; nothing in the runtime changes.

Two gaps the bridge doesn't cover, both Studio-side and both small: redirects created in Studio are saved in the old nested shape, which matchRoute accepts as well; and Studio's module-or-entry check needs to become a manifest lookup before a site can drop the aliases. Both are tracked against Studio, not against sites.

Design decisions

Each of these was argued over. The one-line version, and why it won.

DecisionWhy
The CMS is pure. A block function gets its inputs and nothing else.No context object means block functions are ordinary functions you can call and test, and the same code runs in a website, a mobile app, or a job. Request state comes from the runtime's own context, where it already lives.
Git is the source of truth. Publishing is committing; the API serves commits as releases.History, review, branches, and rollback come for free, and agents can edit content with the tools they already have. There is no publish command because there is nothing to publish that a commit doesn't already express.
One registry rule. A name is data or code; data merges and re-applies, code resolves inputs then runs; outputs are opaque.Saved entries become presets rather than a second concept, identity functions can't loop, and the only recursion is over data, where a cycle check ends it.
The CMS at module scope, a client per request, pinned to one revision.Everything a response renders agrees with itself, sections can stream as separate calls, and the next request sees the next revision. Clients are cheap because every cache lives in the loader.
Loaders are one interface: load(pointer?) and update().Production, drafts, and staying current are three uses of one method pair, so localLoader and remoteLoader are interchangeable and a custom loader is a few lines.
A production request never waits for the network.Serve from memory, poll for a hash in the background, fall back to the content the build shipped with. Eventual consistency for visitors, strict consistency for drafts.
The CMS doesn't route. matchRoute is a helper over entries you list.Which types have URLs is an app decision, a non-website has none, and the framework's file-system router still owns code routes. Editors get pages at arbitrary paths because the path is a field.
Data-only types live in Content, not the block map. No built-in entries.A map entry means "run this". Pages, posts, and redirects have nothing to run; they need a schema, which is the CLI's job. Nothing ships that a site couldn't write in one line.
Lazy loading belongs to the framework.What's heavy is the component, and React and Next already load components lazily. The block map stays a plain object the CLI can read.
Three matchers ship; the rest is app code.always, never, and date depend on nothing but the clock. A device or cookie matcher is an opinion about the request, and the app owns those.
Short type names, aliases for legacy paths.A type name is a column name, not a file path. Existing content keeps working through aliases while new code uses names that survive a refactor.
