Getting started

How it works

Status. Deco Blocks is being designed in the open: the API on these pages is proposed and not released yet. The Roadmap lists what's left.

Deco Blocks lets the people who run a site change what your code does without changing the code. You write ordinary TypeScript functions. The values they're called with, such as a headline, a banner image or the share of visitors who see a new checkout, live as JSON files in your repository. Editors change those files in a visual editor, AI agents edit them directly, and your app reads them at runtime and calls your functions with them.

Deco Blocks has two pieces you install, and one you don't:

Key terms

These terms come up on every page. Each is explained again where it's first used.

Block function
One of your functions with a typed first parameter, registered in a block map. It can return anything: data, a boolean, a descriptor or JSX. The framework treats them all the same. See Quickstart.
Block map
A plain object of your block functions, such as { experiments }. See Quickstart.
Block type
A key in the block map: the name content uses to call that function.
Block
Either a function (code) or saved content (JSON), named by __resolveType. A function is a key in your block map and ships with each deploy. Saved content is a saved entry: it's versioned, can have drafts, and publishes without a deploy. The JSON that calls a block, { "__resolveType": …, …inputs }, is called a block too. See Blocks.
Saved entry
Saved content: a block saved under a name, one JSON file in .deco/blocks, whose file name is the entry name. See Content and loaders.
Content module
.deco/blocks.gen.ts, the file deco content generates from .deco/blocks. It imports each JSON file and exports a snapshot, { revision, blocks }: one fixed copy of all your saved entries. See Content and loaders.
Content map
All saved entries, keyed by name.
Page
A built-in content type: a saved entry with a path, SEO and an ordered list of blocks (its sections field) that editors add, remove and reorder. See Routes and redirects.
Loader
Any object whose load() returns { revision, blocks }. Pass one as createCMS's content to read content from a key-value store, a database or your API. See Content and loaders.
Revision
The ID of one exact content map, released or not, usually a hash of its contents. Change any entry and you get a new revision.
Release
A published content map. With the hosted Deco CMS, each commit to the production branch becomes one. A release never changes, and its revision identifies it. See Releases and deployment.
Draft
Content changed in Studio but not yet published, kept on a branch. See Preview.
Client
The object you read content with, one per request: cms.forRelease() for visitors, cms.forDraft(pointer) for a preview. It has two methods, list and resolve. See Quickstart.
Descriptor
A plain, serializable object such as { component, props } that names a view and its props for your front end to render. See Rendering.

At request time, your app asks the SDK for a piece of saved content by name. The SDK reads it from the content you gave createCMS, the one setting that knows where content lives (usually the content module generated from .deco/blocks; see Content and loaders). If that content refers to other saved entries, the SDK expands them. Then it calls the matching function from your block map with the saved inputs and returns the result. How you render it is up to your framework. When you need more from the block map, such as lazy loading, see Block maps.

If you use the hosted Deco CMS, you can publish content without redeploying. In production your app reads the current release from the Deco API instead of from the content module. A request never waits on that: content stays in memory and refreshes in the background (each server checks for a new release about once a minute, when it's idle), and the content your build shipped with is always there as the fallback. See Releases and deployment, or how the loader stays current for the details.

Small on purpose

Deco Blocks stays out of your way, and every piece is replaceable:

  • Content is plain JSON. Open it in any editor, grep it, diff it, or generate it with a script. There's no database or content API for you to host. The hosted Deco CMS is optional, and Deco runs it.
  • Block functions are plain functions. No framework plugin, no base classes, no magic directories. The block map is a plain object, and you can call any block function directly in a test.
  • Loaders are one method. Reading from a key-value store such as Cloudflare Workers KV, or from your own database, is one load() method that returns { revision, blocks }: an ID for this version of the content, and the saved entries by name. Files in your repository need none, because the CLI turns them into a module. Swap the source and nothing else changes (see Content and loaders).
  • The schema is a file. Commit it, inspect it, or generate it another way. Studio builds its forms from that JSON alone.
  • Nothing is hidden. If the SDK doesn't do what you need, read the content yourself: the block format is documented in Blocks, and the files and the content map in Content and loaders.

Quickstart

Suppose your app has a function that decides which A/B tests a visitor sees. It takes the traffic split for each experiment and returns whether each one is enabled:

The split is hardcoded at the call site. Ramping the new checkout from 10% to 25% means a pull request and a deploy. In this guide you'll move those numbers into content: a JSON file that you, an AI agent, or an editor in Deco Studio can change, while the function stays exactly as it is. It runs in plain Node, with no framework.

This function doesn't render anything; it returns flags. A block function can just as well return JSX, and Blocks shows how.

Prerequisites:

  • Node.js 24 or later, and tsx to run TypeScript.
  • An ESM project ("type": "module" in package.json), because the examples use top-level await.
  • Optional: a site on the hosted Deco CMS connected to this repository, and its token, if you want to try Studio or publish without a deploy. Creating a site and issuing a token for this API isn't available yet (see the Roadmap). Everything on this page works without it.
npm install @decocms/blocks
npm install -D @decocms/blocks-cli

The second package provides the deco command.

1. Make the function configurable

Any function with a typed first parameter can become a block function. Register it in a block map, a plain object of functions. Each key is a block type, the name content uses to call that function; here it's experiments. The CLI reads this file, and your app hands it to createCMS.

satisfies Blocks checks the map's shape without widening it, so TypeScript keeps each function's exact input and return types. The CLI generates the editor form from those types in step 2.

2. Give editors a form

The CLI reads the map and turns the Experiments type into a JSON Schema. The JSDoc tags shape the form: @title becomes the field's label, and @minimum/@maximum its allowed range. Schema generation lists every tag.

npx deco schema

It finds the block map in blocks.ts (or src/blocks.ts; see Schema generation) and writes .deco/schema.json. Commit the file. If the repository is connected to the hosted Deco CMS, Studio now shows each experiment as a number field clamped to 0–100. Without it, the schema still describes the content you or an agent write by hand.

3. Add content

There are two ways to create content:

  • By hand. Write the JSON file yourself, or ask an AI agent to "ramp the new checkout to 25%" and let it edit the file.
  • In Studio (hosted Deco CMS). Pick the experiments block type, fill in the form, and save. Studio commits the same file.

Both routes produce the same file in .deco/blocks, which is where the CLI looks for content (its --root flag points it at another .deco folder):

// Means
experiments({ newCheckout: 10, stickyHeader: 50, freeShippingBanner: 0 })

The file is a saved entry: one named piece of content that code, or other content, can refer to. Its file name without .json is its name (see Content and loaders). __resolveType is a reserved key (the underscores keep it from clashing with your fields) that names the function to call by its block type. The other keys are that function's inputs.

Two names are in play, on purpose: experiments is the block type and names a function, and Experiments is the entry name and names this one piece of saved content. You could save several entries that call experiments, such as HolidayExperiments. Names are case-sensitive, so they don't clash.

4. Generate the content module

The SDK never reads files itself, so it runs the same way in any JavaScript runtime. Instead, the CLI turns your content files into a module your app imports, the content module:

npx deco content

It writes .deco/blocks.gen.ts, which imports each JSON file in .deco/blocks separately and exports a snapshot, { revision, blocks }: one fixed copy of all your saved entries, plus its revision, an ID the CLI computes from their contents. The file is generated, so add it to .gitignore, as you would TanStack Router's routeTree.gen.ts. For this guide, running npx deco content once is enough. Rerun it when you add or remove a file in .deco/blocks; editing an existing file needs no rerun. In an app with dev and build scripts, add the two commands to package.json so they run first (see The content module):

"predev": "deco schema && deco content",
"prebuild": "deco schema && deco content"

5. Read the content from your code

Create the CMS once, at module scope, with your block map and the content module (to connect the hosted Deco CMS or another store, see Configuring content).

Then ask it for a client, the object you read content with. forRelease() returns a client over the published content, the release; with plain files, the release is simply what's in the content module. Its sibling forDraft() reads unpublished drafts for previews (see Preview). Make one client per request: a client reads one consistent version of the content for its whole life.

Fetch the entry by name. The client runs experiments on the saved inputs, so you get the same value as calling experiments() yourself. An entry name is just a string, so TypeScript can't infer the result type from it; pass the type you expect, and it's checked at compile time, not at runtime:

Every call returns a [value, error] tuple, so a missing entry or a failing function never throws. The error names what went wrong, for example NOT_FOUND. Troubleshooting lists every code.

Run it with npx tsx checkout.ts. Now open .deco/blocks/Experiments.json, change newCheckout to 100, and run it again (no need to rerun deco content: only adding or removing a file needs that): newCheckout is true every time. You changed what the code does without touching the code.

That's it. The function didn't change, but its inputs now live in a file that editors change through a form and agents change directly, and every change is a commit. A real implementation would hash a visitor ID from a cookie instead of rolling a die, so each visitor gets a stable result. Block functions receive only their saved inputs, not the HTTP request, so read the cookie the way the rest of your app does (see Block maps).

Core concepts

Blocks

Most of what changes on a website isn't the code. It's the values the code is given: a headline, a banner image, the share of visitors who see the new checkout. Deco is built on that idea: developers write the functions, and the people who run the site decide what goes into them.

Blocks are how they make those decisions. A block is a small piece of JSON that names one of your functions and lists the inputs to call it with. Editors change the inputs in Studio, and agents edit the file directly. When your app resolves the block, Deco calls the function with whatever is saved and gives you back the result. This page shows what a block looks like, how blocks fit inside each other, and exactly how they turn into values.

Start from code you already write

Here's the kind of code you write every day:

productCard({
  title: "Summer collection",
  product: catalogProduct({ slug: "summer-shirt" }),
})

It's function composition. The inner call runs first, and its result becomes an input to the outer one, so productCard receives product data, never a pending call. The functions are the developer's job. The composition is a decision: which product, which title, which function fetches the data. Written in code, changing that decision means editing code and deploying it.

A block is that composition, stored as data

Write the same composition as JSON and nobody has to edit code to change it. __resolveType names the function, the other properties are its inputs, and a block inside an input is a call inside a call. Here productCard and catalogProduct are the functions your block map registers as "product-card" and "catalog-product":

// Stored as JSON
{
  "__resolveType": "product-card",
  "title": "Summer collection",
  "product": { "__resolveType": "catalog-product", "slug": "summer-shirt" }
}

// Means
productCard({
  title: "Summer collection",
  product: catalogProduct({ slug: "summer-shirt" }),
})

Now an editor can change the title or the slug in Studio, and an agent can even point product at a different function, and the composition changes without a deploy. The functions are whatever your block map registers, and each one's input type is what deco schema turns into the editor form. Use the same model for anything your site needs: UI, product data, SEO, navigation, campaign settings. The CMS doesn't reserve any directories or categories.

Name a composition, reuse it

In code, you'd give a composition you use often a name and reuse it. Saved entries do that. Alongside the block map of functions, the CMS reads a second map, the content map, where each name holds a piece of saved JSON. { "__resolveType": "SummerSEO" } means whatever is saved under the name SummerSEO, written in place. The map can come from files in your repository, the hosted Deco CMS, or your own store; see Content and loaders.

Unlike a const that holds a result, what's named here is the call itself, inputs and all. That's why you can add inputs to a reference to override the saved entry's inputs for this one use:

// Saved as SummerSEO
{ "__resolveType": "seo", "title": "Sunny!", "description": "Light layers for long days." }

// A reference to it, anywhere in your content
{ "__resolveType": "SummerSEO", "title": "Summer sale" }

// Means
seo({ title: "Summer sale", description: "Light layers for long days." })
  • Overrides are shallow. The merge is { ...entry, ...inputs }, so an override replaces the whole top-level property, and the saved entry itself doesn't change. It isn't currying or partial application: the reference is expanded into one complete call.
  • An entry doesn't have to be a block. It can be any JSON that contains blocks, like a page with a list of blocks: an object literal with calls inside. Resolving it calls each block inside and leaves the rest of the JSON as it is.

Resolving a page, step by step

Resolving a block is evaluating its composition: named entries expand, then calls run from the inside out. Here's a page saved as SummerSale. It uses the SummerSEO entry with an override, and one carousel block in its sections list. A page is mostly an ordered list of blocks that editors add, remove and reorder. The block map has two functions. seo returns its inputs; that's still worth registering, because it gives editors a form for SEO and lets them save it as a reusable entry. carousel returns a descriptor, { component, props }: a plain object that says which component to render with which props, for your app to render later. A block function can also return JSX directly; Rendering compares the two.

// Saved as SummerSale
{
  "seo": { "__resolveType": "SummerSEO", "title": "Summer sale" },
  "sections": [{ "__resolveType": "carousel", "banners": [] }]
}

This page has no __resolveType, so the page object itself isn't a call: resolving it resolves the blocks inside and keeps the rest of the JSON as it is. (Real pages usually carry "__resolveType": "page" so they can be listed by type. That name has no function behind it, so for those you resolve the fields instead; see below.)

Call client.resolve("SummerSale") and follow the page as it changes. resolve takes either an entry name (a string; a string is always an entry name) or any JSON value, such as one field of a page.

Step 1. The reference expands. SummerSEO is a saved entry, so it's data. The saved entry is merged with the reference's own inputs, and the reference's inputs win. The __resolveType from the entry, seo, names a function.

{
  "seo": { "__resolveType": "seo", "title": "Summer sale", "description": "Light layers for long days." },
  "sections": [{ "__resolveType": "carousel", "banners": [] }]
}

Step 2. The functions are called. What's left is a composition of plain calls. Both blocks have plain inputs, so both functions run. They're siblings, so neither waits for the other.

{
  seo: seo({ title: "Summer sale", description: "Light layers for long days." }),
  sections: [carousel({ banners: [] })]
}

Step 3. The result. Each return value takes its block's place. The page itself was never a block, so its shape stays the same.

{
  seo: { title: "Summer sale", description: "Light layers for long days." },
  sections: [{ component: "Carousel", props: { banners: [] } }]
}

To step through a deeper example, see How resolution works.

Reading without running. Pass { run: false } to read content without running any function. client.resolve("SummerSale", { run: false }) stops after step 1: saved entries like SummerSEO still expand, and blocks that name a function, like seo and carousel, come back as JSON, untouched. Nothing runs. That's useful for previews, editor tooling, and debugging.

The rule

Every __resolveType names a block, and a block is either a function (code) or saved content (JSON): a function in your block map to call, or a saved entry in your content to expand. Both share one namespace, one registry. They differ in how they change: functions ship with a deploy, while saved content is versioned (each version has a revision), can have drafts, and can be published without a deploy.

const registry = { ...savedEntries, ...blocks };   // name → saved JSON | function

Saved entries are the content map you pass as createCMS's content. Functions come from the block map you give createCMS. The CMS applies one rule to every object with a __resolveType:

  1. Look up the name.
  2. Data: replace the object with { ...entry, ...inputs }, so your inputs override the entry's, and apply the rule to the result again.
  3. Function: resolve the inputs first, children before parents and siblings concurrently, then call the function. Its return value takes the block's place.
  4. Neither: fail with UNKNOWN_BLOCK.

The rule in detail

  • Failures stop the parent. If a nested block fails, its parent never runs and resolve returns the error, much as an outer call never runs when an inner one throws. A reference to an entry that doesn't exist fails with NOT_FOUND.
  • Results are returned as is. The CMS never walks a function's return value. Return plain data, a descriptor, or JSX. This is also why a function that returns its input, like seo above, can't loop: __resolveType is stripped before the call, and whatever comes back is never looked up again.
  • Block functions should only read. They run whenever content is resolved: for a visitor, in a Studio preview, for an agent. Put side effects in your own route handlers (see Caching and observability).
  • Only data can loop. A saved-entry expansion is the one branch that applies the rule again, so two entries that reference each other, or an entry that references itself, would recurse forever. The CMS tracks the entries expanded on the current path and fails with CYCLE the moment one repeats, with the chain in error.path.

Pages that are only data. Some saved entries describe a shape but have no function behind them, such as a page (page is a built-in content type, saved with "__resolveType": "page"). Nothing can be called for them, so resolving the entry fails with UNKNOWN_BLOCK. Read the entry instead, then resolve the blocks inside it, for example client.resolve(page.seo). (SummerSale above had no __resolveType at all, which is why it could be resolved whole.) Schema generation shows how to declare such types, and Routes and redirects how to read them.

Entry names and block types share one registry. If a name is both, the function wins, so a saved entry called seo and a seo function can't coexist. deco schema fails when an entry in .deco/blocks has the name of a block type, so rename the entry. By convention, functions are lowercase or kebab-case and saved content is Capitalized.

Core concepts

Content and loaders

Resolving takes two maps. The block map holds your functions, and it ships with your code. The content map holds your saved entries: each name points at a piece of JSON. You hand createCMS your content through its content option, the only setting that knows where content lives: either the content module the CLI generates from your files, or a loader, any object with a load() method that returns the content map. Your functions, the resolver, and your pages never do.

Other meanings of "loader". In these docs, a loader on its own always means a content loader: the object that supplies the content map. Two other things share the name. In Studio, and in sites built on Deco's earlier framework, "loader" also means a block function that fetches data, like catalogProduct in Blocks; those are ordinary functions in your block map. And frameworks such as TanStack Router and Remix call the function that fetches a route's data a route loader. Nothing on this page applies to either.

Content always arrives as the whole map at once, with a revision that identifies it. This pair, { revision, blocks }, is called a snapshot: one fixed copy of all your saved entries.

{
  "revision": "b1946ac92492d2347c6235b4d2611184",
  "blocks": {
    "SummerSEO": { "__resolveType": "seo", "title": "Sunny!", "description": "Light layers for long days." },
    "SummerSale": {
      "seo": { "__resolveType": "SummerSEO", "title": "Summer sale" },
      "sections": [{ "__resolveType": "carousel", "banners": [] }]
    }
  }
}

Each key under blocks is an entry name. It's the name a __resolveType refers to, and the name you pass to client.resolve("SummerSEO"). The field is called blocks for compatibility with Studio's file format, but it holds saved entries: any JSON, never functions. Functions only ever come from the block map you give createCMS.

The revision names this exact set of entries. The CMS and your app use it like a version number: to tell when content changed, to keep cached data from different versions apart, and to tell one release from the next. The one hard rule: any change to any entry must produce a new revision, and a revision must never be reused for different content. deco content, remoteLoader and the Deco API all use the same content hash of the whole map, so two copies of the same content get the same revision wherever they're computed. A loader you write can use any string that follows the rule; Releases and deployment shows what matching the hash buys you.

To read an entry exactly as stored, with references in place, index the map: content.blocks["SummerSEO"], with content imported from ./.deco/blocks.gen (the content module, below).

The map itself isn't a call: it's what the names in your content refer to. What each entry means is in Blocks.

Where content comes from

When you edit with Studio or an agent, content is authored as files: they write to .deco/blocks in your repository, and every change is a commit. The content option only decides where your app reads that content from at runtime. A release is one published version of the whole content map. A draft is content an editor has changed in Studio but not published yet (see Preview). With the hosted Deco CMS, each commit to the production branch becomes a release that reaches your app without a deploy, and the content the build shipped with is the fallback (see Releases and deployment). If you load from your own store, how content gets there is up to you.

There is no publish step. Content is published by changing it: commit a file in .deco/blocks and push, or save in Studio, which commits for you. With the hosted Deco CMS, that commit becomes the current release without a deploy; without it, the content goes live with your next deploy. See Publishing. (Running deco publish only prints this explanation, so an agent that tries it learns to commit instead.)

Configuring content

createCMS takes your content in its content option: usually the content module, or a Loader for your own store. Add token to connect the hosted Deco CMS; it's shorthand for remoteLoader(content, { token, interval }), with your content as the fallback.

token is your site's API key from the hosted Deco CMS, used to call the Deco API. (Issuing tokens for this API isn't available yet; see the Roadmap.) Keep it in an environment variable, never in the repository. When it's undefined, in development for example, the CMS reads content only, so the same line works everywhere.

interval is how often each server checks for a new release, in milliseconds. It defaults to the DECO_CONTENT_INTERVAL environment variable, or 60 000 (one minute) when that's unset. The minimum is 60 000: lower values are raised to one minute, with a warning. Each check runs one interval, plus or minus up to 10 seconds, after the previous one. How and when checks run is in Loader internals.

Core concepts

Schema generation

Studio builds its editor from a JSON Schema, and the CLI writes that schema from your TypeScript. It reads the file that exports your block map, the blocks.ts from the quickstart, and writes .deco/schema.json. It looks for that file as blocks.ts or blocks.tsx, in the project root or in src/:

npx deco schema

For each block type in the map, the CLI reads the type of the function's first parameter and turns it into a form definition. Commit .deco/schema.json with your code, and run the command in CI so the schema never drifts from your types.

The CLI also checks your content model: it fails if a saved entry in .deco/blocks has the name of a block type, or if an alias (a second name for a block type, used when you rename one; see Renaming and migrating) collides with either.

The two CLI commands

The CLI has two commands, and each does one job:

  • deco schema turns the types in your block map into .deco/schema.json. Commit this file.
  • deco content turns the files in .deco/blocks into the content module, .deco/blocks.gen.ts. It's generated, so gitignore it.

Both take --watch, to regenerate as files change, and --root, the .deco folder to use (by default ./.deco). There's no separate dev command: run both before your dev server and your build. Why the content module is gitignored, and what reloads without a rerun, is in The content module.

Content that is only data

A page, a blog post, a redirect: these have a shape but no function. They're never resolved themselves: your app reads them, by type with client.list("post") or by URL with matchRoute (see Routing), and resolves the blocks inside them. They still need a schema so Studio can create them, so declare them for the CLI in a type-level map next to the block map. deco schema always includes two built-in content types, page: Page and redirect: Redirect, so you declare only your own, like post: Post. Page, Redirect and Route are exported from @decocms/blocks.

The CLI reads both exports. Keys of the default export get a schema from each function's parameter type; keys of Content get one from the type itself. The two share one namespace, and a key in both is an error. The CMS never sees Content: list("page") works because the entries exist, and resolving a page means resolving its fields, not the page.

Override or opt out. Declaring a built-in key in Content replaces it. Extend the exported type to add fields, or to narrow sections, a page's ordered list of blocks:

import type { Page } from "@decocms/blocks";

interface StorePage extends Page { theme: "light" | "dark" }

export type Content = { page: StorePage; post: Post };

An app that isn't a website opts out with page: never or redirect: never. Either way, only the schema changes: the CMS never reads Content.

Studio learns the shape of your content only from the schema this command writes. What it looks for, which endpoints it calls on your site, and how the CLI bridges today's Studio conventions are covered under the hood.

Core concepts

Preview

A draft is content an editor has changed in Studio but not published yet, kept on a branch until someone publishes it. Editors want to see a draft before it's published. Because block functions ship with your app and only content changes, previewing a draft needs no deploy: the app renders the same code against different content.

Here's the whole mechanism. Studio opens your site with a draft pointer in the URL:

https://store.example.com/summer?__draft=studio.decocms.com/api/acme/decofile/store/feat-summer%3Ftoken%3D…@9f3c1a

The part after __draft= is URL-encoded, which is why ? and = show as %3F and %3D. Decoded, studio.decocms.com/api/…/feat-summer?token=… is where the draft lives: the Deco API's address for this site's feat-summer branch, plus a token signed by Studio. Treat the path as opaque. 9f3c1a, after the @, is the draft's version.

The pointer is a string, <host><path>@<version>: where the draft content lives, and which version. draftPointer(request) reads it, from ?__draft= or from the cookie described below, and the CMS gives you a client over that draft. Everything after that line is the same code that serves visitors:

forDraft hands the pointer to whatever supplies your content. remoteLoader fetches that exact version from the Deco API, waits for it, and caches it by version, so the second request for the same draft is a memory read. A draft replaces the whole revision, deletions included, so a page in preview looks exactly as it will after publishing. The content module has no drafts, so it ignores the pointer: in development you're already looking at the files. A loader you write honors it if your store has drafts (see Write your own loader). That's why the code above never checks where its content comes from.

Keep the draft across navigation

The pointer is only in the URL of the first page Studio opens. draftCookie(request) gives you the Set-Cookie value that response needs, and null on every other request. Append it, and draftPointer reads the cookie from then on, so every link the editor clicks stays in preview:

Studio ends a preview by opening the site with an empty ?__draft=; draftCookie returns an expiring cookie for that, so the same two lines cover leaving preview. The parameter and cookie names never appear in your code. In Next.js the two steps split across proxy.ts (Next.js 16's name for middleware.ts), which appends the cookie, and a server helper that reads it with cookies(). The Next.js guide has both files.

Not a website

forDraft takes the pointer string and nothing else, so nothing here assumes HTTP. A mobile app takes it from the deep link Studio opens, or from a "preview" field on a debug screen, and keeps it in app state:

// React Native, on a deep link like mystore://preview?__draft=...
const pointer = new URL(url).searchParams.get('__draft')
setClient(pointer ? cms.forDraft(pointer) : cms.forRelease())

A script passes it as an argument. To look inside a pointer, or build one from parts, use parseDraftPointer and formatDraftPointer from the reference; forDraft parses on its own, so normally you don't have to.

Who may preview

Anyone can put ?__draft= in a URL, so the CMS checks two things, and neither needs configuration in your app. First, the pointer must name your site's own Deco API host, which remoteLoader looks up with your token. Any other host is ignored, so a crafted pointer can't make your server fetch from somewhere else. Second, the pointer carries a token signed by Studio, which the Deco API checks before serving the draft.

If a website wants to show drafts on its preview domain only, it checks the request's host before calling forDraft:

const host = new URL(request.url).host
const pointer = host === 'preview.store.example.com' ? draftPointer(request) : null
const client = pointer ? cms.forDraft(pointer) : cms.forRelease()

The token is the only secret. The site holds no other credential. Invalid or unexpected pointers are ignored and the request falls back to published content, never to an error page.

Connect Studio to your site

Studio opens previews on your site's URL, so the site has to be set up in the hosted Deco CMS with your token (creating a site and a token for this API is on the Roadmap). Support for sites on this API, including previews inside Studio's frame, is still being built; see the Roadmap. To try the mechanism locally: with only local files, forDraft returns the release, because the content module has no drafts. Testing a real draft needs a token.

Advanced

Block maps

A block map is the code half of the registry: a plain object from block type to function. The other half is the content map of saved entries, which you pass to createCMS as content. The quickstart's blocks.ts is one. This section covers what else can go in it.

Each key is a block type. Each value is a function (inputs) => value, where inputs is the block without its __resolveType: saved entries already expanded and merged, and nested calls already run, so the function receives values, never a pending call. Use satisfies Blocks rather than a type annotation: it checks the shape while keeping the concrete keys and function types, which is what the schema is generated from.

Keep the map a plain object at module level. The CLI reads the file without running it, so build it once and give it to createCMS. Only functions go in the map. Types that are pure data, such as pages, posts, and redirects, have nothing to run; they're declared for the CLI instead, see content that is only data.

The CMS is pure. It passes your function the block and nothing else: no context object, no request, no hidden state. When a block needs the current request, a cookie, or a route parameter, read it the way the rest of your app does, usually through request-scoped storage your framework already provides (Node's AsyncLocalStorage, which next/headers and TanStack Start's getRequest() use under the hood). That keeps block functions ordinary functions you can call and test directly.

Lazy loading

The map above imports every block at the top, so they all load with the map. That's fine for functions like seo. It's not what you want for a component that drags in a charting library, or for the two hundred components a large store has when any page uses five.

What's heavy is the component a block renders, and your framework already knows how to load components lazily. So do it in one place, the map, and let the block files stay plain components:

With TanStack Start, use React's lazy instead of dynamic. Where it goes depends on which of the two rendering modes you use (see Rendering), and the TanStack guides show the code. In every case the component files know nothing about the CMS, the map stays a plain object the CLI can read, and the bundler splits on the import().

For a block that's heavy for a non-UI reason, say a data function that pulls in a large SDK, a dynamic import inside the function body is enough. It's one line and needs no helper:

"catalog-product": async (input: ProductQuery) => {
  const { fetchProduct } = await import("./commerce")   // loaded on first call; the JS module system caches it after that
  return fetchProduct(input)
},

Keep import paths literal in both cases. A bundler can split import("./components/Product") into its own chunk; it can't split import(`./components/${name}`).

Choose type names that last

A block type's name is what content stores in __resolveType to call it, so pick it like a database column, not like a file path: short (seo, hero) or namespaced when a site has many (commerce/product). Moving a file only means updating an import; the name doesn't change. Renaming a type means migrating every block that uses it, or adding an alias, a second name for the same block type (see Renaming and migrating). Type names share one namespace with saved entry names (see Blocks), and deco schema fails on a clash (at runtime, the function wins). A simple convention avoids clashes: lowercase or kebab-case for block types (seo, product-card), capitalized names for entries (SummerSEO).

Advanced

Matchers and variants

Editors often want content that depends on a condition: a banner that only shows during a campaign, a title that changes on a date, an experiment. Two small ideas cover all of it, and neither knows what a website is, so they work the same in a website, a mobile app, or a background job (a script or cron task).

A variant is one of several alternative values for the same input, together with the rule that selects it. A matcher is a block function that returns a boolean, used as a variant's rule. A multivariate (after multivariate testing) is a block function that takes a list of variants, { rule, value } pairs, and returns the first value whose rule is true. It's three lines, so you own it and can change how it picks. Because the CMS resolves inputs before calling a function, the multivariate never sees a matcher, only booleans.

The three matchers that ship

They depend on nothing but the clock, so they're the only ones the framework provides:

import { always, never, date } from "@decocms/blocks/matchers";

// always()                              => true    the default rule of a variant
// never()                               => false   Studio hides a block by wrapping it in a variant whose rule is never()
// date({ start?: string; end?: string }) => boolean, true when now is inside [start, end]

start and end are ISO 8601 strings. A date without a time, like "2026-11-30", means midnight UTC, so add a time and offset ("2026-11-30T23:59:59-03:00") to end on your own clock.

Everything else that could gate content, a device, a cookie, a country, a user's plan, depends on where your app runs and how it sees its environment. Those are yours to write, below.

The multivariate is three lines you own

Editors compose them in Studio. Each variant is a tab, and its rule is picked from the matchers in your map. Variants are checked in order, so the one with the always rule goes last and catches everything else. A hero whose title changes for a campaign is a hero whose title is a multivariate:

// Means
hero({
  title: multivariate({
    variants: [
      { rule: date({ start: "2026-11-20", end: "2026-11-30" }), value: "Black Friday starts now" },
      { rule: always(), value: "New season, new arrivals" },
    ],
  }),
})

Resolution does the rest: each rule runs and yields a boolean, multivariate runs with those booleans and yields a string, hero runs with a plain title. Nothing in hero knows a variant was involved. The same shape wraps any block in a page, or the page's whole sections list, which is how Studio does page-level variants.

Write your own matcher

A matcher is any block function that returns a boolean. It reads whatever your app knows about the current request or user the way every other block does, through the context your runtime already provides:

Add them to the map and Studio's rule picker shows them next to date. The CLI lists every block function that returns a boolean as a matcher, which is how Studio knows to offer it in the rule picker (see what Studio reads). Combinators are matchers too: and, or, and not are one-liners over booleans, if you want them.

Every variant resolves

Inputs resolve before a function runs, so every variant's value resolves before multivariate picks one. For a title that's free. For two product queries it isn't, and a failure in a variant you didn't pick still fails the whole thing.

The lazy form is to make the values entry names instead of inline blocks. A string isn't a block, so nothing runs; the multivariate returns a name, and your app resolves it:

{
  "__resolveType": "multivariate",
  "variants": [
    { "rule": { "__resolveType": "date", "start": "2026-11-20", "end": "2026-11-30" }, "value": "BlackFridayHero" },
    { "rule": { "__resolveType": "always" }, "value": "DefaultHero" }
  ]
}
// Means
multivariate({
  variants: [
    { rule: date({ start: "2026-11-20", end: "2026-11-30" }), value: "BlackFridayHero" },
    { rule: always(), value: "DefaultHero" },
  ],
})   // the values are entry names, not calls: only the rules and multivariate run

// block is the JSON above, e.g. from a page's sections list;
// client.resolve accepts an entry name or an inline block
const [name, err] = await client.resolve(block);     // "BlackFridayHero"
if (err) throw err;
const [hero] = await client.resolve(name);           // only this variant ran

A variant is not access control. It chooses between values that are all fine to compute and show. Never use one to guard protected data or to decide whether a side effect runs; put that check inside the function that does the work.

If you cache rendered pages, at a CDN for example, anything a matcher looks at must be part of the cache key. Otherwise the first visitor's variant is cached and served to everyone: a page that varies by device would show the cached desktop hero to mobile visitors. See Caching and observability.

Websites

Routes, redirects, and content types

A content type is a kind of saved entry that holds data and runs no function, such as a page, a blog post or a redirect. Its name is the value of __resolveType. You declare your own in Content; page and redirect are built in, and deco schema always includes them (see Content that is only data). The framework also ships the Route interface, which any content type can extend to get a URL.

/** An entry that lives at a URL. Extend it to make a type routable. */
interface Route {
  /** @title Name */
  name: string;
  /** @title Path */
  path: string;        // "/summer", or a template like "/:slug/p"
}

/** A saved entry of the built-in `redirect` content type. */
interface Redirect {
  from: string;        // literal or template
  to: string;
  permanent: boolean;  // 301 or 302
}

A page is a route with SEO and a list of blocks (its sections field). It's not special to the router; it's just the first type that extends Route. It's shaped like the SummerSale entry in Blocks, with three additions: "__resolveType": "page", so the CMS can list it by type, and a name and path, so the router can find it. It's built in, so you don't declare it. To add fields, override it in Content (interface StorePage extends Page { … }; see Schema generation). It's exported from @decocms/blocks:

/** The built-in `page` content type. */
interface Page extends Route {
  seo: Block;                                       // an SEO block, or a reference to a saved one
  sections: VariantOf<Array<VariantOf<Block>>>;   // a list of blocks; the whole list, or any one block, can be a variant
}

Block is a block as stored: JSON whose __resolveType names a function or a saved entry. VariantOf<T> accepts a T or a multivariate block that picks one. Both fields are deliberately loose, because the package can't know your block types. To narrow them, override page: for example interface StorePage extends Page { seo: MySeoBlock; sections: Block[] }, then export type Content = { page: StorePage }.

// What its fields mean. page isn't a function, so the object stays data and you resolve each field separately.
{
  __resolveType: "page",
  name: "Summer campaign",
  path: "/summer",
  seo: seo({ title: "Sunny!", description: "Light layers for long days." }),   // SummerSEO, expanded
  sections: [hero({ title: "Summer starts here", image: "https://cdn.example.com/summer.jpg" })],
}

Two SDK functions turn these entries into URLs. client.list("page") returns every saved entry whose __resolveType is page. matchRoute(url, { routes, redirects }) picks the entry that matches a URL. Routing puts them together.

The router's rule is one line: an entry with a string path matches at that path. Route is what makes that intentional. The CLI checks that any type declaring path extends Route, so a stray path field on an unrelated block is a schema error rather than a surprise URL. Editors see name and path as ordinary fields on every routable thing, in Studio, which is how a marketing team gets /summer-sale live without a developer. Keep path and from plain strings, not blocks, so the router can match without running code.

Your own routable types

A blog doesn't want a page entry per post. Make Post extend Route, declare it in Content as post: Post, and pass the saved posts to matchRoute along with your pages (see Routing). Each post is then served at its own path:

Two entries with the same path, or two templates that can match the same URL, are rejected by the CLI and by matchRoute (see Path templates and match order).

Pages are data; resolve their fields

A page runs no function, so you never resolve the page itself. Read it, then resolve the blocks inside it: client.resolve(page.seo), and one client.resolve(block) per block in page.sections. Separate calls let each block render as soon as its own data is ready (see Rendering). A redirect is never resolved; matchRoute only reads it.

client.resolve("SummerPage") and client.list("page", { run: true }) fail with UNKNOWN_BLOCK, because page names no function, and the CMS never sees Content (see the rule). To read a page, list it, or pass { run: false }.

Running code for a whole page. If you want code to run for a whole page, such as validation or a layout step, add a page function to the block map and opt the built-in type out with page: never in Content, since a key can't be both. Then client.resolve(page) runs it after every block in the page has resolved.

Content types without a URL

Navigation, email templates, and campaign settings work the same way, minus Route: declare the type in Content if it's data, or register a function if something should run, and save entries of that type.

Websites

Rendering

A block function can return anything. For a website it usually returns something that becomes UI, and there are two ways to get that to the browser.

  • Descriptors (data mode): the block returns plain JSON such as { component: "product", props: {…} }, and a view registry in your app (an object mapping each component name to a React component) renders it on the server and again in the browser.
  • React Server Components (RSC): the block returns JSX that renders only on the server. React sends the result to the browser in its own wire format, called Flight, and only components marked "use client" ship JavaScript.

The CMS doesn't care which you pick; it returns whatever your block function returns. Each integration uses one of the two:

IntegrationBlock returnsStreamingShips to the browser
Next.js App RouterJSXServer Component Suspense boundariesClient Components
TanStack Start, dataSerializable descriptorsDeferred promises with AwaitThe view registry and its components
TanStack Start, RSCJSXRSC stream (Flight)Client references and the RSC runtime

Which mode to use

Use descriptors when views must render in an ordinary browser React app. Use RSC when your framework supports it and you want server-only view code to stay off the client. RSC doesn't guarantee smaller responses, so measure payload size, hydration, and navigation on real pages.

Block functions run on the server

In all three integrations, block functions run on the server, so data fetching belongs there. In data mode, a block returns a descriptor and a synchronous React view renders its props. With RSC, a block returns JSX that can include Client Components.

Don't put a Client Component (a component from a "use client" file) in the block map directly. On the server, importing it gives you a placeholder React can render but your code can't call, and the CMS calls every block function. Wrap it instead: cart: (input: CartProps) => <CartButton {...input} />.

Errors, streaming, and cancellation

  • Start every block first. Await critical data, such as SEO, only after all of the page's blocks have started, so they fetch in parallel instead of waiting behind the SEO call.
  • One Suspense boundary per block lets each block appear as soon as it's ready.
  • Suspense handles loading, not errors. Each client.resolve(block) returns [value, error]; render a fallback when error is set. Errors thrown later while React renders need an error boundary.
  • Cancellation is your app's job. The CMS never sees the request. A block that fetches upstream should take the request's signal from wherever your app keeps request state.
  • Once streaming starts, the status code is fixed. The status line and headers are already sent, so a later error can't change them. Decide 404s and redirects (the matchRoute result) before you stream.

Websites

Routing

The CMS doesn't route. It lists and resolves. Routing is three steps in your request handler: list the types you want at URLs, hand them to matchRoute, resolve the winner. Do all three with one client, so they see the same content even if editors publish mid-request (see One revision per response).

The example used here and in the guides

This page and the framework guides share these files: the model in src/model.ts, the post type in src/post.ts (from Your own routable types), and two content entries, stored as files in .deco/blocks, which deco content turns into the content module (see Content and loaders). Each guide's block map (src/blocks.tsx or src/blocks.ts) declares seo and its own product. Pages and redirects are built-in content types (see Content that is only data); the guides override page with StoredPage, below, to narrow its sections field, so Studio's form matches what the guide code reads.

In src/model.ts, ProductDescriptor is the descriptor a product block returns in data mode (see Rendering), and StoredPage is a page exactly as saved, before any of its blocks run.

StoredPage narrows the built-in Page type from Routes and redirects: it doesn't allow a variant around the whole sections list. Each guide's block map exports export type Content = { page: StoredPage }, so deco schema gives Studio the narrower form. If you keep the built-in Page, which does allow it, resolve the list first, const [list] = await client.resolve(page.sections), which picks the variant and also runs every block in it, or store the variant's values as entry names as in Every variant resolves.

// Means (page isn't a function, so the object stays data; the blocks inside it are calls)
{
  __resolveType: "page",
  name: "Product page",
  path: "/:slug/p",
  seo: seo({ title: "Summer shirt | Deco example", description: "A small example of independently resolved fields." }),
  sections: [
    product({ id: "details", name: "Summer shirt", price: 49, currency: "USD" }),
    product({ id: "related", name: "Related shirt", price: 39, currency: "USD" }),
  ],
}
// product is whatever each guide's block map registers: JSX in Next.js and TanStack RSC, a descriptor in data mode

The redirect sends /old-products/summer to /summer/p. The page uses literal product values to keep the example small. A real page would use a block that fetches the product for the slug, reading match.params from your app's request state (see Block maps).

Route a request

With those files in place, this is the whole request handler:

import { matchRoute, type Redirect } from "@decocms/blocks";
// cms comes from cms.ts (see Quickstart); request is the incoming Request; render/renderPost are your own view code
// error handling omitted: check the second tuple element in real code, and catch matchRoute's throw (see below)

const client = cms.forRelease();
const [pages]     = await client.list<StoredPage>("page");   // as saved: seo and sections are still blocks
const [posts]     = await client.list<Post>("post");
const [redirects] = await client.list<Redirect>("redirect");

const match = matchRoute(request, { routes: [...pages, ...posts], redirects });

switch (match.kind) {
  case "not-found":
    return new Response("Not found", { status: 404 });
  case "redirect":
    return Response.redirect(new URL(match.location, request.url), match.status);
  case "match":
    switch (match.entry.__resolveType) {
      case "page": {
        const blocks = match.entry.sections.map((b) => client.resolve(b));   // start them all
        const [seo] = await client.resolve(match.entry.seo);                   // then await
        return render(seo, blocks);
      }
      case "post":
        return renderPost(match.entry);                                        // data: nothing to resolve
    }
}

Mount this handler as your app's catch-all route, the one that runs when no other route matches.

kindFields
"match"entry (the stored route you passed in) and params from the path template.
"redirect"location with parameters filled in, and status (301 or 302).
"not-found"None

matchRoute is a helper, not a requirement. The CMS has no idea what a URL is. If your framework already routes, or you'd rather read a page by name (client.resolve("SummerPage", { run: false }), then resolve its fields) or find it by a field of your own, skip it. It exists because "an editor typed a path into Studio and that page is now live" is the common case, and getting precedence and parameters right by hand is tedious.

Which types route is your decision, per handler: a blog lists post, a docs site lists doc. match.params holds the URL parameters; hand them to your code however your app shares request state. The CMS never injects them into blocks.

For example, with Node's AsyncLocalStorage: export const routeParams = new AsyncLocalStorage<Record<string, string>>(). Wrap rendering in routeParams.run(match.params, () => render(…)), and a block reads routeParams.getStore()?.slug. The Block maps page covers request-scoped state in more detail.

Matching is a lookup, not a scan: entries are compiled into a segment trie (a tree keyed by path segment), so a lookup costs the URL's depth, not the number of routes. The trie is cached per routes array object, so passing the same array again skips the build. The handler above builds a new array per request, which rebuilds the trie each time; that's one pass over the paths, fine for most sites. Reusing one array per revision needs the client to expose its revision, which is on the Roadmap. The algorithm is described under the hood.

Path templates and match order

A route's path and a redirect's from accept literal segments and named parameters. A route at /:slug/p matches /summer/p with params.slug = "summer". Redirects are checked before routes, so a redirect overrides a route at the same path. Within each group, exact paths win over templates. Two entries with the same path, or two templates that can match the same URL, make matchRoute throw. deco schema reports the same conflict, so run it in CI on every commit, including the content commits Studio makes. Content published without that check can still make matchRoute throw at request time, so catch the error and return a 500 rather than crash (removing the throw is on the Roadmap). Serve framework endpoints, API routes and static assets from their own routes, so they never reach this catch-all.

Linking and listing

Because the URL is a field, linking to an entry is reading it, and listing a routable type gives you an index for free:

const [posts] = await client.list<Post>("post", { sort: (a, b) => b.date.localeCompare(a.date) });
for (const post of posts) link(post.path, post.name);          // "/blog/hello-world", "Hello, world"
// link() stands in for your framework's <Link> or an <a href>

const match = matchRoute("/blog/hello-world", { routes: posts });
// { kind: "match", entry: { __resolveType: "post", name: "Hello, world", path: "/blog/hello-world", … }, params: {} }

API reference

createCMS(config)

createCMS returns a CMS: your block map plus your content. Create it once, at module scope; it returns the same instance for the same configuration (see One instance per process). For each request, ask it for a client: forRelease() for visitors, forDraft(pointer) for a preview. A client loads one revision on first use and reads only that revision afterwards, so everything in one response agrees. Every later call, list or resolve, reuses that content, so a page's blocks can stream as separate calls; the next request's client sees the next revision, so don't share a client across requests. A client also remembers what it has already resolved: an entry referenced three times runs its function once per client. That memory is tied to the client and to the block map object (results are kept per function of the map you passed), so a map rebuilt inside your handler starts with an empty cache; build the map once at module scope. Clients are cheap to create, because the CMS caches the content.

  • every interval, which defaults to DECO_CONTENT_INTERVAL or 60 000 ms and is never below 60 000;
  • each check one interval, plus or minus up to 10 s, after the previous one (60 s ± 10 s by default), fetching only the revision hash;

Draft pointers

A pointer is a string, <host[:port]><path[?query]>@<version>, that names where a draft lives and which version it is. Studio makes them; forDraft reads them. Two helpers cover everything in between:

interface DraftPointer {
  host: string;      // host[:port] of the Deco API, e.g. "studio.decocms.com"
  path: string;      // starts with "/"; its query holds a token signed by Studio
  version: string;   // opaque, immutable: the branch head or ETag
}

function parseDraftPointer(raw: string | null | undefined): DraftPointer | null;
function formatDraftPointer(pointer: DraftPointer): string;

parseDraftPointer is strict and returns null on anything unexpected: a scheme, a stray @, an unrooted path, an odd character in the host or version. It's what forDraft calls, so an app only needs it to look inside a pointer, for example to show which version is being previewed, to key a cache on version, or to reject a pointer before storing it in a cookie. formatDraftPointer is the inverse, for building one from parts, as a mobile app might from a deep link.

For websites, two more helpers do the handshake, so the parameter and cookie names never appear in app code:

Releases and deployment

Your code ships when you deploy. Your content can ship the same way, or on its own. This page covers how a content change reaches visitors, how each response stays consistent, and what happens when the network fails. It rests on one idea from Content and loaders: a revision identifies one exact content map. deco content, remoteLoader and the Deco API all compute it as the same hash of the whole map, so two copies of the content are the same exactly when their revisions match, and remoteLoader recognizes the build's content module as the current release and skips a download. A loader you write only has to change its revision whenever content changes (see Write your own loader).

A revision never changes once it exists: change any entry and you get a new revision. That makes a revision a safe cache key everywhere.

Publishing

With the hosted Deco CMS, publishing is committing. A developer or an agent edits the entry files in your content directory (.deco/blocks, or the folder you give the CLI's --root) and pushes; an editor saves in Studio, which commits to the same repository. (If you load from your own store, see Content and loaders.) Either way, the production branch (the branch the hosted Deco CMS publishes from, usually main) moves.

Publishing takes seconds: the Deco API serves that commit as the current release as soon as it lands. Each server checks for a new release about once a minute, at an idle moment, so a publish is live everywhere within about a minute. Calling cms.update(), for example from a webhook, checks at once, but only on the server or isolate that receives the call; every other one picks the release up on its next check (see Loaders). Requests never wait on this: load() always returns from memory, and the check runs in the background. Step by step: under the hood.

Because content and code share one history, a deploy and a content change are the same kind of event: a commit. Rolling content back is reverting one.

Content can't get ahead of code. remoteLoader tells the Deco API which schema your build shipped with (a hash of the committed .deco/schema.json), and the API serves only releases whose content fits that schema. That's why the schema must be regenerated and committed with every code change; run deco schema in CI. If a commit adds a block type the deployed build doesn't have, visitors see that commit only after you deploy the code that defines the type; until then, the loader keeps serving the previous release. (Sending the schema hash is part of the Deco API release service, still on the Roadmap.)

Fallback

Until a server has fetched its first release (a new server, or one that has never reached the Deco API), remoteLoader serves its fallback's content. If the Deco API becomes unreachable later, the server keeps serving the newest release it already has. With the content module, that's the content the build shipped with, the content this deploy was tested against, so it's always there and always compatible with the code. If your content is a loader you wrote (see Write your own loader), keeping those guarantees is up to you. remoteLoader always switches between whole revisions, never mixing entries from two of them, because a mix can break references or bring back deleted entries. The loader reports the revision it actually served.

One revision per response

Because new content can arrive in the background at any moment, two reads a few milliseconds apart could see different revisions; a header from one and a footer from the other make an inconsistent page. A client prevents that: its first call picks a revision, and every later list and resolve on it, including concurrent ones, uses the same one. So make one client per request.

Follow-up requests from the browser may land on a newer revision. If data must match the HTML, render it in the same response. (A way to read and pin the served revision is on the Roadmap.)

A revision only selects content; it isn't a secret and unlocks nothing. Unpublished drafts are protected by the signed token in the draft pointer (see Preview).

Renaming and migrating

Saved content refers to your code by name: every block stores a type name in __resolveType, references store entry names, and inputs are stored by field name. Treat these names like database columns: once content uses them, changing one breaks that content. Renaming a type or removing an input affects every block that uses it, and renaming a saved entry breaks every reference to it (NOT_FOUND).

This page covers renaming safely, and bringing in content from a site built on Deco's earlier framework, where type names were file paths such as site/sections/Product.tsx. Moving source files is free; only names matter.

Rename a type with an alias

An alias is another key pointing at the same thing: the same function in the block map, or the same type in Content. Content that stores the old name keeps working, and routing is unaffected because matchRoute looks at each entry's path field (see Routes and redirects), not its type name. export default {
  "product-card": productCard,

deco schema rejects an alias that collides with an entry name.

Checklist for migrating existing content

  1. Keep existing names. If the content stores file-path type names, register them as they are or alias them.
  2. Check inputs. Regenerate the schema and validate saved content. Review new required fields, narrowed unions, and changed defaults.
  3. Migrate the content in one commit. A script reads the JSON in .deco/blocks, rewrites it, and writes it back. The commit is a new revision you can revert in one step. Keep fields the script doesn't recognize instead of deleting them, and report references to missing entries (NOT_FOUND) instead of dropping them.
  4. Test the integration. Load real pages against the migrated content: routes resolve, titles and SEO tags are right, blocks that load later (if your framework streams them) appear, failing blocks show their fallback, and navigation works.
  5. Keep a rollback pair. Keep the previous build plus the content revision it was tested with. Rolling back content alone can't bring back code you removed.

Test behavior, not just schemas. A function can keep its input type and still change its output, defaults, or upstream calls.

How remoteLoader stays current

The rule that matters: a production request never waits for the network. load() returns from memory, immediately, every time. Staying current happens beside requests, not in front of them.

Request path · synchronous, never touches the network

Requestclient.list or client.resolve
→

→

  1. Serve from memory. load() returns the newest release this process has fetched, or, if it hasn't fetched one yet, the fallback's content. A freshly started server (a cold start) serves the content the build shipped with on its very first request.
  2. Ask for the hash. In the background, on first use and then every interval, update() fetches only the current revision hash from the API. That's a few bytes. The interval is one minute by default; set it with interval or the DECO_CONTENT_INTERVAL environment variable, never under 60 000 ms. Each check is scheduled one interval, plus or minus up to 10 s, after the previous one (60 s ± 10 s by default; the random part is called jitter), so servers that started together don't check together. A check that's due waits for an idle moment, a gap when the process has nothing else to do:
    • requestIdleCallback where it exists (browsers, React Native);
    • otherwise scheduler.postTask({ priority: "background" });
    • otherwise setTimeout;
    • on Node, an unref'd timer (one that doesn't keep the process alive) plus setImmediate, so it never keeps the process running;
    • on Cloudflare Workers, which run no timers between requests, after the response inside ctx.waitUntil (the Worker's way to finish work after a response is sent), automatically.
    Updating never competes with rendering, and a request never waits. There's no push signal: servers ask, the API never calls them.
  3. Compare. If the hash equals what's in memory, there's nothing to do. If it equals the fallback's revision, the content the build shipped with is current: the loader uses it and never downloads it. This is the common case right after a deploy: the content module's revision is the CLI's copy of the same hash. A loader you write with its own revision scheme is downloaded once.
  4. Fetch and swap. Otherwise it fetches that revision, checks that the content hashes to it, and swaps it in whole. The API answers only with releases whose content fits the schema the build shipped with (see Publishing), so content never gets ahead of code. Requests in flight keep the revision they started with.
  5. Fail quietly. Any network or validation error leaves memory as it was, so a server that loses the API keeps serving the newest release it has. Nothing reaches a request.

So different servers can briefly serve different releases, by design. A published change reaches each server on its next check, within about a minute (or at once on the one server where you call cms.update()), and each server sends one tiny request per interval, however much traffic it serves. (This is called eventual consistency.)

Drafts are the opposite: a preview must show exactly the version Studio asked for, so load(pointer) fetches that version and waits for it, cached by version afterwards. If the draft can't be fetched, the client serves what a normal request would get: the newest release in memory, or the build's content if none has been fetched yet. It never mixes draft and published entries.

One instance per process

A cache and a poller only help if there's one of each. createCMS and remoteLoader store their instances on globalThis, under keys made with Symbol.for("decocms.blocks…"). Symbol.for returns the same symbol for the same string anywhere in the process, so two copies of the package, from two bundles or from a dev reload (hot module replacement, HMR), find each other's instances. Without it, each copy would keep its own cache and run its own poller, doubling the memory and the checks. The key is derived from the configuration (the site token and the content's identity: for the content module, the .deco folder it was generated from; for a loader you write, the loader object. Never the revision, so a hot reload that hands in new content keeps the same instance), so several sites in one app get separate instances. A second call with the same key but different options, such as another interval, keeps the first instance and logs a warning that names the conflicting options, so there is still only one cache and one poller and the mismatch is visible. resetForTests() clears every stored instance.

A loader you write that has update() is checked the same way: the CMS calls its update() on this idle schedule and interval. To configure remoteLoader, see Configuring content; for what a release is, see Releases and deployment.

How matchRoute matches

The naive version of this function walks every entry and tests each path against the URL. That's fine for fifty pages and wrong for fifty thousand. matchRoute instead compiles the entries into a segment trie, once per list, and matches in time proportional to the URL's length, not the catalog's size.

A segment is one piece of a URL path between slashes: /blog/hello has the segments blog and hello. A trie is a tree where each edge is one segment, so paths that start the same share nodes.

/summer                 /:slug/p                /blog/:slug             /blog/archive
                                    ┌── root ──┐
                                    │           │
            ┌───────────────────────┼───────────┼──────────────────┐
         "summer"                "blog"                        :slug
            │                       │                            │
        [SummerPage]     ┌──────────┴──────────┐                "p"
                     "archive"                :slug               │
                         │                      │           [ProductPage]
                    [BlogArchive]           [Post …]

Top: four route paths. Below: the trie built from them. Quoted words are literal segments, :slug is a parameter, and [Brackets] mark the entry stored at that node.

  1. Build, once per list. Every path is split on / and inserted segment by segment. A literal segment becomes a named child; a :param segment becomes the node's single parameter child. The entry is stored at the leaf. Cost is the total number of segments, and the result is cached in a WeakMap keyed by the array you passed, so the second call with the same array skips this entirely. A new array rebuilds the trie, which is one pass over the paths.
  2. Reject ambiguity while building. Two entries reaching the same leaf, or two parameter children under one node (/:slug/p and /:id/p have the same shape, so every URL that matches one matches the other), throw with both names in the message. The CLI runs the same build at schema time, so running deco schema in CI on every commit, including Studio's, catches it before it ships.
  3. Match, one segment at a time. Walk the URL's segments from the root. At each node try the literal child first, then the parameter child. If a branch dead-ends, go back up and try the parameter child you skipped. Each node has at most one literal match and one parameter, so a lookup visits about as many nodes as the URL has segments, however many entries exist.
  4. Precedence falls out of the walk order. Trying the literal child before the parameter child at every node is exactly "exact paths win over templates", per segment rather than per path: /blog/archive beats /blog/:slug for /blog/archive, and /blog/:slug still serves /blog/hello-world. No sorting, no regex.
  5. Redirects are a second trie, checked first, with the same rules. A hit fills the parameters into the redirect's to path and returns { kind: "redirect", location, status }.

Before matching, the URL is normalized: percent-decoded, query and fragment dropped, trailing slash removed except for /. Parameters capture one segment and never contain a slash. That's the whole algorithm; it's the same shape as the routers in Fastify and Hono, and it's about a hundred lines.

Deco Studio compatibility

What Studio reads

Studio learns about your site from your site. Your app serves a few HTTP endpoints for it. The main one, /live/_meta, returns the schema the CLI wrote; Studio also calls your app to render previews (/live/previews), to run functions for pickers and the Run button (/deco/invoke), and to encrypt secret fields (/live/invoke). In today's packages, these handlers come from @decocms/blocks-admin; how the new API mounts them is on the Roadmap. Studio also reads your content files in .deco/blocks. Everything Studio knows about the shape of your content comes from the schema, so it's all inferred from your types; the other endpoints run your code, they don't describe it.

The schema file has two parts. definitions holds one JSON Schema per type: the form Studio shows. manifest lists every key of your block map and your Content type, grouped by kind, so Studio knows which keys render UI, which are rules, and so on. The group names are Studio's, inherited from Deco's previous framework. Each manifest entry points at its definition with a JSON Schema $ref. The CLI picks the group from the type:

Three conventions follow from this, and they're the ones the rest of the doc already uses. A key is a block type if it's in the manifest and a saved entry if it isn't, so short names like hero are fine, as long as no saved entry uses the same name (see Blocks). A variant is { "variants": [{ "rule": …, "value": … }, …] }. The first variant whose rule is true wins, so the default, with the always rule, goes last. A redirect is a flat { from, to, permanent } entry.

Studio compatibility today

Deco's previous framework named every block type by the path of the file that defined it, so a page type was website/pages/Page.tsx and the always-true rule was website/matchers/always.ts. Today's Studio was built for that framework and still expects those names. It decides whether a key is a block type or a saved entry by checking for a file extension, and it finds pages, the always rule (the default variant), the never rule (how it hides a block) and multivariate (website/flags/multivariate.ts) by their old paths.

Until Studio reads the manifest instead, the CLI bridges the gap: for the types Studio looks up by name, it also writes the old path into the manifest as an alias (a second key for the same type). Content Studio saves under an old name resolves through the same alias mechanism your own renames use. Your code uses page and always; the manifest carries both spellings; nothing in the SDK changes.

Two gaps remain. Redirects created in Studio are saved in the old nested shape, not the flat one from Routes and redirects:

// Saved by today's Studio
{ "__resolveType": "website/loaders/redirect.ts",
  "redirect": { "from": "/campaigns/summer", "to": "/summer", "type": "permanent" } }

// The shape these docs use
{ "__resolveType": "redirect", "from": "/campaigns/summer", "to": "/summer", "permanent": true }

matchRoute accepts both. And Studio's file-extension check must become a manifest lookup before a site can drop the aliases. Both are Studio work, tracked in the Roadmap, not something sites do.
