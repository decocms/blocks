# Troubleshooting

Most problems come down to three facts: which revision this server is serving, which entry was asked for, and which block type it names. Until the client exposes its revision (see the [Roadmap](/roadmap#roadmap-api--add-a-revision-handle)), build the loader yourself (`const loader = remoteLoader(content, { site, token })`), pass it as `createCMS`'s `content`, and log `(await loader.load()).revision`; that's the revision a new client would read right now. To see an entry with references expanded but no function run, call `client.resolve(target, { run: false })`. To see it exactly as stored, open `.deco/blocks/<name>.json`.

| Symptom | What to check |
|---|---|
| `UNKNOWN_BLOCK` | Compare `__resolveType` with your block map's keys, including case. Add an [alias](/next/adoption) for renamed types. If the function does a dynamic `import()`, confirm the imported module has a default export. |
| `NOT_FOUND` | A string target is always an entry name, never a block type. Confirm the entry exists in the served revision, that `createCMS`'s `content` is the content you expect, and that `deco content` ran after the file was added (see [Configuring content](/next/content#configuring-content)). To run a type directly, pass an inline block: `client.resolve({ __resolveType: "seo", … })`. |
| `CYCLE` | Follow the references in `error.path` and remove the one that leads back to an entry already being expanded. |
| My saved entry is ignored | A block type probably has the same name, and the function wins. Run `deco schema`, which reports the collision, and rename the entry. |
| Blocks come back as JSON instead of running | You called `client.list` without `{ run: true }` (it returns saved entries by default), or you passed `{ run: false }` to `resolve`. To run listed entries, pass `run: true`, or resolve the fields you need with `client.resolve`. |
| A function runs more than once per request | A client runs each block once and reuses the result, but only within that client and for that block map object. Make one client per request, not per component, and create the block map at module level, not inside your handler. |
| Wrong fields in the editor | Regenerate the schema from the right `blocks.ts`. Check the first parameter's type and its property JSDoc (see [Schema generation](/next/schema)). |
| Serialization error when sending a block's result to the browser | JSON can't carry functions or React elements. Return plain data (descriptors, see [Rendering](/next/rendering)), or use an integration that renders on the server, like [TanStack RSC](/next/tanstack-rsc) or [Next.js](/next/nextjs). |
| Hydration mismatch (React's browser render doesn't match the server's HTML) | Look for time-dependent or random rendering, and for request context the server and browser see differently. If the browser fetches data after the page loads, it may get a newer revision; render data that must match the HTML in the same response. |
| Content changes mid-response | Use one client for the whole response; a client never changes revision. If you wrote the loader, check that it never returns different content under an existing revision. |
| Stale or fallback content | Compare the revision your server serves (see above) with the revision of the latest release. A server that hasn't fetched a release yet reports its fallback's revision, which matches when the fallback is the content module. If they differ, the server hasn't checked yet: allow about a minute after publishing. See [Releases and deployment](/next/releases) and [how remoteLoader stays current](/next/loader-internals). |
| `UNKNOWN_BLOCK` right after publishing | The content uses a block type the deployed code doesn't have, usually because the content went out before the code that defines the type, or the code was rolled back to a version without it. Deploy the code, or revert the content commit. See [Keep the schema compatible](/next/schema#keep-the-schema-compatible). |
| A new content file isn't found in development | Run `deco content`, or keep `deco content --watch` running beside your dev server. Only adding or removing a file needs it; edits to an existing file hot-reload. |
| Warning about an instance with different options | `createCMS` (or `remoteLoader`) ran twice with the same site, token and content but different options, such as another `interval`. The first instance is kept. Create the CMS once, at module scope (see [One instance per process](/next/standalone#one-instance-per-process)). |
| Studio can't reach `deco content serve` | Check that the server is still running and that you opened the link from this run: a restart prints a new token, and Studio asks you to reconnect. Allow the browser's prompt to let Studio reach your machine (Local Network Access). If you use another browser origin than Studio's, pass it with `--allow-origin`. See [Studio and the content protocol](/next/studio-protocol#edit-your-local-checkout). |
| A form field in Studio is a text box instead of a picker | Studio never runs your code, so options that would come from a function aren't available in this version. Give the field a string-literal union, an enum or an `@options` list, and run `deco schema` (see [Annotate fields with JSDoc](/next/schema#annotate-fields-with-jsdoc)). |
| No telemetry reaches Deco | Telemetry needs both `site` and `token` on `createCMS`, and an enabled [Telemetry entry](/next/operations#telemetry-settings-are-content). Error logs are sampled and metrics are sent in batches, so expect a delay and only a share of errors. |
| Warning that `interval` was raised | The minimum is 60 000 ms (one minute); lower values, from `interval` or `DECO_CONTENT_INTERVAL`, are raised to it. |
