# Your content in Git

Everything the people who run your site decide, from the text on a promo banner to the blocks on the home page, is saved as JSON files in your repository. This page shows where those files live, how your app reads them, and how a change reaches visitors.

## Content is files in your repository

Your content lives in `.deco/blocks`, one JSON file per piece of content:

```text
.deco/
├── blocks/
│   ├── HomePage.json
│   ├── PromoBanner.json
│   └── SummerSEO.json
├── schema.json      generated by deco schema; commit it
└── blocks.gen.ts    generated from the files (see below); gitignore it
```

Here's one of them, the free-shipping bar at the top of the store:

```json title=".deco/blocks/PromoBanner.json"
{
  "__resolveType": "promo-banner",
  "title": "Free shipping over $50",
  "href": "/summer"
}
```

Each file is a **saved entry**, and its file name without `.json` is the entry's name: this one is `PromoBanner`.

`__resolveType` names the block type the entry is for: one of your functions, here `promo-banner`, the one that renders the bar (your [block map](/next/manifest) lists them). The other fields are its inputs. Entries can also contain other blocks and refer to each other by name, which is how a page is built; [Blocks](/next/model) covers that.

These files change in three ways, and every change ends up as a commit:

- **Developers** edit them like any other file in the repository.
- **AI agents** edit them directly, with the file tools they already use.
- **Editors** use [Studio](/next/studio), which shows each entry as a form built from your types. Studio commits each save to a draft branch in your repository through its GitHub integration, and publishing a draft brings it to your production branch.

Because content is files in Git, you get what you already have for code: history, review in pull requests, branches, and rollback by reverting a commit.

## The content module

Your app doesn't read the folder itself. The SDK never touches the filesystem, so the same code runs on Node, Cloudflare Workers, Deno, Bun, React Native and in browsers. Instead, the CLI turns the folder into an ordinary module your app imports:

```bash
npx deco content
```

That writes `.deco/blocks.gen.ts`, the **content module**. It imports each JSON file (the `with { type: "json" }` clause is a JSON import attribute) and exports them together:

```ts title=".deco/blocks.gen.ts (excerpt)"
// Generated by deco content; don't edit.
import HomePage from "./blocks/HomePage.json" with { type: "json" };
import PromoBanner from "./blocks/PromoBanner.json" with { type: "json" };
// … one import per file

export default {
  revision: "b1946ac92492d2347c6235b4d2611184",
  blocks: { HomePage, PromoBanner /* , … */ },
};
```

`blocks` holds your saved entries by name, the **content map** that [Blocks](/next/model#name-a-composition-reuse-it) refers to, and `revision` is an ID the CLI computes from their contents (see [Snapshots and revisions](#snapshots-and-revisions)).

Pass the module to `createCMS`, next to your [block map](/next/manifest), the object that maps each block type to its function:

```ts title="cms.ts"
import { createCMS } from "@decocms/blocks";
import content from "./.deco/blocks.gen";
import blocks from "./blocks";

export const cms = createCMS({ blocks, content });
```

Now your code can ask for an entry by name. `cms.forRelease()` gives you a **client** over your published content (with plain files, that's what's in the content module); make one per request. Its `resolve` method finds the entry, calls the function it names with the saved inputs, and returns the result, paired with an error instead of throwing (see [Quickstart](/next/quickstart)):

```ts
const client = cms.forRelease();
const [banner, error] = await client.resolve("PromoBanner");
// the same as promoBanner({ title: "Free shipping over $50", href: "/summer" })
```

That's all resolving means for a single entry. When entries contain other blocks or refer to each other, `resolve` expands and runs those too; [Blocks](/next/model#resolving-a-page-step-by-step) walks through a whole page.

The content module is generated, so add it to `.gitignore`, like TanStack Router's `routeTree.gen.ts`, and run `deco content` before your dev server and your build:

```json title="package.json"
{
  "scripts": {
    "predev": "deco schema && deco content",
    "prebuild": "deco schema && deco content"
  }
}
```

Both commands are described in [CLI reference](/next/schema#the-two-cli-commands). Because each file is an ordinary import, editing one reloads through your framework's own hot module replacement (HMR, which swaps changed modules into the running app without a restart), and the new content is handed to the running CMS. Only adding or removing a file needs `deco content` again, or `deco content --watch` left running beside your dev server. To have Studio edit your local files while you develop, run `deco content serve` (see [Edit local content from Studio](/next/schema#edit-local-content-from-studio)); you commit its changes as usual.

To keep content in another folder, point the CLI at it and import from there: `deco content --root ./content/.deco`, then `import content from "./content/.deco/blocks.gen"`.

## Publishing is committing

There is no separate publish step: publishing is a commit to your production branch (usually `main`). A developer or an agent commits a file in `.deco/blocks` and pushes, or merges a pull request; an editor publishes a draft in Studio, which brings its commits to that branch. (Running `deco publish` only prints this explanation, so an agent that tries it learns to commit instead.)

On its own, the content module ships with your code, so a commit goes live with your next deploy, like any other change.

## Go live without a deploy

With the hosted Deco CMS, a published commit doesn't wait for a deploy. Add your site ID and site token to `createCMS` (see [Configuring content](#configuring-content)).

Each commit to your production branch (usually `main`) becomes a **release**, one published version of all your content. The Deco API serves it within seconds, and each server running your app picks it up on its next check, about once a minute, in the background: a request never waits for it. The content module stays as the fallback, so a new server, or one that can't reach the Deco API, serves the content your build shipped with. [Releases and deployment](/next/releases) follows a commit step by step.

The same two values turn on previews and telemetry. A **draft** is the editor's saved changes on their draft branch, not published yet. Studio opens your real site with that draft, so the editor sees exactly what visitors will see once it's published (see [Preview](/next/preview)). And your site sends its [telemetry](/next/operations#telemetry) to the Deco API.

<Callout>**Status.** Issuing site tokens for this API isn't available yet; see the [Roadmap](/roadmap#roadmap-platform--build-the-deco-api-release-service).</Callout>

## Configuring content

```ts title="cms.ts"
import content from "./.deco/blocks.gen";

// Your files, shipped with each deploy
createCMS({ blocks, content });

// Releases from the hosted Deco CMS, with your files as the fallback
createCMS({ blocks, content, site: process.env.DECO_SITE, token: process.env.DECO_SITE_TOKEN });

// Check for new releases every 2 minutes instead of every minute
createCMS({ blocks, content, site: process.env.DECO_SITE, token: process.env.DECO_SITE_TOKEN, interval: 120_000 });
```

`site` is your site's ID in the hosted Deco CMS, and `token` is its site token. Read them from environment variables, by convention `DECO_SITE` and `DECO_SITE_TOKEN`. The site ID isn't a secret; the token is, so keep it out of the repository. When either is undefined, in development for example, the CMS reads `content` only and sends no telemetry, so the same line works everywhere.

`interval` is how often each server checks for a new release, in milliseconds. It defaults to the `DECO_CONTENT_INTERVAL` environment variable, or 60 000 (one minute) when that's unset. The minimum is 60 000: lower values are raised to one minute, with a warning. Each check runs one interval, plus or minus up to 10 seconds, after the previous one; [Under the hood](/next/loader-internals) has the details.

On Cloudflare Workers with several megabytes of content, see “Large content on Workers” under [Create the CMS](/next/tanstack-data#2-create-the-cms). `content` also accepts any object with a `load()` method that returns a snapshot, for cases the content module doesn't cover; the `Loader` interface is in the [API reference](/next/standalone#loaders).

## Snapshots and revisions

The content module's default export, `{ revision, blocks }`, is a **snapshot**: one fixed copy of your content map. The CMS always works with a whole snapshot at a time, never with single files. The field is called `blocks` for compatibility with Studio's file format, but it holds saved entries: any JSON, never functions. Functions only ever come from your block map.

The revision names that exact set of entries, like a version number. The CMS and your app use it to tell when content changed, to keep cached data from different versions apart, and to tell one release from the next. Any change to any entry produces a new revision, and a revision is never reused for different content. `deco content` and the Deco API compute it the same way, as a hash of the whole map, so two copies of the same content get the same revision wherever they're computed; [Releases and deployment](/next/releases) shows what that buys you.

To read an entry exactly as stored, with references in place, index the map: `content.blocks["PromoBanner"]`.
