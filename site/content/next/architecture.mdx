# How it works

<Callout>**Status.** Deco Blocks is being designed in the open: the API on these pages is proposed and not released yet. The [Roadmap](/roadmap) lists what's left.</Callout>

Deco Blocks lets the people who run a site change what your code does without changing the code. You write ordinary TypeScript functions. The values they're called with, such as a headline, a banner image or the share of visitors who see a new checkout, live as JSON files in your repository. Editors change those files in a visual editor, AI agents edit them directly, and your app reads them at runtime and calls your functions with them.

Deco Blocks has two pieces you install, and one you don't:

| Piece | What it does | Where it runs |
|---|---|---|
| **SDK** `@decocms/blocks` | Reads your content (a module the CLI generates from files in your repo, the hosted Deco CMS, or your own store) and calls your functions with it. | Your app, in any JavaScript runtime: Node, Cloudflare Workers, Deno, Bun, React Native or the browser |
| **CLI** `@decocms/blocks-cli` | Provides the `deco` command. `deco schema` generates a JSON Schema from your types (and, in CI, checks a change against the previous one), and `deco content` turns your content files into a module your app imports. | Your machine or CI |
| **Studio** | Builds a visual editor from that schema and saves edits back to your files. | Part of the hosted Deco CMS (optional) |

The SDK and CLI are open source and run without a Deco account. The **hosted Deco CMS** is Deco's optional service. It adds **Deco Studio**, the visual editor, and the **Deco API**, the HTTP service that delivers published content and draft previews to your app without a redeploy, using your site's token.

## Key terms

These terms come up on every page. Each is explained again where it's first used.

<Terms>
  <Term name="Block function">One of your functions with a typed first parameter, registered in a block map. It can return anything: data, a boolean, a descriptor or JSX. The framework treats them all the same. See [Quickstart](/next/quickstart).</Term>
  <Term name="Block map">A plain object of your block functions, such as `{ experiments }`. See [Quickstart](/next/quickstart).</Term>
  <Term name="Block type">A key in the block map: the name content uses to call that function.</Term>
  <Term name="Block">Either a function (code) or saved content (JSON), named by `__resolveType`. A function is a key in your block map and ships with each deploy. Saved content is a saved entry: it's versioned, can have drafts, and publishes without a deploy. The JSON that calls a block, `{ "__resolveType": …, …inputs }`, is called a block too. See [Blocks](/next/model).</Term>
  <Term name="Saved entry">Saved content: a block saved under a name, one JSON file in `.deco/blocks`, whose file name is the entry name. See [Content and loaders](/next/content).</Term>
  <Term name="Content module">`.deco/blocks.gen.ts`, the file `deco content` generates from `.deco/blocks`. It imports each JSON file and exports a snapshot, `{ revision, blocks }`: one fixed copy of all your saved entries. See [Content and loaders](/next/content).</Term>
  <Term name="Content map">All saved entries, keyed by name.</Term>
  <Term name="Page">A built-in content type: a saved entry with a path, SEO and an ordered list of blocks (its `sections` field) that editors add, remove and reorder. See [Routes and redirects](/next/content-types).</Term>
  <Term name="Loader">Any object whose `load()` returns `{ revision, blocks }`. Pass one as `createCMS`'s `content` to read content from a key-value store, a database or your API. See [Content and loaders](/next/content).</Term>
  <Term name="Revision">The ID of one exact content map, released or not, usually a hash of its contents. Change any entry and you get a new revision.</Term>
  <Term name="Release">A published content map. With the hosted Deco CMS, each commit to the production branch becomes one. A release never changes, and its revision identifies it. See [Releases and deployment](/next/releases).</Term>
  <Term name="Draft">Content changed in Studio but not yet published, kept on a branch. See [Preview](/next/preview).</Term>
  <Term name="Client">The object you read content with, one per request: `cms.forRelease()` for visitors, `cms.forDraft(pointer)` for a preview. It has two methods, `list` and `resolve`. See [Quickstart](/next/quickstart).</Term>
  <Term name="Descriptor">A plain, serializable object such as `{ component, props }` that names a view and its props for your front end to render. See [Rendering](/next/rendering).</Term>
</Terms>

## Authoring: from types to an editor

<Flow label="Authoring flow">
  <FlowNode title="Your TypeScript">Functions with typed inputs: UI and data fetchers alike</FlowNode>
  <FlowNode title="CLI → JSON Schema">`deco schema` writes `.deco/schema.json`</FlowNode>
  <FlowNode title="Studio">Forms and previews for editors, built from the schema</FlowNode>
</Flow>

You write functions with typed inputs, for example a hero block that takes a title and an image. The CLI turns those types into a schema, and Studio turns the schema into forms. Editors, and AI agents, save content as JSON files in `.deco/blocks`, in your repository.

## Delivery: from files to your app

<Flow label="Delivery flow">
  <FlowNode title="Content">The content module built from `.deco/blocks`, or a release (a published version of your content) from the Deco API</FlowNode>
  <FlowNode title="SDK">`client.list` and `client.resolve` read and resolve content</FlowNode>
  <FlowNode title="Your app">Next.js, TanStack Start, or any server</FlowNode>
</Flow>

At request time, your app asks the SDK for a piece of saved content by name. The SDK reads it from the content you gave `createCMS`, the one setting that knows where content lives (usually the content module generated from `.deco/blocks`; see [Content and loaders](/next/content)). If that content refers to other saved entries, the SDK expands them. Then it calls the matching function from your [block map](/next/quickstart) with the saved inputs and returns the result. How you render it is up to your framework. When you need more from the block map, such as lazy loading, see [Block maps](/next/manifest).

If you use the hosted Deco CMS, you can publish content without redeploying. In production your app reads the current release from the Deco API instead of from the content module. A request never waits on that: content stays in memory and refreshes in the background (each server checks for a new release about once a minute, when it's idle), and the content your build shipped with is always there as the fallback. See [Releases and deployment](/next/releases), or [how the loader stays current](/next/loader-internals) for the details.

## Small on purpose

Deco Blocks stays out of your way, and every piece is replaceable:

- **Content is plain JSON.** Open it in any editor, grep it, diff it, or generate it with a script. There's no database or content API for you to host. The hosted Deco CMS is optional, and Deco runs it.
- **Block functions are plain functions.** No framework plugin, no base classes, no magic directories. The block map is a plain object, and you can call any block function directly in a test.
- **Loaders are one method.** Reading from a key-value store such as Cloudflare Workers KV, or from your own database, is one `load()` method that returns `{ revision, blocks }`: an ID for this version of the content, and the saved entries by name. Files in your repository need none, because the CLI turns them into a module. Swap the source and nothing else changes (see [Content and loaders](/next/content)).
- **The schema is a file.** Commit it, inspect it, or generate it another way. Studio builds its forms from that JSON alone.
- **Nothing is hidden.** If the SDK doesn't do what you need, read the content yourself: the block format is documented in [Blocks](/next/model), and the files and the content map in [Content and loaders](/next/content).
