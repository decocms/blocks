# CLAUDE.md

Guidance for AI assistants working in this repo.

## Project Overview

This is **blocks** (repo `decocms/blocks`): a Bun workspace monorepo for the framework layer of [deco.cx](https://deco.cx) sites. This line (`main`) is the **next major (v8)**: one core package, `@decocms/blocks`, the framework bindings `@decocms/tanstack` (TanStack Start on Cloudflare Workers, deployed the Deco way) and `@decocms/nextjs` (any Next.js App Router app), plus thin upstream clients, `@decocms/apps-*`, and `@decocms/compat-v7` (v7's pure helpers, with v7's output, for migrated sites). The spec is the docs site's `/next/*` pages; when the code and the docs disagree, the docs win.

**v7 lives on the `7.x` branch.** v7's `@decocms/tanstack` and `@decocms/nextjs` (7.x), `@decocms/blocks-admin`, `@decocms/blocks-cli`, `@decocms/apps-commerce`, `@decocms/apps-blog`, `@decocms/apps-website` and v7's `@decocms/blocks` modules (`/cms`, `/sdk/*`, `/hooks`, `/setup`, …) are maintained and released there, not here. Don't reintroduce them on this line.

History worth knowing: the framework used to be a single tsup-bundled package, `@decocms/start`, reverted at v5.2.2 because bundling created two module instances of what must be one singleton (the CMS registry). Here no bundler is in the loop: each package is compiled file-for-file by `tsc` (see "How packages build" below), so module boundaries, and the singletons that live in them, are exactly the source's.

## Tech Stack

- Package manager / workspace / test runner: Bun + Vitest (one root `vitest.config.ts`)
- Runtime targets: any (Cloudflare Workers, Node, Bun, browsers for the client-safe parts); `@decocms/blocks` has no framework binding
- React 19: the root runtime uses React types only; `/analytics` uses `createElement` (react is a required peer)
- Lint/format: Biome; unused code: knip (run once from the root over all workspaces)

## Common Commands

```bash
bun install           # also builds every package's dist/ (root `prepare` script)
bun run build         # tsc (TypeScript 7) -> dist/, per package, blocks first
bun run test          # vitest, whole repo: packages, tests/, the migration skill's scripts
bun run typecheck     # tsc --noEmit per package, plus the skill scripts and tests/
bun run examples      # build the packages and the three examples, then typecheck them
bun run check         # typecheck + lint + lint:unused
bun run skills:check && bun run skills:readme:check   # agent skills gate (CI: skills-check.yml)
```

No dev server at the root. `examples/tanstack-smoke`, `examples/tanstack-rsc-smoke` and `examples/nextjs-smoke` are real consumers that depend only on `@decocms/blocks`; `examples/tanstack-worker-smoke` is the same app on `@decocms/tanstack`, and its `bun run smoke` runs the worker's header matrix on workerd (`vite preview`); `examples/nextjs-binding-smoke` is the Next.js app on `@decocms/nextjs`, and its `bun run smoke` runs the draft flow and checks `http.server.request.duration` (a local OTLP sink) on `next start`; both in CI (`cd examples/<name> && bun run dev`).

### How packages build (per-file `tsc`, no bundler)

Every package publishes compiled JavaScript so plain Node (scripts, Playwright, Node servers, Next without `transpilePackages`) can import it; npm never ships only `.ts`. The build is `tsc -p tsconfig.build.json` (via `scripts/tsc.mjs`, which runs the TypeScript 7 native compiler from the root `typescript7` alias): `rootDir: src`, `outDir: dist`, `module`/`moduleResolution: NodeNext`, `declaration` + declaration and source maps, tests and fixtures excluded. Each `src/**/*.ts(x)` becomes exactly one `dist/**/*.js` (+ `.d.ts`), with its imports left as imports.

- **Why no bundler**: a bundle inlines modules, so a package that bundles another (or a bundle loaded next to the unbundled copy) carries a second instance of module state — the `@decocms/start` registry bug. With per-file output there is one `dist/x.js` per `src/x.ts` and every importer gets that one module, as with the source; cross-package imports stay package imports (`@decocms/blocks`), never inlined. Don't add tsup/esbuild/rollup to a package build.
- **Relative imports carry the `.ts` extension** (`from "./run.ts"`, `from "./server/index.ts"`, never extensionless or a bare directory) and `rewriteRelativeImportExtensions` turns them into `.js` in the output; the build's `NodeNext` resolution rejects a specifier Node couldn't resolve. Test files may stay extensionless (they're never emitted).
- **Exports maps**: every subpath is `{ "types": "./dist/….d.ts", "source": "./src/….ts", "default": "./dist/….js" }`; conditional subpaths nest that object under each branch (`/protocol/storage/fs`: `node` before `default`). `files` ships `dist` and `src` (minus tests) so the `source` condition and the declaration maps resolve. Add a subpath to both `src` and the map in that shape (`sdk.test.ts`/`run.test.ts` check it).
- **The `source` condition** lets in-repo tools use `.ts` without a build: `tsconfig.base.json` (`customConditions`) for type-checks and `vitest.config.ts` (`resolve.conditions`) for tests, so a test importing a file by path and one importing `@decocms/blocks` share one module. A consumer that opts into `source` must do so for every environment it builds; mixing `source` and dist in one process loads both copies.
- **The bin runs dist**: `bin/deco.js` imports `dist/v8/cli/main.js` (no tsx). `tests/globalSetup.ts` rebuilds blocks' dist before the suite because the CLI conformance tests spawn the bin.
- **Two TypeScripts**: builds and type-checks use TypeScript 7 (`typescript7`, npm alias of `typescript@7`); the plain `typescript` name stays on 5.x because TypeScript 7 has no JavaScript compiler API, and `deco schema` loads the app's `typescript` peer through that API (as do Next's type-check and a few conformance tests).
- **Release**: `.releaserc.json`'s `prepareCmd` runs `bun run build` after the version sync, and each package's `prepack` rebuilds, so `npm publish` never ships a stale or missing dist. CI (`.github/workflows/ci.yml`) type-checks, builds, imports every built export of every package with plain Node (the `apps-*` helper subpaths such as `/image` included), and runs `tests/release.test.ts`, which also checks each export's shape and that `npm pack` ships every export's files and no test or fixture.
- **Ranges on `@decocms/blocks`**: the bindings and the `apps-*` take it as a **peer** with a caret range (`"^8.6.0"` for the bindings, `"^8.4.0"` for `compat-v7` and the `apps-*`), plus `"workspace:*"` in `devDependencies` for the workspace; never `workspace:*` in `dependencies`, which publishes as an exact pin and puts a second blocks copy next to the app on the next patch. `scripts/sync-versions.mjs` writes the release version, rewrites only `devDependencies`' `workspace:` ranges, and refuses an in-repo `dependencies` entry or a peer floor above the release. Raise a package's peer floor when it starts using a newer blocks API, and add the subpath to `BLOCKS_API_SINCE` in `tests/release.test.ts`. The release publishes through `scripts/publish.mjs`, which skips what is already on npm and retries a transient `npm publish` failure, because a failed publish can't be re-run once semantic-release has tagged.

### Key boundaries

- **The runtime never imports the protocol or the CLI.** `src/v8` modules import only each other (no Node built-ins, no React at runtime except `/analytics`); `src/v8/browserBundle.test.ts` proves it with a real esbuild bundle. The one exception is `#async-store` (package.json `imports`): its `node`/`workerd`/`bun`/`deno` condition loads `src/async/node.ts` (`AsyncLocalStorage` from `node:async_hooks`, so Workers need `nodejs_compat`), its `default` `src/async/default.ts` (a global `AsyncLocalStorage` if the runtime has one, else none). The CLI may import the protocol.
- **Clients depend only on `@decocms/blocks`**, with no peers and no framework binding. A client takes settings as arguments (no env reads), never caches, has no hooks, converters or `"use client"` code: those belong in the site's platform template (`tests/upstream-clients.conformance.test.ts`).
- **Platform helpers live in the platform's package, not in blocks.** Besides its client, an `apps-*` package may export pure helper subpaths that compose with `@decocms/blocks` (`@decocms/apps-vtex/image` and `@decocms/apps-shopify/image`: image URL providers for `createImageUrl`). Pure: no network, no React, no env reads, no runtime imports (`tests/upstream-helpers.guardrail.test.ts`, which also bundles each for a browser and workerd). The product owner's call: `@decocms/blocks` holds framework code only, nothing that knows VTEX, Shopify or another commerce platform. Bindings never depend on an `apps-*` package: sites wire the helper in.
- **Cross-package imports are package imports**: type-checks resolve them to `.ts` source through the `source` condition; the build resolves them to the dependency's built `dist/*.d.ts`, which is why `bun run build` builds blocks before the clients. No `tsconfig.json` `references` anywhere: adding them back reintroduces a TS6305 build-ordering bug.
- **No compat layers, one exception.** If a site needs something a package should export, add the export; don't let sites (or this repo) re-create v7 APIs as shims. The product owner approved `@decocms/compat-v7` (2026-10-14) as the one home for v7's *pure* helpers (types, device detection, scripts, `clx`, request-explicit matchers, the `(props, req)` section-loader runner, commerce types and helpers): each pinned to v7's output, none of v7's runtime (no `ctx`, invoke dispatcher, `cachedLoader` or request scope). Nothing else may re-create v7 APIs: not sites, not `@decocms/blocks`, the bindings or the clients, and none of them depends on compat-v7.

## v8 core — `packages/blocks/src/v8/`

- **`createCMS` instances are `globalThis` singletons** under `Symbol.for("decocms.blocks.cms:<content identity>[|site|token-hash]")`, so two copies of the package share one content cache (`dualInstance.test.ts`, the regression test for the bug this repo exists to prevent). Never key on the revision, and never put a raw token in a symbol.
- **`lazy` and the built-in `multivariate` are the resolver's only special cases** (`lazy`'s value isn't resolved first; `multivariate`'s rules run in order and stop at the first true one, as in v7); everything else is an ordinary block function. Values from the snapshot are copied while walked, so callers and block functions can't mutate shared content.
- **No framework binding, no request scope: inputs arrive as arguments.** The version, the visitor, the date and the tests and campaigns already decided arrive as arguments to `cms.client({ version, visitor, date, experiments, campaigns })` (`experiments`/`campaigns` override name by name; the rest are decided from the visitor and the date; a name the block doesn't have stays out; given full maps and no visitor a client is fully decided, which is how a page renders what its proxy or worker decided); `currentClient()` (`src/v8/current.ts`) only hands that client to the block functions it runs (the resolver sets it while it calls one, so it works before the first `await` everywhere and across `await` where `#async-store` has `AsyncLocalStorage`; the slot is on `globalThis` under `Symbol.for`). Blocks never reads a request, cookie, header or URL in the core; `readVisitor` and `cms.readVersion` are helpers the app calls. Platform specifics (a Workers KV `Loader`, a Cache API upstream cache passed as `createInstrumentedFetch`'s `fetch`) are template code shown as docs recipes, not package exports. Don't add `requestScope()`, `Deferred`, `BlockList`, cache logic, consent handling or other non-CMS helpers to the core.
- **A/B tests are content** (`src/v8/builtins/experiments.ts`, `__conformance__/experiments.test.ts`, `__conformance__/client.test.ts`): the saved block `experiments` has the built-in type `split-traffic` (`Record<string, number>`, whole percentages 0–100: 0 off, 100 everyone; two arms, a multi-way test is several tests); resolving it gives `{ [name]: boolean }` for the client's visitor (`assign`, with the client's `experiments` on top, a test at 0% included: the 0%-stays-off rule for a forged path lives in the bindings' parsing, not in the client), never percentages. The rule `experiment { name }` is `(await currentClient().resolve("experiments"))[name] === true`, so the tests are decided once per client however many rules ask, and a draft's tests run in its preview. No Studio database, no writes to production: tests live only in blocks content. A client without a visitor has every test off. A section prop typed `Assignments` (any `Record<string, boolean>`) can hold the whole map, `{ "__resolveType": "experiments" }`: `deco schema` lists `split-traffic` among the blocks that fit such a field (`BUILT_IN_RETURNS` in `cli/schema/generate.ts`), so the site editor offers it and `deco check` accepts it. `split-traffic` and `experiment` are reserved; the saved name `experiments` is not. `deco check`: a percentage that isn't a whole number 0–100 is an error; it warns on `experiments` saved with another type, a rule naming a missing test, and a block map entry named `experiment` or `split-traffic` (overriding `page` and the others stays silent).
- **Campaign dates are content too** (`src/v8/builtins/campaigns.ts`, `__conformance__/campaigns.test.ts`): the saved block `campaigns` has the built-in type `calendar` (`Record<string, { start?, end? }>`, ISO date-times with an offset; `start` inclusive, `end` exclusive, an empty bound open, a bound that doesn't parse never runs); resolving it gives `{ [name]: boolean }` at `client.date` (with the client's `campaigns` on top), never dates, so a section prop of that type can hold `{ "__resolveType": "campaigns" }` as it can `experiments` (`calendar` is in `BUILT_IN_RETURNS` too). The rule `campaign { name }` is `(await currentClient().resolve("campaigns"))[name] === true`. `calendar` is the only place date logic lives: there are no inline `{ start, end }` rules. `calendar` and `campaign` are reserved; the saved name `campaigns` is not, and neither are the prerelease names `date` and `date-windows` (PO 2026-10-21 renames; v7's date matchers and the legacy names are untouched). `deco check` warns on `campaigns` saved with another type, a rule naming a missing campaign or none, an end not after its start, and a block map entry named `campaign` or `calendar`; it rejects the prerelease `date` rule (saying the `campaign` rule to write, or that inline dates move into a campaign) and type `date-windows` (now `calendar`).
- **A preview link carries more than the version** (`src/v8/draft.ts`): `__at=<ISO with offset>`, `__test=<name>=on|off` and `__campaign=<name>=on|off`, in a draft pointer's query or after a release SHA (`<sha>?__at=…&__test=…`), the link Studio builds. `parseVersion` (and `cms.readVersion`, host-checked) lifts them out as `{ version, date, experiments, campaigns }`; the version itself is only a draft pointer (with its `__variant` parameters, part of the draft it names) or a bare SHA, and `cms.client` rejects one still carrying them (`LOADER_FAILED`). A link with one that doesn't parse is no version at all. The draft's body is keyed without them, so every preview of one draft shares one fetch.
- **Conformance tests** (`src/v8/__conformance__/`) encode the docs' claims, one test per claim. When the docs change, change the test; don't relax an assertion to make code pass.

## Upstream observability

Every client builds its requests with `createInstrumentedFetch({ provider: "<name>" })` from `@decocms/blocks/fetch`, which measures each request once (`http.client.request.duration` with `provider`/`operation`/`status_class`/`cached`/`retries` labels) and reports to the CMS's telemetry in the same process. Nothing has to be wired at boot: the instrumented fetch is the only way a client reaches the network. An upstream cache is the site's own `fetch` passed as the `fetch` option; a response it serves carries `x-cache: HIT` and is measured with `cached=true`.

`tests/upstream-clients.guardrail.test.ts` checks that every `packages/apps-*` is listed and that its client imports `createInstrumentedFetch` from `@decocms/blocks/fetch` under its provider name and never calls `fetch` directly; Biome denies the bare `fetch` global in `packages/apps-*/src` too. A new client package goes in that test's `CLIENTS`.

One folder, `.agents/skills/`, and only skills that describe this line's packages **as they are today**. Claude Code discovers them through the `.claude/skills` symlink. Gate: `bun run skills:check && bun run skills:readme:check` (regenerate the index with `bun run skills:readme`), copied from `decocms/migrations`: `SKILL.md` ≤10KB as an index, every other `.md` ≤15KB, quoted descriptions, no dead relative links, a generated index; CI in `.github/workflows/skills-check.yml`. - **`deco-v7-to-v8-migration`** — moves a v7 site onto v8: `scripts/main.ts` (run with `bun` or `npx tsx`) writes the block map with legacy aliases, vendors the app loaders the content calls, moves content to `.deco/blocks`, re-encrypts secrets, points the v7 imports the bindings keep at `@decocms/tanstack` (`MOVES` in `imports.ts`) and v7's pure helpers at `@decocms/compat-v7` (`compat.ts`: `@decocms/apps-commerce`, `clx`, scripts, device, widgets, `ctx.device`), turns `registerSectionLoaders` into the map the block map's `loadSections` runs, registers v7's matchers except `random` (the binding is the only writer of `deco_segment`), reports v7's random matchers and every date rule still holding its own dates as manual steps (`experiments.ts`: they move by hand into the saved blocks `experiments` and `campaigns`; every v8 site's content is changed in its own PR), writes `src/views.ts` and, on TanStack, `src/imageUrl.ts` wired into `createDecoRouter`, turns v7's app blocks into `src/clients/<app>.ts` (`apps.ts`) and each `/deco/invoke` key into one server function its call sites import (`invoke.ts`), stubs what has no port in `src/migration-stubs.ts` (`stubs.ts`: `ctx.invoke`, app state, `useSection`), writes the page setup (`scaffold.ts`: `src/cms.ts`, the page loader on the page's URL, the catch-all route with v7's route options, head and section wrapper, a per-request `QueryClient`), on TanStack the worker entry (`workerEntry.ts`: the README's site-owned page cache recipe with v7's `buildSegment` and `csp`) and reports every other v7 import with its replacement. ## Important constraints

1. **No compat layers** in a package or a migrated site, except `@decocms/compat-v7`'s pure v7 helpers (no v7 runtime; see Key boundaries).
2. **One instance per process**: anything that must be a singleton lives on `globalThis` under a `Symbol.for` key; packages never bundle each other.
3. **Base64**: `toBase64()` in `src/v8/cli/schema/typeToSchema.ts` must produce padded output matching `btoa()`; the site editor uses `btoa()` for schema definition refs.
4. **Dependency direction**: runtime ← CLI/protocol; `apps-*`, `@decocms/tanstack` and `@decocms/nextjs` → `@decocms/blocks` only (the bindings never import each other, and blocks imports neither); `@decocms/compat-v7` → `@decocms/blocks`, plus a binding only in its `/tanstack` or `/nextjs` subpath, and nothing depends on it. Enforced by tests (`guides.cli.test.ts` in-11, `sdk.test.ts`) and review.
5. **Upstream observability**: a new client MUST build on `createInstrumentedFetch` and be listed in the guardrail test.
6. **Tests that guard production bugs** (e.g. `dualInstance.test.ts`): if one fails, fix the code, not the assertion.
