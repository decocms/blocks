# The generate-invoke.ts Script

## Location

Source: `packages/blocks-cli/scripts/generate-invoke.ts` (this repo, published as `@decocms/blocks-cli`).
Site usage: `node_modules/@decocms/blocks-cli/scripts/generate-invoke.ts`.

This moved from the old single-package `@decocms/start/scripts/generate-invoke.ts` when the framework split into `runtime`/`admin`/`cli`/`tanstack`/`next` — see the root `README.md`. `@decocms/blocks-cli`'s `exports` map has no `./generate-invoke` entry (only `./generate` and `./generate-blocks`) — the script is a standalone `tsx` entry point and an internal implementation detail of the unified orchestrator `scripts/generate.ts`, which runs it as its `invoke` stage. Sites run `npm run generate`; invoking the script by file path as shown below still works for one-off debugging.

## What It Does

1. Finds `@decocms/apps-vtex`'s `invoke.ts` (source: `packages/apps-vtex/src/invoke.ts` in this monorepo; resolved from the installed package, at its root or under `src/`, with a legacy `../apps-start/vtex` checkout as last resort). **That legacy fallback exists only when the script is run directly by path.** The orchestrator (`npm run generate`) resolves only the installed package or an explicit `--apps-dir`; with neither, it *skips* the invoke stage (logging "no apps invoke.ts found") and `invoke.gen.ts` is not regenerated — so a site relying on a sibling `../apps-start/vtex` checkout must pass `npm run generate -- --apps-dir ../apps-start/vtex`
2. Parses it with `ts-morph` to extract action definitions
3. For each action, extracts: name, import source, imported function, input type, return type, unwrap flag, call body
4. Generates `src/server/invoke.gen.ts` with:
   - Top-level `createServerFn().inputValidator().handler()` declarations (one per action)
   - A `forwardResponseCookies()` helper, called at the end of every handler
   - A `vtexActions` export (for merging into a site-local `invoke.ts`) and a default `invoke` re-export

## Usage

```bash
# From site root
npx tsx node_modules/@decocms/blocks-cli/scripts/generate-invoke.ts

# With custom output
npx tsx node_modules/@decocms/blocks-cli/scripts/generate-invoke.ts --out-file src/invoke.gen.ts

# With custom apps location
npx tsx node_modules/@decocms/blocks-cli/scripts/generate-invoke.ts --apps-dir ../apps-start/vtex
```

## CLI Options

| Option | Default | Description |
|--------|---------|-------------|
| `--out-file` | `src/server/invoke.gen.ts` | Output file path |
| `--apps-dir` | Auto-detected (installed `@decocms/apps-vtex`, then `../apps-start/vtex` — the latter only for direct script runs, not via `npm run generate`) | Path to the directory holding the apps `invoke.ts` |

## How It Parses invoke.ts

The script navigates the AST:

```
invoke (VariableDeclaration)
  └── { vtex: { actions: { ... } } } as const  (AsExpression → ObjectLiteral)
        └── vtex (PropertyAssignment)
              └── actions (PropertyAssignment)
                    └── getOrCreateCart: createInvokeFn(...) as (...)
                    └── addItemsToCart: createInvokeFn(...) as (...)
                    └── ...
```

For each property in `actions`:
1. Strips the `as Type` assertion to get the `createInvokeFn(...)` call
2. Extracts the arrow function parameter type → `inputType`
3. Extracts the arrow function body **verbatim** as `callBody` — e.g. `getOrCreateCart(data)` for a direct pass-through, or `createSession({ data })` for a wrapper that adapts the payload shape. This is emitted as-is in the generated handler (`const result = await ${callBody};`), so adapting wrappers keep working; hard-coding `${importedFn}(data)` for every action was tried and reverted because it silently dropped the adaptation (see the generator's inline comment and `generate-invoke.test.ts`'s "preserves adapting wrappers verbatim" case)
4. Checks for `{ unwrap: true }` in the second argument
5. Resolves which imported function is called (matches against import map)
6. Extracts the return type from the outermost `as` assertion

The parser does **not** execute `createInvokeFn` — it only reads source text via `ts-morph`. (`createInvokeFn` is a real export — `@decocms/apps-vtex`'s `invoke.ts` imports it from `@decocms/tanstack/sdk/createInvoke` — but the generator never relies on that.)

## Generated Output Structure

This is the actual current shape (condensed from `packages/blocks-cli/scripts/generate-invoke.ts`; read the script for the full comment block explaining each design decision):

```typescript
// invoke.gen.ts
// Auto-generated by @decocms/blocks-cli/scripts/generate-invoke.ts
// Do not edit manually. Re-run the generator to update.

import { createServerFn } from "@tanstack/react-start";
import { addItemsToCart, ... } from "@decocms/apps-vtex/actions/checkout";
import type { OrderForm } from "@decocms/apps-vtex/types";
import {
  getResponseHeaders,
  setResponseHeader,
} from "@tanstack/react-start/server";
import { RequestContext } from "@decocms/blocks/sdk/requestContext";

function unwrapResult<T>(result: unknown): T {
  if (result && typeof result === "object" && "data" in result) {
    return (result as { data: T }).data;
  }
  return result as T;
}

// Forwards Set-Cookie headers captured in RequestContext.responseHeaders
// (by vtexFetchWithCookies) into TanStack Start's HTTP response. Uses
// Headers.getSetCookie() — not .entries() — because .entries() collapses
// multiple Set-Cookie values into one comma-joined string, which browsers
// silently discard. No-op when nothing was captured, so every handler can
// call it unconditionally.
function forwardResponseCookies(): void {
  const ctx = RequestContext.current;
  if (!ctx) return;
  const captured =
    typeof ctx.responseHeaders.getSetCookie === "function"
      ? ctx.responseHeaders.getSetCookie()
      : [];
  if (captured.length === 0) return;
  const existing =
    typeof getResponseHeaders().getSetCookie === "function"
      ? getResponseHeaders().getSetCookie()
      : [];
  setResponseHeader("set-cookie", [...existing, ...captured]);
}

// ---------------------------------------------------------------------------
// Top-level server function declarations — compiler can transform these
// ---------------------------------------------------------------------------

const $addItemsToCart = createServerFn({ method: "POST" })
  .inputValidator((data: { orderFormId: string; orderItems: CartItem[] }) => data)
  .handler(async ({ data }): Promise<any> => {
    const result = await addItemsToCart(data.orderFormId, data.orderItems);
    forwardResponseCookies();
    return unwrapResult(result);   // only when the action declared { unwrap: true }
  });

// ---------------------------------------------------------------------------
// Typed VTEX actions map — merge with site-specific actions in your invoke.ts
// ---------------------------------------------------------------------------

export const vtexActions = {
  addItemsToCart: $addItemsToCart as unknown as (ctx: { data: { orderFormId: string; orderItems: CartItem[] } }) => Promise<OrderForm>,
} as const;

export type { OrderForm } from "@decocms/apps-vtex/types";

// ---------------------------------------------------------------------------
// Default invoke object — import this if you don't need site extensions
// ---------------------------------------------------------------------------

export const invoke = {
  vtex: {
    actions: vtexActions,
  },
} as const;
```

Two things every earlier version of this doc was missing, both load-bearing:

- **`.inputValidator((data: InputType) => data)`** before `.handler()`. Without it, TanStack Start types the handler's `data` as `undefined` and every field access is a type error. `architecture.md` already assumed this; this doc now matches.
- **`forwardResponseCookies()`**, called after the `await` but before `return`, in *every* generated handler (unconditionally — it's a cheap no-op for read-only actions). This is the fix for the "cart forgets items" bug documented in `cookie-forwarding.md`. `generate-invoke.test.ts` locks both the call-count (one per handler) and the ordering (after the await).

Handlers whose action wasn't parseable are emitted as throwing stubs (`// TODO: could not auto-generate ${name} — add manually`) rather than silently omitted — check the generator's console warnings after running it.

## Setup for a New Site

1. Add the `generate` script (see "Integration with Build Pipeline" below) and run `npm run generate` — its invoke stage writes `src/server/invoke.gen.ts`.
2. Hand-write `src/server/invoke.ts` merging `vtexActions` with site actions (`architecture.md`'s "Layer 3.5").
3. Call it from components: `import { invoke } from "~/server/invoke"; await invoke.vtex.actions.addItemsToCart({ data: { orderFormId, orderItems } });`

Re-run `npm run generate` whenever actions are added to `packages/apps-vtex/src/invoke.ts`, action signatures (input/return types) change, or the `@decocms/apps-vtex` dependency is updated.

## Adding New Actions

1. Add the pure function to `packages/apps-vtex/src/actions/{module}.ts` (published as `@decocms/apps-vtex/actions/{module}`)
2. Add it to `packages/apps-vtex/src/invoke.ts` using `createInvokeFn`
3. Re-run `npm run generate` in the site
4. The new action is automatically available in `vtexActions.*` / `invoke.vtex.actions.*` (if your site's `src/server/invoke.ts` re-exports `vtexActions` — see `architecture.md`'s "Layer 3.5")

## unwrapResult

VTEX checkout functions return `VtexFetchResult<T>` which wraps `{ data: T, setCookies: string[] }`. The `unwrap: true` flag causes the generated handler to extract `.data` before returning to the client:

```typescript
// Without unwrap:
const result = await simulateCart(items, postalCode);
return result;  // returns raw simulation response

// With unwrap:
const result = await getOrCreateCart(orderFormId);
return unwrapResult(result);  // returns OrderForm, not { data: OrderForm, setCookies }
```

## Site-Local Composition (`invoke.ts`)

`generate-invoke.ts` only emits the canonical VTEX action set. Sites needing custom/site-specific server functions write those by hand in `src/server/invoke.ts`, importing and spreading `vtexActions` from the generated file. That hand-written layer follows the same `.inputValidator()` + `Promise<any>` pattern documented in the `deco-to-tanstack-migration` skill's `references/server-functions/README.md` (lives in decocms/migrations) — but must additionally forward `Set-Cookie`s for any action touching VTEX cookies. The generated `forwardResponseCookies()` is private to `invoke.gen.ts`; use the public `forwardResponseCookies(cookies)` from `@decocms/tanstack/sdk/cookiePassthrough` (snippet in `architecture.md`'s "Layer 3.5"). See `architecture.md`'s "Layer 3.5" for the full example.

## Integration with Build Pipeline

The script fits into the existing build pipeline alongside other generators:

```json
{
  "scripts": {
    "generate": "tsx node_modules/@decocms/blocks-cli/scripts/generate.ts --site <site>",
    "generate:routes": "tsr generate",
    "build": "npm run generate && tsr generate && vite build"
  }
}
```

This is the shape the migration script scaffolds (`packages/blocks-cli/scripts/migrate/templates/package-json.ts`); its test asserts the old per-generator `generate:blocks`/`generate:invoke`/`generate:schema` scripts are no longer scaffolded. Order still matters, and the orchestrator owns it: invoke runs in stage 1 (concurrently with blocks/manifest/sections/loaders), schema runs after, because schema needs to see `src/server/invoke.gen.ts`, which the invoke stage rewrites. The invoke stage is skipped (with a reason) when no apps `invoke.ts` is resolvable or the site is not TanStack Start.

# When the generator or its output fails

## "invoke.vtex.actions.X is not a function"

**Cause**: The generated file doesn't include that action.

**Fix**:
1. Check `packages/apps-vtex/src/invoke.ts` — is the action declared there?
2. Re-run `npm run generate`
3. Check the generated `invoke.gen.ts` — is the action present?

## Generator Fails: "Could not find @decocms/apps-vtex"

**Cause**: The script can't locate the apps package.

**Fix**: Use `--apps-dir`:
```bash
npx tsx node_modules/@decocms/blocks-cli/scripts/generate-invoke.ts --apps-dir ../apps-start/vtex
# or
npx tsx node_modules/@decocms/blocks-cli/scripts/generate-invoke.ts --apps-dir node_modules/@decocms/apps-vtex/src
# (via the orchestrator: npm run generate -- --apps-dir <dir>)
```

## Generator Fails: "Could not find 'export const invoke'"

**Cause**: The `invoke.ts` in `@decocms/apps-vtex` changed structure.

**Fix**: The generator expects:
```typescript
export const invoke = {
  vtex: {
    actions: {
      actionName: createInvokeFn(...) as ...,
    },
  },
} as const;
```

If the structure changed, update `generate-invoke.ts` to match.

## New Action Not Available After Re-generating

**Checklist**:
1. Added to `packages/apps-vtex/src/invoke.ts`? 
2. Ran `npm run generate`?
3. Check `src/server/invoke.gen.ts` — is the new action in the file?
4. Restarted dev server? (HMR may not pick up `.gen.ts` changes)

## TypeScript Errors in invoke.gen.ts

The generated file uses `as unknown as` casts for typing. If you see TS errors:
- They're usually harmless in the generated file
- The consumer types (what components see) are correct
- If a type is wrong, fix it in `packages/apps-vtex/src/invoke.ts` and re-generate
