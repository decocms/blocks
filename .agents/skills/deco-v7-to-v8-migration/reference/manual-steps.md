# Manual steps (what the report leaves)

The full text behind `SKILL.md` ("Manual steps"). Work through the report top to bottom; these are the steps it groups its "Left to do" lines under.

1. **Dependencies.** Depend on `@decocms/blocks@^8.4`, the v8 binding at the same version (`@decocms/tanstack@^8.4` or `@decocms/nextjs@^8.4`; they take blocks as a peer, so one copy installs), `@decocms/compat-v7@^8.4` when the script pointed imports at it and the v8 `@decocms/apps-<platform>` client. Remove `@decocms/blocks-admin`, `@decocms/blocks-cli`, `@decocms/apps-commerce`, `@decocms/apps-website` and `@decocms/apps-blog` once nothing imports them, and drop the v7 codegen from `build`. On Next.js, check what the installed `@decocms/blocks` publishes: when its `exports` default to `dist/*.js` (`8.1.0` does), it needs no `transpilePackages` entry; a prerelease whose `exports` point at `src/*.ts` needs `@decocms/blocks` in `transpilePackages` (v7's `withDeco` wrapper used to add it), or a clean install fails `next build` with `Module parse failed: Unexpected token`.
2. **Check the page setup the script wrote, on the binding.** It follows the framework guide (`/next/tanstack-start-descriptors`, `/next/nextjs`): `src/cms.ts` (`createCMS` and the binding's `contentClient`), `src/open-page.server.ts` (`matchRoute`, every section resolved, then `loadSections` at the page's URL, and on TanStack `matchPage(url)` first), the page's server function (`src/page.functions.ts`: it takes the page's path, so a client-side navigation loads the page and not `/_serverFn/…`), and the catch-all route rendering `src/views.ts` (`src/routes/$.tsx`, or the Next.js `[[...slug]]/page.tsx`, with `bindDraft`). It replaced v7's page routes (`cmsRouteConfig`, `createDecoPage`), keeping their options, v7's head and v7's section wrapper: carry over what the site added to them (a not-found component, a head tag or loader of its own, a wrapper such as a `<main>` landmark around the sections) from git. The block map has no `page` of its own: the built-in page takes the views' descriptors as its sections, and in its `seo` field any block that returns only optional SEO fields (a `title` or a `description`, strings), such as one returning the block map's `PageSeo`; a loader whose result has required fields (a blog post, a category) stays out. A file that already existed was kept and reported. Still by hand: `pageUrlRequestHeaders` in the proxy (Next.js) when the report says so, the visitor in the proxy (Next.js: `draftProxy`, or `decideVisitor`/`visitorRequestHeaders`/`applyVisitor`) when the content has `experiments`, the A/B tests and date rules the report lists, moved into the saved blocks `experiments` and `campaigns` (`/next/matchers-and-variants#run-an-a-b-test`, `#schedule-a-campaign`), and the binding wired as its README shows: on TanStack, `createDecoWorker` as the worker entry, `DecoDocument` as the root, `createDecoRouter`, `decoServerFnFetch` and `decoTanstack()`; on Next.js, the draft proxy and route, `StudioBridge`, `withDeco` and the image loader (`reference/framework-code.md`). The script deleted v7's admin routes; delete the v7 setup files too, and the v7 CI jobs: a `.github/workflows/regen-blocks.yml` (or any job that runs `generate:blocks` or calls the shared `regen-blocks` workflow) regenerated `blocks.gen.json` on every content push to `main`. v8 has no such file and the script it calls is gone, so once merged every publish starts a job that fails or does nothing useful.
3. **Replace v7's framework code with the binding, and move the rest into the site** (`reference/framework-code.md`): the worker, drafts, the Studio bridge, the badge and the image components come from the binding, a platform's image URLs from its client's `/image` (`@decocms/apps-vtex/image`, `@decocms/apps-shopify/image`); SEO/head, device detection, cookies, cart/user/wishlist flows, commerce loaders and converters are site code.
4. **Finish `/deco/invoke`.** The script wrote one server function per key the site invoked (`src/server/invoke.functions.ts` with TanStack `createServerFn`, loaders as private GETs; `src/server/invoke.actions.ts` with Next.js `"use server"`), each calling its handler with `(props, request)` as v7's endpoint did, and pointed every call site at its own: `invoke.site.loaders.spin(props)` → `$siteLoadersSpin({ data: props })`. Give each a zod validator and a typed result (they're `any`, as v7's invoke was), and set the cookies a handler needs with the framework's API. What it couldn't port is a `@deprecated` stub in `src/migration-stubs.ts`: `unportedInvoke` (`ctx.invoke` in a loader, a key no file answers), `appState` (an app's state off `ctx`); both reject, as reading `ctx` does in v8. `useSection` keeps v7 7.x's placeholder URL, so `hx-*` attributes render as before and still do nothing. Replace each stub, then delete the file. Don't rebuild the `invoke.x.y` tree or a string-keyed dispatcher (see DO NOT in `SKILL.md`). Details in `reference/server-functions.md`.
5. **Fix the content `deco check` rejects**: fields no type declares, `.tsx`-named preview blocks, v7 app blocks (the script wrote each one's client config to `src/clients/<app>.ts`: set the credentials it names, then delete the block), `requestToParam` blocks in string fields.
6. **Telemetry, analytics and previews**: the `telemetry` option of `createCMS` (`/next/telemetry`), with switches and rates in the `telemetry` section of `CMS.json`; `AnalyticsScript` with `const { analytics } = await cms.settings()` and `track` from `@decocms/blocks/analytics`; drafts through the binding (the TanStack worker, or `decideDraft`/`bindDraft` on Next.js), which applies v7's host allowlist: the hosts the site declares in the `CMS` block's `preview.hosts` (none when it lists none, as in v7: blocks' every-host default doesn't apply), plus `<site>.deco.site` and `<site>.deco-cx.workers.dev` from the `site` option; `previewHosts: [...]` replaces the block's list and `previewHosts: "none"` turns previews off, where v7 read `DECO_ALLOWED_PREVIEW_HOSTS`. The report's "preview hosts" line says what to pass to keep v7's hosts; list the dev server's host with its port (`localhost:5173`, `localhost:3000`) when editors preview there, and name each host you add for the product owner. The report carries GTM/GA4 IDs over. If v7 sent no CMS telemetry, pointing `telemetry` at the site's existing collector is new traffic and cost there: list it as a behaviour change.
