# What the script does

The full list behind `SKILL.md` ("Run"). What it does, in order (`scripts/migrate.ts`):

1. **content**: saved blocks into `.deco/blocks`, v7 generated files removed, v7 async-rendering wrappers (`website/sections/Rendering/Lazy.tsx`, `SingleDeferred.tsx`, `Deferred.tsx`) unwrapped to the sections they held (v8 has no async rendering), the seven legacy names outside the alias table rewritten (`reference/legacy-names.md`); v7's random matchers and every date rule still holding its own dates (v7's or v8's `date { start, end }`) are left as they are and reported, one line each: move each test into the saved block `experiments` under its saved-block name (Run an A/B test, `/next/matchers-and-variants#run-an-a-b-test`) and each window into the saved block `campaigns` (Schedule a campaign, `/next/matchers-and-variants#schedule-a-campaign`). The binding reads the visitor, hands it to `cms.client({ visitor, version })` and is the only writer of `deco_segment` (TanStack: the worker; Next.js: the proxy, reported; elsewhere `readVisitor`, reported);
   **settings**: site settings folded into the `CMS` block (`.deco/blocks/CMS.json`, type `cms-settings`): the v7 Site block's (`Site`/`site`) `previewHosts` → `preview.hosts` (the field moves, ports kept, each entry trimmed and lowercased as v7 compared it; an entry that isn't a host is reported). The hosts Deco runs the site on (`<site>.deco.site`, `<site>.deco-cx.workers.dev`) are not written: the binding allows them from its `site` option, and the report's "preview hosts" line names the `site` to pass (from `DECO_SITE_NAME`) (with no `previewHosts` in v7 nothing more is needed: the binding then allows only those two, as v7 did), a literal `collectorAddress` on `OneDollarStats` → `analytics.collector`, and an earlier prerelease's `Telemetry.json`/`Analytics.json` → their sections, field for field and variants included (the old files are deleted). It keeps what `CMS.json` already has, writes nothing when there's nothing to fold, and a second run changes nothing. The report lists the environment-only settings to move by hand (`DECO_ALLOWED_PREVIEW_HOSTS`, `DECO_OTEL_*` sampling, `DECO_ANALYTICS_ENABLED`/`ONEDOLLAR_ENABLED`/`ONEDOLLAR_COLLECTOR`);
   **apps**: each v7 app block v7's autoconfig read by name (`deco-vtex`, `deco-shopify`, `deco-wake`, `deco-resend`) → `src/clients/<app>.ts`, a function creating the v8 client (`createVtexClient`, …) with the block's settings and v7's defaults (VTEX's sales channel `"1"`, Wake's checkout URL, the Storefront API version the installed Shopify app spoke), each encrypted credential read from the environment variable v7 fell back to (`VTEX_APP_KEY`, `SHOPIFY_STOREFRONT_TOKEN`, `WAKE_TOKEN`, `RESEND_API_KEY`; the Worker's `env` or `process.env`), never its value; what v7 kept beside the client (`publicUrl`, Resend's sender) is an exported constant. The block stays until the variables are set; the report says to delete it then. The HTMX and analytics app blocks are reported for deletion;
2. **secrets**: v7 secrets re-encrypted with `.deco/secrets.pub`;
3. **block map**: the site's `registerSectionLoaders({ … })` (and `registerNonCriticalSections`) turned into exports of the same map; then `.deco/index.ts` with each block under its v7 names only (the names the content stores, and `site/sections/….tsx` for every section in `src/sections`), so the site editor lists each block once (PO 2026-10-15), after vendoring the app loaders and actions the content calls into `src/vendor`. A section's descriptor names it by its v7 type name (`site/sections/….tsx`), and `src/views.ts` maps each name to its module. On a TanStack Start or Next.js site, v7's matchers the content uses (`device`, `cookie`, `host`, `pathname`, `queryString`, `location`, `multi`) are registered from `@decocms/compat-v7/matchers` over the binding's `matcherContext()` (TanStack: `matchPage(href)` in the page's server function tells them the page); `random` never is (step 1 reports it, for `experiments`), and `environment` is reported. `loadSections(sections, request, pageUrl)` runs v7's section loaders with v7's rules (`@decocms/compat-v7/sections`; the nested walk of the site's 7.x release), and also every section's own `loader` v7 never ran because `registerSectionLoaders` didn't list it: an approved difference (PO 2026-10-15), each one reported by name to list in the PR (v7 rendered its saved props). The site's registered map wins where it lists a section;
4. **invoke**: each `/deco/invoke` key the site calls (`invoke.a.b(props)`, bracket and flat keys, `invoke(key, props)`, `Runtime.invoke`, from `@decocms/blocks/sdk/invoke` or a site module that fetches `/deco/invoke`) → one server function calling its handler with `(props, request)`, as v7's endpoint did: `src/server/invoke.functions.ts` (TanStack `createServerFn`; loaders GET with `markPrivate()`, actions POST) or `src/server/invoke.actions.ts` (Next.js `"use server"`), imported by each call site; v7's proxy module is deleted once unused. `site/<path>` resolves to `src/<path>`, an app key to its vendored module, and a key v7's VTEX app answered from its own invoke map (`vtex/actions/checkout/addItemsToCart`) to what `--vtex-invoke` says (no default: without it, a site that calls such keys stops before step 1 with the list): `keep` vendors v7's module and calls that export, `v8` writes `src/server/vtex-invoke.server.ts` over `@decocms/apps-vtex`'s client where it has the operation, else `unportedVtexInvoke` (`reference/server-functions.md`). Then the stubs in `src/migration-stubs.ts` (all `@deprecated`): `unportedInvoke` for a key with no handler and for `ctx.invoke` in a v7 loader, `appState` for an app's state read off its `ctx`, and `useSection`/`usePartialSection` with v7 7.x's placeholder URL; `hx-*` attributes are reported (inert in v7 and v8);
5. **scaffold**: on TanStack Start or Next.js, the page setup from the docs' guides: `src/cms.ts`, `src/open-page.server.ts` (every section resolved, then `loadSections` and `matchPage` when the block map has them, `requestDevice` when the site calls `useDevice`), TanStack's `src/page.functions.ts` (the page's server function, taking the page's path, so a client-side navigation opens the page and not `/_serverFn/…`) and `src/page-view.tsx`, and the catch-all route (`src/routes/$.tsx` and v7's home route; Next.js `[[...slug]]/page.tsx` with `bindDraft`, which also binds the visitor the proxy forwarded). Each section renders in v7's wrapper (`<section id data-manifest-key>` around v7's error boundary, `src/section-error-boundary.tsx`). The page's SEO is v7's (`PageSeo` in the block map; on TanStack the saved `site` block's `seo` defaults and templates too), and the TanStack routes keep what v7's `cmsRouteConfig` gave them: the options the site passed (titles, ignored search params, pending times), every other search param reaching the loader, its cache times and its head (robots, Open Graph, Twitter Card, canonical, JSON-LD); Next.js gets v7's metadata (canonical, robots). The router's module-scope `QueryClient` moves into `getRouter`. It replaces v7's page routes (`cmsRouteConfig`, `createDecoPage`, …), deletes v7's admin routes, and keeps any other file that exists;
6. **imports**: `ctx.device` in v7 loaders read from the loader's request (other `ctx` reads reported), then the codemod over `src/` (`reference/import-map.md`): v7's pure helpers and `@decocms/apps-commerce` move to `@decocms/compat-v7`, and on TanStack Start `src/imageUrl.ts` is written and given to `createDecoRouter`'s `Wrap`; v7 names the bindings keep move to `@decocms/tanstack` subpaths, the draft names and Studio's origins to the site's binding root (`@decocms/tanstack` or `@decocms/nextjs`, never `@decocms/blocks`), the rest are reported name by name. The image URLs it reports (`createImageUrl` with `decoCdn`'s options) follow the site's 7.x release, or, when the site kept its own copy of v7's image helper, that copy's rules and the site's register calls. `stripAssetHosts` is left at decoCdn's default, `"leading"`, even for a site whose v7 code stripped the asset hosts anywhere (7.x before 7.71.4, or such a copy): the PO approved the switch (2026-10-15), and the report's "image URLs" line counts and lists the content and code URLs whose image URL changes (a URL that merely contains an asset URL, `https://other.host/https://assets.decocache.com/…`);
7. **scripts**: `predev`/`prebuild` run `deco schema && deco content` (`&& deco check`), and `deco schema --check` goes into the site's CI right after the install step (the pull-request workflows when there are any; never v7's `regen-blocks`), run through the lockfile's runner (`bunx`, `pnpm exec`, `yarn`, `npx`) and the install's working directory. It fails a pull request whose `.deco/schema.gen.json` differs from what `deco schema` writes. A workflow it can't edit (none, or a multi-line install) is reported.
