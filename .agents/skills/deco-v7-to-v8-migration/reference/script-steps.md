# What the script does

The full list behind `SKILL.md` ("Run"). What it does, in order (`scripts/migrate.ts`):

1. **content**: saved blocks into `.deco/blocks`, v7 generated files removed, v7 async-rendering wrappers (`website/sections/Rendering/Lazy.tsx`, `SingleDeferred.tsx`, `Deferred.tsx`) unwrapped to the sections they held (v8 has no async rendering), the seven legacy names outside the alias table rewritten (`reference/legacy-names.md`), A/B tests keyed on a random matcher get its saved-block name as `experiment`;
   **settings**: site settings folded into the `CMS` block (`.deco/blocks/CMS.json`, type `cms-settings`): the v7 Site block's (`Site`/`site`) `previewHosts` → `preview.hosts` (the field moves, ports kept, each entry trimmed and lowercased as v7 compared it; an entry that isn't a host is reported). The hosts Deco runs the site on (`<site>.deco.site`, `<site>.deco-cx.workers.dev`) are not written: the binding allows them from its `site` option, and the report's "preview hosts" line names the `site` to pass (from `DECO_SITE_NAME`) (with no `previewHosts` in v7 nothing more is needed: the binding then allows only those two, as v7 did), a literal `collectorAddress` on `OneDollarStats` → `analytics.collector`, and an earlier prerelease's `Telemetry.json`/`Analytics.json` → their sections, field for field and variants included (the old files are deleted). It keeps what `CMS.json` already has, writes nothing when there's nothing to fold, and a second run changes nothing. The report lists the environment-only settings to move by hand (`DECO_ALLOWED_PREVIEW_HOSTS`, `DECO_OTEL_*` sampling, `DECO_ANALYTICS_ENABLED`/`ONEDOLLAR_ENABLED`/`ONEDOLLAR_COLLECTOR`);
2. **secrets**: v7 secrets re-encrypted with `.deco/secrets.pub`;
3. **block map**: the site's `registerSectionLoaders({ … })` (and `registerNonCriticalSections`) turned into exports of the same map; then `.deco/index.ts` with each block under a short name plus an alias under its v7 name, after vendoring the app loaders and actions the content calls into `src/vendor`. A section's descriptor names it by its v7 type name (`site/sections/….tsx`), and `src/views.ts` maps each name to its module. On a TanStack Start or Next.js site, v7's matchers the content uses (`device`, `random`, `cookie`, `host`, `pathname`, `queryString`, `location`, `multi`) are registered from `@decocms/compat-v7/matchers` over the binding's `matcherContext()` (TanStack: `matchPage(href)` in the page's server function tells them the page), and each saved random matcher gets its saved name as `cohort` (v7's sticky key in `deco_segment`); `environment` is reported. `loadSections(sections, request, pageUrl)` runs v7's section loaders with v7's rules (`@decocms/compat-v7/sections`; the nested walk of the site's 7.x release). A section loader v7 never ran (not registered) is reported, not wired;
4. **imports**: `ctx.device` in v7 loaders read from the loader's request (other `ctx` reads reported), then the codemod over `src/` (`reference/import-map.md`): v7's pure helpers and `@decocms/apps-commerce` move to `@decocms/compat-v7`, and on TanStack Start `src/imageUrl.ts` is written and given to `createDecoRouter`'s `Wrap`; v7 names the bindings keep move to `@decocms/tanstack` subpaths, the draft names and Studio's origins to the site's binding root (`@decocms/tanstack` or `@decocms/nextjs`, never `@decocms/blocks`), the rest are reported name by name. The image URLs it reports (`createImageUrl` with `decoCdn`'s options) follow the site's 7.x release, or, when the site kept its own copy of v7's image helper, that copy's rules and the site's register calls;
5. **scripts**: `predev`/`prebuild` run `deco schema && deco content` (`&& deco check`).
