# Framework code: the v8 bindings, and what stays site code

From the site migrations; the sites and what the commit hashes refer to are listed in `SKILL.md` ("Gotchas by subject").

v8 keeps the framework layer in two bindings, released with `@decocms/blocks` at one version (`^8.4.0`): `@decocms/tanstack` (TanStack Start on Cloudflare Workers, deployed the Deco way) and `@decocms/nextjs` (any Next.js App Router app). Use them; don't copy v7's worker, draft, preview or image code into the site. What neither binding covers (commerce flows, SEO, device-specific UI) is site code. Each package's README has the full wiring; `examples/tanstack-worker-smoke` and `examples/nextjs-binding-smoke` in this repo are complete apps.

## TanStack Start (`@decocms/tanstack`)

- **Worker entry**: `createDecoWorker({ serverEntry, cms, site, dev, pageCache })` from `/worker` replaces v7's `createDecoWorkerEntry`. Built in: `/deco/_liveness`, 404 for v7's admin paths, drafts (the host allowlist, the cookie, no-store and noindex), CMS redirects before any route, the visitor and its first-visit cookie, Studio's `frame-ancestors`, one `Set-Cookie` per cookie, `x-page-status`. The worker caches no page (PO, 2026-10-21: the page cache is site-owned, as on Next.js): the script writes `src/worker-entry.ts` as the recipe in `@decocms/tanstack`'s README, the site's own cache on the Cloudflare Cache API (`pageCache`, which the worker calls only for a `GET` of the current release, never a preview), with v7's `buildSegment` pasted in as the cache's segment (`loggedIn: true` is never cached), v7's `csp` as `csp: { reportOnly }`, v7's cache profiles in `PROFILES`, the key on path, device, segment, assignments (`readAssignments`/`assignmentsKey`) and `<build>.<revision>` (`cacheVersion`), `__cseg` CDN caching of navigation data, and v7's `POST /_cache/purge` with the `PURGE_TOKEN` secret and `{ paths, segments? }`. It's the site's code now: change the profiles, the key or the purge there. The visitor's cookie is added by the worker after `pageCache` answers, so a cached copy never stores one and a new visitor served from the cache still gets theirs: never add it, or any other visitor cookie, inside the cache. The other options: `preload`, `previewHosts`, and `routes` for requests the site answers itself (a commerce proxy, a sitemap; v7's `proxyHandler`). The script reports v7 options it didn't carry. Code the site keeps (geo cookies, a v7 request context) wraps the worker's `fetch`; it needs no new option.
- **Build hash**: `decoTanstack({ buildHash: <CI commit sha> })` from `/vite` (CI sha, then git, then the time) defines `__BUILD_HASH__` and includes `decoContent()` from `@decocms/blocks/vite`. The package reads no env: the site passes the CI value.
- **Root document**: `DecoDocument` from `/react` (`site`, `lang`, `nonce`, `editShortcut`) mounts `StudioBridge` and `DraftBadge` from `@decocms/blocks/preview`, the events bus, `NavigationProgress` and `StableOutlet`. A layout it can't express (a skip link before `<main>`) keeps its own document and renders `<DecoPreview site="…" />` from `/react` in its `<body>`: the bridge, the draft badge and the draft they read (`StudioBridge` alone leaves draft pages without the badge).
- **Studio**: the page loader returns `pathTemplate: match.entry.path` (the page `matchRoute` matched) in its loader data, so "." on the store page opens that page in Studio's editor, as v7's `cmsRoute` did with `path`. Each page section renders in v7's wrapper, `<section id={sectionId} data-manifest-key={component}>`: Studio's editor outlines, selects and scrolls to those.
- **Router and server functions**: `createDecoRouter` (`/router`) keeps `?q=`; a router that needs TanStack's `hydrate` builds its own router with `decoParseSearch`/`decoStringifySearch`. `createStart(() => ({ serverFns: { fetch: decoServerFnFetch } }))` (`/start`). The worker decides the draft, so delete the draft middleware in `start.ts`; pages read it with `contentClient(cms)` (`/server`).
- **Image**: `Image`, `Picture` and `Source` from `/react` render v7's markup with v7's props (the script moves those imports). The binding knows no commerce platform, so the script writes the site's own URLs to `src/imageUrl.ts` and wires them as `createDecoRouter({ routeTree, Wrap: ({ children }) => <ImageUrlProvider value={imageUrl}>{children}</ImageUrlProvider> })`, where `imageUrl = createImageUrl({ providers: [vtexCatalog(), shopifyCdn(), decoCdn({ domain, quality, sources: "all", ...byRelease })] })`: `createImageUrl` and `decoCdn` from `@decocms/blocks/image`, `vtexCatalog` from `@decocms/apps-vtex/image`, `shopifyCdn` from `@decocms/apps-shopify/image`. Keep both helpers whatever the site's platform: v7 resized VTEX and Shopify images on every site, so dropping one changes those URLs. A store with Nuvemshop images (`*.mitiendanube.com/stores/…/products/…-{w}-{h}.{ext}`) also lists its own provider before `decoCdn`, since no `@decocms/apps-*` package covers Nuvemshop (see below). That is v7's `Image` byte for byte, an `Image` or `Source` without a width included (`width=NaN … NaNw`, as v7 wrote it); `domain` and `quality` are what the site passed to `registerImageCdnDomain`/`registerImageQuality`, else left out. v7's `Image` changed across 7.x releases; `byRelease` is, for the `@decocms/blocks` version the site ran (the script's report spells the whole line for it):

  | Site's 7.x | `decoCdn` options besides `domain`, `quality`, `sources: "all"` |
  |---|---|
  | before 7.71.0 | `legacyHosts: []`; `domain` defaults to `"decoims.com"` there |
  | 7.71.0 to 7.71.3 | `legacyHosts: []` |
  | 7.71.4 | `legacyHosts: ["decoims.com"]` |
  | 7.71.5 on | none (and, from 7.77.1, the Nuvemshop provider below for a store with Nuvemshop images) |

  `stripAssetHosts` stays at its default, `"leading"`, on every row. Before 7.71.4, v7 stripped the asset hosts anywhere in a source; the switch is approved (PO, 2026-10-15) and changes only a source that merely contains an asset URL. The report's "image URLs" line lists those URLs for the PR.

  A site that kept its own copy of v7's image helper (a file under `src/` that defines `getOptimizedMediaUrl`) keeps that copy's rules, not its release's: the script reads the options from the copy and from the site's `registerImageCdnDomain`/`registerImageQuality` calls, and reports them on the copy's own line (fuzzed against each release's `Image.tsx` and two storefronts' edited copies). A copy whose rules it can't read is reported for you to compare by hand. One approved change from v7 (PO, 2026-10-14): an already-resized Deco CDN URL in the content (`https://assets.decocms.com/image?…&src=…`, or the `decoims.com`, `deco-assets.edgedeco.com` and `deco-assets.decoazn.com` endpoints) is re-resized from its `src`. v7 wrote `src=image`, which the CDN can't serve. Without a provider every source goes through the Deco CDN, VTEX and Shopify images too. Check a page's image URLs against v7's. v7's Nuvemshop rule, for the site's `src/imageUrl.ts` (`tests/tanstack-image-markup.golden.test.ts` holds it to v7's markup):

  ```ts
  const NUVEMSHOP_IMAGE = /^(https:\/\/[a-z0-9-]+\.mitiendanube\.com\/stores\/.+\/products\/.+)-\d+-\d+\.(\w+)$/;
  const NUVEMSHOP_SIZES = [50, 100, 240, 320, 480, 640];
  const nuvemshop: ImageProvider = {
    name: "nuvemshop",
    match: (src) => NUVEMSHOP_IMAGE.test(src),
    format(src, { width }) {
      const m = src.match(NUVEMSHOP_IMAGE);
      if (!m) return null;
      const size = NUVEMSHOP_SIZES.find((s) => s >= width);
      return `${m[1]}-${size ? `${size}-0` : "1024-1024"}.${m[2]}`;
    },
  };
  // providers: [vtexCatalog(), shopifyCdn(), nuvemshop, decoCdn({ domain, quality, sources: "all" })]
  ```
- **Draft names and Studio's origins**: `DRAFT_PARAM`, `DRAFT_COOKIE`, `DRAFT_HEADER`, `draftResponseHeaders`, `STUDIO_ORIGINS`, `STUDIO_FRAME_ANCESTORS` and `isStudioOrigin` come from the root, `@decocms/tanstack` (not from `@decocms/blocks`); the script moves them.
- **Cache metrics**: the worker records `http.server.request.duration` (route template, method, status class, cache decision, device) in the CMS's telemetry by itself (`recordServerRequest` from `@decocms/blocks/metrics`, the bindings' API; the site imports nothing); its `cache` label is the `X-Cache` the site's `pageCache` answers with. v7's `DECO_METRICS` writes have no writer; the worker entry's `pageCache` is where a site sends hit/miss/bypass anywhere else (`telemetry.md`).

## Next.js (`@decocms/nextjs`)

- **Drafts**: `decideDraft`, `draftRequestHeaders`, `rewriteToDraftRoute`, `applyDraft` and `isDraftRoutePath` from `/proxy` in `proxy.ts` (or `draftProxy` for a site with no proxy of its own); `bindDraft(cms, { searchParams, site })` and `contentClient(cms)` from `/server` on the `/_draft` route and in a layout that reads content. Pass the same `{ site, previewHosts }` to both. Details and gotchas: `nextjs.md`.
- **Studio and the badge**: `<StudioBridge site="…" />` in the root layout and `<DraftPreviewIndicator />` on the draft route, from `@decocms/nextjs`. Each CMS page renders `<StudioPage pathTemplate={match.entry.path} />` (a `<meta>` React puts in the head), so "." opens that page in Studio; the root layout stays across navigations and can't know it. Studio's editor outlines, selects and scrolls to top-level `<section id data-manifest-key={component}>` elements, v7's `SectionRenderer` wrapper: a site whose section list renders its own wrapper (v7 storefronts on Next often did) makes that wrapper a `<section>` with those two attributes.
- **Request metric**: `instrumentation.ts` (next to `app/`) is `export { register } from "@decocms/nextjs/instrumentation";`, which records `http.server.request.duration` from Next's own request span; a site already on `@vercel/otel` or an OpenTelemetry SDK adds `serverRequestSpanProcessor()` to its span processors instead (`telemetry.md`).
- **next.config**: `withDeco(config)` from `/config` puts v7's draft header rules first and adds Studio's dev origins; it adds no rewrites (v7's `/deco/*` handlers are gone) and no `transpilePackages`.
- **Image**: `createDecoImageLoader(imageUrl, { fallback: nextImageOptimizer })` from `/image-loader` as the `loaderFile`, over the site's `createImageUrl`. The loader knows no platform: a VTEX store lists `vtexCatalogWebp()` and `vtexFileManager({ via })` from `@decocms/apps-vtex/image` (`via` is the resizer its loader uses today: `"query"` or `"thumbor"`), then `decoCdn({ quality: "high", fit: "contain", layout: "quality-last" })` from `@decocms/blocks/image`. URLs match the site's current loader byte for byte, except the approved re-resizing of an already-resized Deco CDN URL (above). A loader still on `via: "query"` should move to `"thumbor"`: VTEX's `?width=&aspect=true` resizer answers 500 for raster files since 2026-10-07 (PO-approved, a site change).
- **Draft names and Studio's origins**: from the root, `@decocms/nextjs` (its own copy; never `@decocms/tanstack` or `@decocms/blocks`).
- **Dev**: nothing to pass. `createCMS` reads `NODE_ENV`, so `next dev` keeps local content and `next start` serves the hosted release; drop a v7 `isNextDev`/`dev` line (the `dev` option still overrides it when a site needs to).

## Site code either way

- **SEO/head**: a head builder; SEO blocks return the page's SEO.
- **Device detection**: v7's own from `@decocms/compat-v7` (`detectDevice` from `/device`; `useDevice` under `DeviceProvider` from `/tanstack` or `/nextjs`, seeded with `requestDevice()` from their `/server`). The TanStack worker keys its cache by device on its own.
- **Cookies and request state**: pass the request and response headers explicitly, or a site-owned `AsyncLocalStorage`, instead of v7's `RequestContext`.
- **Cart, user, wishlist, sign-in flows and commerce loaders**: vendored next to the loaders the script copied, sending through the v8 client.
- **Section loaders**: v7's registered map, run once per page by `loadSections` (`.deco/index.ts`, over `runSectionLoaders` from `@decocms/compat-v7/sections`), globals included; a loader that throws keeps its section's saved props and lands in `degraded`.
- **Module-level config from v7 apps is cross-request state.** A v7 app's `configureX({...})` singleton (the website app's SEO defaults, for one) called from the page loader on every request is shared by every request in the isolate. A preview host and production share the worker, so a draft's values can land in a concurrent release render that the edge then caches. Put per-page values in the page's own state and pass them to whatever read the singleton.
- **Identification headers** (`x-powered-by`, the outbound `User-Agent`) are the site's own values; if they change (v7 sent its package version), list it as the site's difference.
- **Keep v7's platform client, or adopt the v8 one?** Keeping the vendored v7 client (and its cached loaders and fetch cache) keeps every upstream request identical, so recorded upstream fixtures replay. If you keep it, drop the v8 `@decocms/apps-<platform>` dependency nothing imports, and list the move to its client plus the `/next/caching` recipe (`cachedLoader` is gone in v8) as a follow-up.
- **Error reporting.** v7's `onResolveError` sent every failed section or loader to the site's exception reporting. v8 has no hook: `client.resolve` returns `[value, error]`, and a section loader that throws is caught in its block function. Report both explicitly there (same attributes as before, so dashboards keep working); `console.error` alone only reaches the SDK's sampled log export.
- **A worker-level A/B split (`withABTesting`, `SITES_KV`).** If the KV holds no config for the site's hosts, nothing was split: delete the wrapper and the binding. If it does, on TanStack Start replace the wrapper with `abTestingRoutes` from `@decocms/compat-v7/tanstack/worker` (v7's split as a handler run first in `createDecoWorker`'s `routes`, with `worker: () => worker` so the worker's own bucket still gets its cookie; README of `@decocms/compat-v7`). One difference a site sees: legacy-origin HTML leaves through the worker, so it gets the worker's `preload` hints and security headers, which v7 added only to its own pages.
- **Not ported to the TanStack worker**: v7's caching of POST server functions by body. A site that relied on it keeps that wrapper or lists it.
